## Блок A. Файл определения слоёв на WFS

**A.1. Причина, по которой `levelsagg` не анонсирован — установлена
фактом.** REST GeoServer (`GET .../featuretypes/levelsagg.json`):
`"advertised": false`. Слой — виртуальная SQL-таблица без геометрии
(`select distinct usname, usern_co, left(usern_co,4) rn from
levelsagg_ready`), явно скрыта от `GetCapabilities` при регистрации.

**Критично для остального блока A**: прямой `GetFeature`/WPS по имени
уже работает и без этого флага (round45 показал это для WPS, в этом
раунде подтверждено и для обычного WFS `GetFeature` — 313 записей), но
**нативный WFS-провайдер QGIS так использовать слой не может** —
проверено фактом: `QgsVectorLayer` с любым вариантом WFS-URI
(`typename='pikurr:levelsagg'`) даёт `isValid()=False` без текста
ошибки — провайдер сверяется с `GetCapabilities` и молча отбрасывает
неанонсированный typename ещё до `DescribeFeatureType`/`GetFeature`.
То же самое и через GDAL/OGR-провайдер (`WFS:` префикс с `TYPENAME=`) —
тоже `isValid()=False`; без явного typename GDAL просто подставляет
первый АНОНСИРОВАННЫЙ слой (`fields_latest`), не наш.

**Вывод**: включение `advertised=true` — не улучшение, а **жёсткое
условие**, без которого справочник в `.qlr`/QGIS не откроется никаким
способом. Готовая команда — в пакете подтверждений в конце отчёта.
→ Причина **подтверждена фактом**; сама правка **не применена**
(прод-запись).

**A.2. `.qlr` с тремя слоями** — собран, `REPIKURR/tools/pikurr_layers.qlr`
(и его копия в `REPIKURR/repikurr/public/`, публикуется кнопкой,
см. блок B):
- `pikurr:levelsagg` (WFS, без ограничения по охвату — 313 строк, лёгкая);
- `pikurr:fields_latest` (WFS, `restrictToRequestBBOX='1'`,
  `pagingEnabled='true'` — обоснование в A.3);
- `pikurr:image_assessment` (растр) — через **XYZ/тайловое подключение
  к `/geoserver/gwc/service/wms`**, не через обычный WMS. Установлено
  фактом, почему только так: `tiled=true` с произвольным размером
  канвы (как шлёт QGIS "WMS"-слой, например 1400×900) отдаёт `400: The
  requested tile dimensions 900x1400 do not match those of the grid
  set (256x256)`; обычный `/geoserver/wms` вообще никогда не отдаёт
  заголовок `geowebcache-cache-result` — рендерит вживую всегда, минуя
  кэш. Только клиент с XYZ-схемой (запрашивающий ровно 256×256 по сетке
  z/x/y) реально попадает в кэш GWC.

**A.3. Стоимость WFS-слоя — измерено фактом** (`geobotany.of.by`,
`pikurr:fields_latest`, GeoJSON с геометрией):

| охват | объектов | объём | время |
|---|---|---|---|
| весь слой | 55 784 | 98.6 МБ | ~116 с — **неприемлемо** |
| один район (2212, самый крупный) | 9 039 | 18.6 МБ | ~22 с — тоже тяжело |
| bbox размером с экран карты (~5×5 км, z13) | 83 | 232 КБ | 0.8 с — приемлемо |

Настроено `restrictToRequestBBOX='1'` — QGIS запрашивает только
объекты в текущей области просмотра, полный охват не загружается
никогда, пока пользователь сам не отдалит карту на весь регион.

**A.4. Проверка сходимости чисел с плагином** — проверено фактом в
реальном QGIS (тот же headless-стенд, что и round45, C.3):
- справочник: код землепользователя «Фоменков Г.В.» получен запросом
  к `levelsagg` (напрямую по имени, т.к. `advertised` ещё не включён —
  см. A.1) — `2212000055`;
- `fields_latest` (слой из `.qlr`), фильтр `nr_user LIKE
  '2212000055%'`, агрегация по `valuation`/`area_ha`: **1 объект, 5.6
  га, сценарий tillage**;
- плагин (round45, C.3) на том же землепользователе дал: **1 объект,
  5.6 га, tillage**.
**Числа совпадают полностью, расхождений нет.**

Побочная находка: первый запрос сразу после `loadLayerDefinition()`
может вернуть 0 объектов (WFS-провайдер QGIS ещё не закончил
асинхронную инициализацию) — повторный запрос через несколько секунд
даёт верный результат. Отражено в инструкции (блок B.2) явной
рекомендацией подождать после открытия файла.

**A.5. Проверка в GUI с интерфейсом** — **не сделано, графическая
среда недоступна** на координаторской машине (только headless
`QT_QPA_PLATFORM=offscreen`). Все проверки A.2-A.4 выполнены
программно через PyQGIS API в реальном QGIS 3.44.7 (не имитация — тот
же движок, что в GUI), но визуального осмотра человеком, что слои
действительно красиво рисуются на экране, не было. **Нужно ваше
подтверждение**: откройте `REPIKURR/tools/pikurr_layers.qlr` в QGIS
(после того как будет применена правка A.1 — иначе справочник не
подключится) и подтвердите, что три слоя видны на карте как ожидается.

## Блок E. Предупреждение о мелких тайлах

**E.1. Установлено фактом, при каких условиях доля мелких тайлов
законно высока** — и это **не то, что предполагал round45**.
Измерено на реальном, полностью исправном кэше (`geobotany.of.by`):

| зум | fields_latest | image_assessment | режим bbox |
|---|---|---|---|
| z8 | 25.0% | 50.0% | полный охват слоя |
| z9 | 21.4% | 32.1% | полный охват слоя |
| z10 | 38.5% | 40.7% | полный охват слоя |
| z11 | 52.2% | 56.3% | полный охват слоя |
| z12 | 57.1% | 63.3% | полный охват слоя |
| z13 | 0% | 0% | **прицельный** bbox (`tiles_with_data.json`, центроиды полей) |

**Доля растёт с ростом зума при полном охвате, а не падает** — округ
предположения round45 («широкий охват на тайл, много фона») был верным
по механизму, но неверным по направлению: на низком зуме один
гигантский тайл почти всегда захватывает хоть что-то из разбросанных
по региону полей, а на высоком зуме подавляющее большинство мелких
тайтов приходится на промежутки МЕЖДУ полями — пустых тайлов
СТАНОВИТСЯ БОЛЬШЕ, не меньше. Проблема не в конкретном зуме — в том,
что засев (и `gwc_http_seed.py` без `--bbox`, и реальный
`deliver.py:_seed_gwc_layer`) покрывает весь ПРЯМОУГОЛЬНИК слоя
целиком, большая часть площади которого физически не занята полями.
Это уже нарушало бы правило на z9-z12 — на существующем, ничем не
новом диапазоне засева — если бы это когда-либо проверялось этим
конкретным способом (не проверялось: `deliver.py` эту метрику не
считает вообще, только `gwc_http_seed.py` как ручной диагностический
инструмент, и раньше запускался с прицельными bbox, не с полным
охватом).

**E.2. Порог сделан не «зависящим от зума», а зависящим от РЕЖИМА
проверки** (обоснование в E.1 — зависимость от зума немонотонна и не
даёт разумного единого числа): `REPIKURR/tools/gwc_http_seed.py`,
новый параметр `--warn-small-fraction THRESHOLD` (0..1, по умолчанию
`None` — предупреждение выключено, доля по-прежнему считается и
печатается в JSON). При полноохватном засеве (обычный режим работы
скрипта, включая эксперимент round45 G.2) предупреждение больше не
шумит. Для проверки на прицельных bbox с заведомым содержимым флаг
включается явно. `verify_tiles_have_data.py` не тронут — единственный
сценарий его использования (`tiles_with_data.json`) уже прицельный,
фиксированный порог 20% там верен как и раньше.

**E.3. Проверка обоих исходов — фактом:**
```
нормальная доставка (полный охват, z8, без флага):
  доля 25.0% — печатается, ПРЕДУПРЕЖДЕНИЯ НЕТ

прицельный bbox с заведомым содержимым (tiles_with_data.json, z13),
--warn-small-fraction 0.2, исправный кэш:
  доля 0.0% — ПРЕДУПРЕЖДЕНИЯ НЕТ

тот же режим, bbox намеренно сдвинут в пустой угол области (симуляция
"кэш отдаёт пустоту там, где ожидается содержимое"), --warn-small-fraction 0.2:
  доля 100.0% — ПРЕДУПРЕЖДЕНИЕ ЕСТЬ, с точным числом
```
→ **Подтверждено фактом по всем трём пунктам ТЗ.**

которое сам этот раунд призван соблюдать.
