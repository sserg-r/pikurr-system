## Блок B. Проверки должны ходить туда же, куда фронтенд

### B1. `healthcheck.py` — проверка по реальным URL

`REPIKURR/healthcheck.py` дополнен функцией `check_gwc_layers`: она НЕ
собирает URL вручную, а читает `REPIKURR/tools/smoke/captured_gwc_urls.json`
— файл, который теперь пишет сам `smoke.mjs` (доработан этим блоком:
захватывает первый увиденный запрос к `/geoserver/gwc/service/wms` для
каждого кэшируемого слоя, сохраняет как JSON). `bbox` в захваченном URL
заменяется на заведомо непустой тайл из `tiles_with_data.json` (правило
непустых тайлов — случайный/панорамный bbox из живой сессии браузера
непредсказуем по содержимому), все остальные параметры (`layers` с
префиксом workspace, `tiled=true`, `version`, `format` и т.д.) —
дословно те, что реально ушли с фронтенда. Тело ответа разбирается
(PNG-сигнатура + минимальный размер + текст `Unknown layer`/`GWC Error`)
— не только код.

Прогон против прода (после раскатки блока A round34, слой уже
исправен):
```
gwc_layer[pikurr:fields_latest]    True  HTTP 200, PNG, 48272 байт, geowebcache-cache-result=HIT
gwc_layer[pikurr:image_assessment] True  HTTP 200, PNG, 10390 байт, geowebcache-cache-result=HIT
```

Побочно найдена и исправлена проблема деплоя: `healthcheck.py`
обычно копируется на VPS/эмулятор ОТДЕЛЬНЫМ файлом (не всем деревом
`PIKURR_REFACTOR/`), поэтому жёстко прошитый относительный путь до
`docs/round32_assets/tiles_with_data.json` там не существует —
добавлены переменные окружения `TILES_WITH_DATA_PATH` и
`CAPTURED_GWC_URLS_PATH` с понятной ошибкой вместо падения, если файлы
не найдены.

### B2. Проверка фактом: ломаем слой на эмуляторе

Обнаружено попутно: фронтенд на эмуляторе был **не синхронизирован** с

на эмуляторе (были в apt только Node 18, Playwright требует 20+) —

Прогон по шагам (все — эмулятор, `http://localhost`):

| шаг | действие | smoke.mjs | healthcheck.py (`gwc_layer[...]`) |
|---|---|---|---|
| 1 | база (фикс round34 синхронизирован) | 9/9 | `True`, HTTP 200 |
| 2 | `layers={rasterFqName}` → `layers={rasterLayer}` в `MapView.jsx`, пересборка | 6/9 (4a/6/7 упали) | **`False`, HTTP 400 `GWC Error: Unknown layer image_assessment`** |

что было в round34, и зеленеет обратно после отмены — цепочка
`smoke.mjs` (перехватывает реальный URL) → `healthcheck.py`
(переигрывает его структуру напрямую, без браузера) работает как
задумано. Важная оговорка о механизме (честно, не подгонка): здоровье
`healthcheck.py` соответствует ПОСЛЕДНЕМУ прогону `smoke.mjs`, не
живому фронтенду в реальном времени — если фронтенд-регрессия
произойдёт МЕЖДУ прогонами `smoke.mjs`, обычный 5-минутный
`external_healthcheck.sh` её не увидит, пока `smoke.mjs` не
перезапустят и не перезапишут `captured_gwc_urls.json`. Это и есть
причина, почему блок B3 делает `smoke.mjs` частью самой выкатки — тогда
`captured_gwc_urls.json` обновляется именно в момент, когда риск
регрессии максимален.

### B3. Дымовой сценарий — обязательная часть выкатки

Выбор: **скрипт выкатки сам вызывает `smoke.mjs`**, не отдельный шаг в
инструкции. Инструкция полагается на то, что оператор (человек или
будущая сессия) прочитает и не забудет последний пункт — именно так
слой оставался сломанным между round32 и round34, хотя дымовая
проверка теоретически была «обязательна» по формулировке CLAUDE.md уже
с round33. Скрипт технически не даёт считать деплой успешным (код
возврата 1) без зелёного прогона.

Добавлен `REPIKURR/deploy_frontend_vps.sh` — формализует
последовательность round34 (`docker build` → бэкап тега на VPS →
`docker save | gzip | scp | docker load` → retag →
`up -d --force-recreate react-client`), затем **обязательно** прогоняет
`tools/smoke/smoke.mjs` против только что раскатанного домена; при
красном прогоне явно печатает, что деплой не считается завершённым, и
готовую команду отката (сам не откатывает — решение за оператором).
Синтаксис проверен (`bash -n`), **на VPS в этом раунде не запускался**
— раскатывать нечего, фронтенд не менялся со времени round34 (правило
«Не делать»: никаких изменений фронтенда на бой сверх блока B, а он
весь — про эмулятор).

## Блок C. Прогрев кэша при доставке

### C1. Оценка до внедрения

**Какие зумы реально запрашивает фронтенд** — два источника, как просит
ТЗ:

1. **Дымовой сценарий** (`smoke.mjs`, доработан этим блоком — пишет
   `tools/smoke/all_tile_requests.json`, разобран
   `tools/analyze_zoom_usage.py`): загрузка + один клик "зум +" + один
   сдвиг дают диапазон **z=9…11** (60/58/40 запросов соответственно).
2. **Реальный интерактивный сеанс** (`claude-in-chrome`,
   `geobotany.of.by`, колесо мыши на карте вплоть до упора): от
   стартового z=9 до **z=18** (дефолтный максимум Leaflet, слой
   продолжает отдавать реальные тайлы, `HTTP 200`, до самого предела).

Оговорка честно: при быстром синтетическом зуме (8 уровней за ~2с,
имитация через `WheelEvent`) часть запросов получила **`503`** —
похоже на control-flow лимит GeoServer (та же неподтверждённая
гипотеза round32, `controlflow.properties` не трогать). Это шум от
нереалистично быстрой синтетической прокрутки, не находка о реальном
поведении пользователей — при паузах между уровнями (~1.5с) 503 не
воспроизводился.

**Сколько тайлов в покрытии** — границы слоёв из `GetCapabilities`
(`EX_GeographicBoundingBox`, реальные, не оценка): `image_assessment`
— `26.436°…30.938° в.д., 54.790°…56.126° с.ш.` (чуть шире, чем у
`fields_latest`). Тайлы по сетке GWC (`EPSG:900913`, 256×256):

|---|---|---|

| 10 | 98     | 16   |
| 11 | 378    | 56   |
| 12 | 1484   | 196  |
| 13 | 5720   | 728  |

| 18 | 5 630 043 | — заведомо неподъёмно |

**Оценка объёма на диске** — не прикидка, реальные средние веса
тайлов, замеренные `curl` по 8 точкам покрытия на каждом зуме (те же

**Забегая вперёд (см. C2)**: реальный целевой объём тайлов по счёту
самого GWC на z9-14 оказался **~2× больше** оценки этого раздела
(64416 против расчётных ~29960 на слой `image_assessment`) — вероятно,
GWC дополняет запрошенный диапазон до границ гридсета/дозаполняет
частично покрытые тайлы на краях, не обрезая их по `EX_GeographicBoundingBox`

подогнана задним числом), расхождение зафиксировано отдельно.

Накопительный объём z9-14 (оба слоя): **≈1.14 GiB** — укладывается в
квоту 2 GiB (57%) с запасом, ничтожно мало относительно ~16 ГБ
свободного места на VPS. z=15 **один** уже добавил бы ≈3.1 GiB (по

**Оценка времени засева** — метатайл 4×4 на VPS стоит **~370-660мс**

на случай более пристального разглядывания района/области (не
отдельного поля — глубокий зум на одно поле, z15-18, редкий и
персональный кейс, не обязан быть предзасеян: цену промаха платит один
пользователь один раз, не размазана на множество посетителей одной и
той же свежей области). Обоснование объёма и времени переходит к C2 —
это ещё оценка, не факт после внедрения.

### C2. Внедрение и проверка на эмуляторе

**Реализовано**: `REPIKURR/deliver.py` — новые функции `_seed_gwc_layer`
(запуск `POST /gwc/rest/seed/{layer}.json` с `type=seed`,
`zoomStart`/`zoomStop`/`threadCount` из констант, опрос статуса до
завершения или предохранителя по времени) и `seed_gwc_cache` (обёртка
по обоим кэшируемым слоям, ловит любое исключение — засев не должен
останавливать доставку). Встроено в `deliver()` **строго после**
`reload_geoserver` (растровые гранулы уже свежие) и после truncate
векторного кэша — шаг `seed_gwc_cache`, между `reload_geoserver` и
`healthcheck`. Результат — в статус-файле доставки
(`seed_gwc_cache` ключ, как и `healthcheck`).

**Параллелизм**: 2 потока (обоснование — C1: столько же, сколько vCPU
на VPS).

**Найден и исправлен баг опроса статуса** (проверено фактом на
эмуляторе, до фикса — ложноположительный): реальная схема ответа GWC
— `{"long-array-array": [[...], ...]}`, объект с ключом, не голый
список. Первая версия кода проверяла `isinstance(tasks, list)`, что
для объекта всегда `False` → засев считался завершённым на первой же
секунде опроса. Обнаружено кросс-проверкой: после "успешного"
5-секундного засева объём на диске (224 МБ) оказался в разы меньше
расчётного (~1.14 ГиБ) — несоответствие не списано на погрешность
оценки, а прослежено до конкретной строки кода.

**Реальные (не оценочные) числа заглянул через собственный счётчик
GWC**, полученные при живом прогоне: суммарная цель — **64416 тайлов**
для `image_assessment` и **59232** для `fields_latest`(!) на z9-14 —
**заметно больше** расчёта C1 (~29960/~29960) — см. оговорку в C1.

#### Критическая находка: засев ненадёжен — зависает на ~50% без ошибок

Дважды независимо воспроизведено (первый раз — во время реальной
доставки с засевом, второй — отдельным прямым REST-вызовом после
чистого перезапуска GeoServer, чтобы исключить влияние доставки как
таковой): прогресс засева идёт нормально первые ~90-105 секунд (десятки
тысяч тайлов, обе задачи, оба слоя по отдельности в разных прогонах),
затем **останавливается ровно на ~50%** цели и не возобновляется. Во
время зависания:

- CPU контейнера GeoServer — **0.72%** (`docker stats`, снято прямо во
  время зависания) — не перегрузка, не рендеринг, процесс явно ничем не
  занят;
- в логе GeoServer — **ноль** строк `geoserver.flow` (control-flow) за
  всё время зависания — запросы даже не доходят до стадии, которую
  видит control-flow (не тот же класс проблемы, что нерешённая гипотеза
  round32);
- во втором воспроизведении зафиксирован явный маркер: поле статуса в
  ответе GWC (5-й элемент массива на задачу) сменилось с `1` на `2`
  ровно в момент остановки прогресса — до этого GWC также репортил
  положительный ETA (уменьшающийся), после — **отрицательный**;
- **спустя ~15 секунд после смены статуса на `2` список задач стал
  пустым** (`"long-array-array": []`) — то есть GWC САМ репортит
  «нет активных задач» тем же способом, что и при настоящем успешном
  завершении, хотя фактически на диске оказалось тайлов заметно МЕНЬШЕ
  цели (проверено: 29960 файлов `.png` в каталоге слоя против заявленной
  цели 64416). **Пустой список задач GWC не отличим от настоящего
  успеха, не проверив реальный объём на диске отдельно** — тот же
  урок раунда 33 (200 с пустым телом — не успех), но уже про
  собственный REST GWC, не про Caddy/GeoServer WMS.

Причина не установлена — версия-гипотеза (не проверена отдельным
экспериментом, честно помечена как неподтверждённая): периодический
`cacheCleanUpFrequency=60с` диск-квоты (HSQL-хранилище,
round34 D1) конкурирует с активным засевом за тот же файл кэша квоты,
и точка остановки (~90-105с, около второго цикла cleanup) совпадает по
порядку величины — совпадение, не доказательство.

**Решение**: `GWC_SEED_ENABLED` в `deliver.py` переключён на
**выключено по умолчанию** (`false`) — включать только явным
`GWC_SEED_ENABLED=true` для контролируемых экспериментов, не для
постоянной эксплуатации, пока причина зависания не найдена и не
исправлена. `GWC_SEED_MAX_WAIT_S` снижен с 1800с (изначальная
консервативная оценка) до **300с** — на практике наблюдалось только
«быстро закончилось» или «зависло насмерть», ни одного случая «долго,
но доехало», ждать дольше нет смысла.

**Позитивная часть находки**: правило ТЗ «неудачный засев не должен
оставлять витрину без данных» **подтверждено фактом** — первый (ещё
багованный) прогон продолжил доставку и завершился успешно несмотря на
то, что засев на самом деле не закончился; принудительная остановка
(`kill`, симулирующая зависшую доставку) корректно записала статус
`step_failed: seed_gwc_cache` через существующий SIGTERM-механизм
(round25, блок B4) — новый шаг интегрировался с этой инфраструктурой
без доработок.

**Замеры, которые всё же получены (по факту, честно с пометкой, что
это баланс на фоне незавершённого внедрения)**:

- Время доставки БЕЗ засева (эмулятор, 2 прогона): **27с, 26с**.
- Время экрана из 12 тайлов в новой области ДО засева (эмулятор, сразу
  после truncate, холодный кэш), 3 непересекающихся области (проверено
  программно, `tiles_overlap()`), порядок перемешан:

  | область | первый тайл (MISS) | экран из 12, мс |
  |---|---|---|
  | idx=2 | 194мс | 339 |
  | idx=0 | 148мс | 156 |
  | idx=1 | 148мс | 450 |

  Медиана — **339мс**. Того же порядка, что round34 C2 (медиана
  4×4 на эмуляторе — 380мс) — согласуется, не подгонялось.

- Время доставки И время экрана ПОСЛЕ полностью успешного засева —
  **не получены**: ни один прогон не довёл засев до объявленной GWC
  цели без зависания, честно помечено как «не сделано» из-за находки
  выше, а не как «результат отрицательный».

### C3. Внедрение на VPS

**Не выполнялось** — ТЗ обуславливает блок C3 успехом на эмуляторе
(«После успеха на эмуляторе: одна реальная доставка с засевом»); C2
успеха не показал (см. критическую находку выше). Разворачивать
ненадёжный механизм на проде — прямое нарушение духа raунда 34
(«не подстраивать под цифры/не гнаться за один шаг, если это создаёт
риск для витрины») и явного правила текущего ТЗ «не нагружать VPS выше
ступени с ошибками». На VPS `GWC_SEED_ENABLED` не менялся (дефолт
`false`, засев там никогда не запускался).

**Откат** (для будущего раунда, когда причина зависания будет найдена
и захочется включить): `GWC_SEED_ENABLED=false` (уже дефолт) — засев
просто не запускается, доставка ведёт себя как до этого раунда.
Отдельного отката конфигурации не требуется — фича полностью
опциональна через один флаг.

## Блок D. Метатайл — только если C не снял вопрос

ТЗ формулирует блок как развилку: «если после засева промахи всё ещё
случаются часто — вернуться к эксперименту; иначе — зафиксировать
вопрос закрытым». **Ни одна из веток не выполнима буквально**: засев
не был успешно развёрнут (блок C2) — предпосылка «после засева»
(реальный прод-прогон с работающим прогревом) не наступила, значит
нельзя ни измерить «промахи после засева» (нечего измерять — засева
нет), ни зафиксировать «вопрос закрыт засевом» (он не закрыт — засев
не работает).

**Вывод**: вопрос кэш-прогрева остаётся **открытым**, не закрытым — ни
в одну из сторон, которые предполагало ТЗ. Размер метатайла (`4×4`)
**не менялся** — выводы round34 C2/C3 (не менять без данных за это) по
прежнему в силе, эксперимент с 5 повторами из этого блока не
проводился, т.к. его условие («после засева промахи часты») не
наступило. Добавлено в CLAUDE.md, раздел «Открытые вопросы»
(см. ниже) — открытым текстом, не как достижение.

## Блок E. Сеть со стороны пользователя

round34 C4 замерял долю сети с координаторской машины — там одно
TLS-рукопожатие на холодном соединении занимает ~335мс, что не похоже
на канал реального пользователя (может быть географически далёк от
VPS, может быть, наоборот, ближе; неизвестно без факта). Инструкция
ниже — что прислать, чтобы оценить реальную долю сети именно для
пользователя, не додумывая за него.

**Инструкция для пользователя** (добавлена как отдельный файл
`docs/round35_assets/devtools-network-howto.md`, текст также ниже):

1. Открыть `geobotany.of.by` в браузере, открыть DevTools (`F12` или
   `Ctrl+Shift+I` / `Cmd+Option+I`), вкладку **Network**.
2. Обновить страницу (`Ctrl+R`/`Cmd+R`) с открытым DevTools.
3. Включить слой «AI оценка» в панели слева (если ещё не включён).
4. В списке запросов найти любой запрос на `gwc/service/wms` (можно
   отфильтровать по `wms` в строке поиска над списком).
5. Кликнуть по запросу → вкладка **Timing** справа.
6. Сделать скриншот вкладки Timing (там разбивка: `Queueing`,
   `Stalled`, `DNS Lookup`, `Initial connection` (включает TLS),
   `Request sent`, `Waiting (TTFB)`, `Content Download`).
7. Прислать скриншот **и** три числа словами: `Initial connection` (это
   сетевой RTT+TLS до сервера), `Waiting` (это время ответа сервера —
   рендер+обработка), `Content Download` (передача самого файла).

**Зачем именно так**: `Initial connection` — доля, которую можно
объяснить географией/интернет-провайдером пользователя (round34 C4 —
это она была ~335мс с координатора); `Waiting` — доля стороны сервера
(round34 C1 — метатайл GWC при промахе, или мгновенный ответ при
попадании в кэш); складывать их в одно число, как это невольно делает
общий "время ответа сервера" в некоторых инструментах браузера
(упомянутые в исходной жалобе пользователя "891 мс"), — и есть причина,
по которой round34 не смог разложить исходную цифру на компоненты,
не имея этой детализации.
