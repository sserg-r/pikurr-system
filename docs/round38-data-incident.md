### A5. Признаки давности снимка

**Сделано**: `manifest.json` внутри найденной локальной копии
доставленного пакета (см. B2) + метки времени файлов внутри ZIP
(`unzip -l`, сохраняет оригинальные mtime источника, не время
распаковки).

**Доказательства**:
- `manifest.json` пакета `pikurr_update_2024_2025_2026-09-24_09-41.zip`:
  `{"created_at": "2026-09-24T09:42:07", "year": 2025,
  "years": [2024, 2025], "version": "2.0", "contents": ["vectors.gpkg", "rasters/"]}`
  — **не содержит** ни источника БД, ни версии кода ETL, ни числа
  строк, ни контрольных сумм (это ровно пробел, который закрывает
  блок D1).
- `create_assessment_schema.sql` внутри пакета датирован **2026-04-17
  11:28** (mtime внутри архива) — не 24 сентября. Растры
  `rasters/2024/*.tif` внутри пакета датированы **2024-11-29** —
  оригинальная дата обработки этих гранул, задолго до раунда.
- В локальной ETL-базе `pikurr_refactor-db-1` (см. B4) `assessment.updated_at`:
  год 2023 и 2024 — **2026-04-16 10:48:40** (единая метка, «пакетная»
  вставка); год 2025 — диапазон **2026-01-22 07:14 — 2026-01-27 12:06**
  (более старый, чем 2024!). Три года — три разных по возрасту снимка
  в одной базе.
- Контейнер `pikurr_refactor-db-1` (координаторская машина) создан и
  запущен **2026-09-24T09:41:06** — с точностью до минуты совпадает с
  именем пакета (`..._2026-09-24_09-41.zip`) и с началом сборки
  (манифест `created_at: 09:42:07`). Это означает: контейнер с
  остановленной базой был поднят специально перед сборкой пакета,
  пакет собран сразу же, без проверки содержимого.

**Вывод**: подтверждено — снимок в `pikurr_refactor-db-1` не единый
«срез на дату», а слипшиеся вместе фрагменты минимум трёх независимых
прогонов ETL (2023/2024 — апрель 2026, 2025 — январь 2026), и версия
схемы пакета (SQL-файл апреля) подтверждает возраст независимо от
даты создания ZIP.

## Блок D. Чтобы это не повторилось

### D1. Провенанс в пакете

`PIKURR/src/tasks/package.py`: `manifest.json` версии `2.1` — добавлены
`source_db` (хост/имя БД, без пароля), `etl_git_commit` (git-коммит ETL-

`assessment`, `raster_counts_by_year`, `vectors_gpkg_sha256`.
`REPIKURR/deliver.py`: манифест целиком копируется в статус-файл
(`_StepTracker.manifest`, заполняется сразу после `unpack` — попадает в
статус даже при падении на ЛЮБОМ более позднем шаге, не только при
успехе). `python3 -m py_compile` — без ошибок. Живым пакетом не
проверено (следующая реальная сборка на стенде это подтвердит).

### D2. Предполётная проверка состава

`deliver.py`: `_check_year_composition()` — до первого изменения БД/
растров сравнивает `manifest["years"]` с набором лет, уже стоящим на
боевой `assessment` (`SELECT DISTINCT year`). Несовпадение —
`YearCompositionGuardError`, боевые таблицы не тронуты, обход — явный
`--allow-year-change` (по аналогии с `--allow-shrink` round26).
Встроено в `deliver()` сразу после проверки версии схемы (шаг
`check_year_composition`). Первая же реальная доставка раунда (блок
C2, штатная — тот же год 2025, что и на витрине) прошла через эту
проверку без срабатывания — ожидаемо, состав не менялся.

### D3. Сохранение предыдущего состояния

`deliver.py`: `backup_before_swap()` — `pg_dump -Fc` трёх боевых таблиц
в `REPIKURR/backups/backup_<таймстамп>.dump` сразу после обеих
предполётных проверок, до первого реального изменения БД. Ротация по
числу файлов (`BACKUP_RETENTION_COUNT`, по умолчанию 10). Результат
(путь, размер, время) — в статусе, ключ `backup`. Восстановление:
`pg_restore -d <db> <файл>`. Объём/время — не измерены отдельным
прогоном в этом раунде (округ38 не успел; первая реальная доставка с
этим кодом покажет реальные цифры для боевой БД VPS — таблицы `assessment`
64к-155к строк в этом раунде, ожидаемый размер дампа — единицы-десятки
МБ, секунды).

### D4. Расхождение кода на VPS

`REPIKURR/deploy_backend_vps.sh` — по образцу `deploy_frontend_vps.sh`.
`--check`: сравнивает sha256 `deliver.py`/`healthcheck.py`/`watchdog.py`
