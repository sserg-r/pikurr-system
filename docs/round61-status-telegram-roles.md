## 3. Markdown в Bot API (блок A, п. 2)

Источник: `https://core.telegram.org/bots/api`, раздел «Markdown style» (legacy):

> To escape characters '_', '*', '`', '[' outside of an entity, prepend the character '\\' before them.
> Escaping inside entities is not allowed, so entity must be closed first and reopened again…

Документация требует экранирования, но **прямо не говорит**, что непарный символ даёт отказ отправки.
По разрешению пользователя выполнена живая отправка трёх тестовых сообщений в настроенный чат стенда
(2026-10-16, временный контейнер из образа `etl`, токен из окружения, значения не выводились;
по подтверждению пользователя два сообщения дошли):

| Случай | Ответ Bot API |
|---|---|
| A: `_`, `*`, `[` вне блока кода | **400 Bad Request: can't parse entities: Can't find end of the entity starting at byte offset 81** (сообщение не доставлено) |
| B: обратная кавычка внутри блока `…` (парное число) | 200 |
| C: штатный вид из notifier — `_` внутри блока `…` | 200 |

Вывод: дефект подтверждён **как класс** (непарные `_ * [` вне блока кода → 400, ошибка уходит только в
`logger.warning`, аварийное сообщение теряется). Исходная гипотеза («`_` в тексте ошибки почти всегда
даёт 400») уточнена: текст ошибки в `notifier` обёрнут в обратные кавычки, там `_` безопасен; ломают
непарные `*`/`[`/`_` вне обёртки и нечётное число обратных кавычек в тексте ошибки. Исправление по ТЗ
(блок C, п. 1): простой текст без `parse_mode`.

Стенд, блок A, п. 3: в `~/pikurr-system/.env` на стенде `TELEGRAM__TOKEN` и `TELEGRAM__CHAT_ID`
**заданы** (проверено по признаку «задано», значения не читались). Контейнер `etl` на момент проверки
остановлен (`exited`), поэтому окружение контейнера не читалось.
