## Блок A. Разведка (без изменений)

### A1. Обзоры в растрах

**Сделано**: `gdalinfo` на 5 файлах мозаики на VPS (`N-35-22-V-v-2/3/4`,
`N-35-23-A-a-2/3`), проверка `indexer.properties`/`*.properties`
мозаики, параметров чтения coverage `image_assessment` в GeoServer
(REST), прямое измерение через `/proc/<pid>/io` (байты) и `strace -f`
(файлы) на **эмуляторе** при одном запросе широкого тайла (2°×1°,
256×256px, layer `image_assessment`).

**Находки**:
- Все 5 проверенных TIF: `Size 6144×7168` (или `6144×6912`), сжатие
  `LZW`, **`Block=6144x1`** — полосовая организация (весь ряд пикселей
  в одном блоке), **не тайлированы**. **`Overviews` не встречается ни
  разу** — пирамиды обзоров нет вообще.
- `2025.properties` мозаики: `LevelsNum=1` — подтверждает: у мозаики
  как целого тоже только один (полное разрешение) уровень пирамиды.
- GeoServer-параметры чтения coverage: `USE_JAI_IMAGEREAD=true`,
  `AllowMultithreading=false`, `SUGGESTED_TILE_SIZE=512,512` — но при
  нетайлированных исходниках "подсказка" размера тайла чтения не может
  обойти полосовую организацию файла.
- **Один запрос широкого тайла (машина: эмулятор) открывает ~230
  разных TIF-файлов**, но суммарно читает всего **~668 КБ** (`/proc/PID/io`,
  `read_bytes` до/после: `1356185600`→`1356869632`). В среднем ~2.9 КБ
  на файл — то есть цена не в объёме байт, а в **числе операций
  открытия/поиска** файлов при отсутствии пирамиды: на низком зуме
  запрос всё равно трогает каждый полноразрешающий файл в охвате по
  отдельности, вместо одного уменьшенного обзорного уровня.

**Подтверждено** полностью: обзоров нет, тайлинг файлов отсутствует,
цена одного широкого тайла — не байты, а количество открываемых
файлов (IOPS), что напрямую связывает эту находку с диагнозом round27
(диск/IOPS — первое узкое место).

### A2. Растры против файлового кэша

**Сделано** (машина: VPS, только чтение):
- `du -sh` каталога мозаики: **1.3 ГБ** (912 файлов).
- `free -m` в состоянии покоя: `total=5924 used=3714 free=897
  buff/cache=2034`, **swap уже используется: 190 МБ** (не 0 — даже
  без активной нагрузки в момент замера).
- `docker stats --no-stream`: `geoserver 2.697GiB/3GiB` (RSS почти у
  самого потолка контейнерного лимита), `postgis 565MiB/1.5GiB`,
  `react 10.9MiB/128MiB`, `caddy 57.9MiB/256MiB`.
- Резидентность файлов мозаики в кэше ОС — `vmtouch`/`fincore` на VPS
  не установлены, а установка пакетов на VPS не входит в разрешённое
  «только чтение»; вместо этого — самодостаточный скрипт на `mincore()`
  через `ctypes` (ничего не устанавливает, использует только уже
  имеющийся `python3`), по всем 912 файлам мозаики: **резидентно 25.3%
  страниц (82329/325406) ≈ 337 МБ из 1331 МБ**.

**Вывод**: мозаика (1.3 ГБ) физически меньше, чем `buff/cache`
(2.0 ГБ) в моменте, но резидентно в кэше — только четверть её объёма.
Что вытесняет: GeoServer занимает 2.7 из 3 ГБ лимита контейнера почти
целиком (heap 2048M + off-heap/native буферы), плюс PostGIS 565 МБ —
на файловый кэш ОС для растров остаётся мало места на хосте с 5.9 ГБ
общей RAM, и своп уже используется даже в покое. Мозаика **не
помещается в доступный кэш с комфортным запасом**.

**Подтверждено** полностью.

### A3. Как фронтенд реально запрашивает тайлы

**Сделано**: перехват реальных сетевых запросов в браузере (Chrome,
`claude-in-chrome`, не буквально Firefox — тот же результат) на живой
витрине `https://geobotany.of.by`, три сценария: загрузка страницы,
сдвиг карты (drag), включение слоя «AI оценка».

**Находки**:
- **GWC не используется нигде** — все запросы идут напрямую
  `.../geoserver/pikurr/wms?...GetMap...`, нет `/gwc/service/wms`, нет
  параметра `tiled=true`. Подтверждает round25/26/27: слои не
  зарегистрированы в GWC, каждый тайл — полный рендер, не кэш-хит.
- Сетка — стандартная Leaflet, тайл 256×256px, EPSG:3857.
- **Загрузка страницы (один пользователь, без единого действия)**
  запрашивает **24 тайла одновременно** — по 12 на каждый из двух
  векторных слоёв (`pikurr:fields_latest` и `pikurr:fields`,
  ОБА сразу, не один в зависимости от режима — избыточность, не была
  явно нужна пользователю в этот момент).
- Один `drag` (сдвиг карты на том же зуме) — **8 новых тайлов**
  (только для вскрывшейся области, Leaflet кеширует уже загруженные;
  запрошен только один слой — `fields`).
- Включение переключателя «AI оценка» — **16 тайлов растра
  `image_assessment`** + 1 `GetLegendGraphic`, тоже напрямую WMS, не
  через GWC.
- **Критичная живая находка, не гипотеза**: при загрузке страницы **6
  из 12 запросов к `pikurr:fields_latest` вернули HTTP 503** прямо
  сейчас, в бою (2026-09-22, во время этой проверки). Повторный прямой
  запрос той же комбинации (curl) сразу после — `200`, тело валидный
  PNG: сбой не постоянный, а именно от одновременного всплеска.
  Причина найдена фактом — `~/repikurr/geoserver_data/controlflow.properties`
  на VPS:
  ```
  timeout=60
  ows.global=100
  ows.wms.getmap=10
  ows.wfs.getfeature.application/msexcel=4
  user=6
  ows.gwc=16
  user.ows.wps.execute=1000/d;30s
  ```
  **`user=6`** (не более 6 одновременных запросов на пользователя) и
  **`ows.wms.getmap=10`** (глобально) — а одна загрузка страницы уже
  создаёт 24 одновременных WMS GetMap-запроса от одного пользователя.
  Это **не гипотеза о нагрузочном тесте «тяжелее реальной»** — это
  подтверждённый фактом баг конфигурации, который ломает **самый
  обычный, однопользовательский** визит на сайт, безо всякой
  синтетической нагрузки.

**Важный практический вывод**: это отдельный, лёгкий рычаг —
поднять `user`/`ows.wms.getmap` в `controlflow.properties` — не
входил в исходный список рычагов ТЗ (обзоры/куча/GC-потоки/GWC-засев),
но найден фактом при честной разведке A3 и, вероятно, даёт более
быстрый и надёжный выигрыш, чем часть исходных пяти. Кандидат для
проверки в блоке C (не изменялось на VPS — только диагностика).

**Побочная находка**: `pikurr:fields_latest` и `pikurr:fields`
запрашиваются ОБА при каждой загрузке страницы, хотя в интерфейсе
виден только один режим года за раз — потенциальное удвоение
начальной тайловой нагрузки. Не проверялось, чем это вызвано во
фронтенд-коде (фронтенд менять запрещено, но само наблюдение стоит
знать).

**Подтверждено** полностью.

### A4. Параметры JVM

**Сделано**: поиск источника `ParallelGCThreads=20 -XX:ConcGCThreads=5`
в `entrypoint.sh` образа `kartoza/geoserver` (машина: VPS, `docker exec
... grep`, только чтение).

**Находка**: значения **жёстко зашиты литералами** в скрипте
(`-XX:ParallelGCThreads=20 -XX:ConcGCThreads=5` — не переменные
окружения, не производные от числа ядер), собираются в `GEOSERVER_OPTS`
и попадают в `JAVA_OPTS` ДО `${ADDITIONAL_JAVA_STARTUP_OPTIONS}`,
который подставляется последним в командной строке. Значит:
переопределение через `ADDITIONAL_JAVA_STARTUP_OPTIONS` (тот же
механизм, что включил GC-лог в round27, B2) технически работает — JVM
берёт последнее значение `-XX:ParallelGCThreads=N`/`ConcGCThreads=N`
в командной строке. Не менялось на VPS (запрещено ТЗ), только
установлен факт механизма для блока C.

**Подтверждено** полностью.

### A5. GC-лог

**Сделано**: скачан накопленный с round27 (B2) лог
(`~/repikurr/geoserver_data/gc.log`, машина: VPS), разбор пауз по
регулярным выражениям.

**Результат** (окно лога: `2026-09-21T11:02:52` — `2026-09-21T18:36:43`,
~7.5 часов, 660 GC-событий):
- Всего распознано пауз: **756**.
- Медиана: **45.1мс**, среднее: **61.4мс**, максимум: **4166.1мс**.
- **Пауз >1с: 3** — `12:02:44` (4166.1мс, `Young (Mixed)`),
  `12:17:30` (1170.0мс, `Young (Prepare Mixed)`), `12:20:22` (3474.4мс,
  `Young (Concurrent Start)`).
- Full GC: 1 раз, `11:49:47`, 713.9мс — не катастрофично.

**Сопоставление с нагрузкой**: round27 B5 (реальная доставка с
одновременной нагрузкой k6 1→5→10 VU) шла с `12:13:53` по `12:21:12` —
**обе паузы `12:17:30` и `12:20:22` попадают точно внутрь этого окна**.
Третья (`12:02:44`, самая длинная) на ~11 минут раньше — по времени
согласуется с завершающими, самыми тяжёлыми ступенями лестницы round27
B4 (20/40 VU), которые шли непосредственно перед B5. Отдельных
сохранённых `iostat`/`%steal` с точной привязкой к этим трём меткам
времени нет (round27 не вёл непрерывный `vmstat` через всю сессию, а
только на отдельных ступенях) — сопоставление по совпадению временных
окон, не по одновременному прямому измерению `%steal` секунда-в-секунду.

**Вывод**: длинные паузы **не фоновые, беспричинные события** — все
три происходят строго во время известных эпизодов реальной нагрузки
(round27 B4/B5), не в покое. Это говорит в пользу гипотезы «GC-паузы —
следствие той же нагрузки на диск/память, что уже диагностирована»,
а не независимая, отдельная проблема JVM, но не исключает вклад GC
как усиливающего фактора (мусор от рендеринга большого числа тайлов —
дополнительное давление на heap именно в моменты нагрузки).

**Подтверждено частично**: число/максимум/паузы>1с — установлены
фактом; точное сопоставление секунда-в-секунду с `%steal`/`iostat` —
не выполнено (данных нет), только сопоставление по известным временным
окнам активности.

## Что требует решения пользователя (по срезу блока A)

1. **Живой продакшн-баг найден фактом (A3)**: `controlflow.properties`
   (`user=6`, `ows.wms.getmap=10`) ломает обычную, однопользовательскую
   загрузку страницы (24 параллельных WMS-запроса от одной загрузки
   > лимита в 4 раза) — не гипотетическая нагрузка, происходит прямо
   сейчас на боевом сайте. Требует решения: поднимать ли лимиты
   (кандидат для проверки в блоке C на эмуляторе, применение на VPS —
   отдельное решение пользователя, вне разрешённого этим раундом
   «только чтение»).
2. **`fields_latest` и `fields` запрашиваются оба при каждой загрузке
   страницы** (A3, побочная находка) — потенциальное удвоение
   начальной нагрузки, требует разбора фронтенд-кода (менять фронтенд
   в этом раунде запрещено) — вне scope, но стоит знать.
3. **Обзоров растров нет, файлы не тайлированы** (A1) — прямой кандидат
   для блока C (`gdaladdo`), не выполнялось в этом срезе (только
   разведка).
4. **Блоки B, C, D, E — не выполнены**, отдельное продолжение по
   решению пользователя (сессия зафиксирована на блоке A явно, чтобы
   не потерять контекст на большом объёме).
5. **GC-паузы >1с сопоставлены с нагрузкой только по временным окнам**,
   не прямым одновременным измерением `%steal`/`iostat` — если нужна
   более строгая проверка причинности, это отдельная задача (вести
   `vmstat`/`iostat` непрерывно вместе с GC-логом на будущее).
