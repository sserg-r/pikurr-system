## Версия

**Текущая версия системы — `2.0.0`** (раунд 59). Предыдущая — `1.0.0` (раунд 44).

- **Схема нумерации** (семантическая, назначается вручную при заморозке
  раунда, не при каждом коммите): `X.Y.Z`, где `X` — несовместимые
  изменения (схема БД, формат манифеста пакета, публичные эндпоинты
  API), `Y` — новая функциональность без нарушения совместимости, `Z`
  — исправления в рамках существующей версии. Основание для `2.0.0` —
  смена схемы БД 3 → 4 (раунд 57).
- **Соответствие**: версия `2.0.0` ↔ git-тег `v2.0.0` (коммит, который он
  несёт — источник истины, текстом здесь не дублируется) ↔ `SCHEMA_VERSION=4`
  (`REPIKURR/deliver.py`, `create_assessment_schema.sql`) ↔ манифест пакета
  `version: "2.1"` ↔ плагин QGIS `1.2.0` (`pikurr_qgis/metadata.txt`) ↔ пакет
  данных на проде `pikurr_update_2025_2026-10-01_16-32.zip`
  (`etl_git_commit` = `625a0199…`, `vectors_gpkg_sha256` = `f412714c…`).
- **История**:
  - `1.0.0` (раунд 44, схема 3) — первая версия со сведёнными
    version↔commit↔схема↔манифест на трёх машинах.
  - `2.0.0` (раунды 45–58) — плагин QGIS 1.1–1.2; учёт года на витрине;
    индикация прогресса шагов 6–7 ETL; исправления D1–D4 раунда 57 (маска
    обработки по геопривязке, статистика по полигонам листов в фиксированном
    порядке, публичные растры без перекрытия, сведение частей участка);
    схема 4.
- **Сверка развёрнутого с репозиторием** (раунд 59, `docs/round59-version.md`):
  код ETL стенда, манифест пакета на проде, бэкенд и конфигурация стека VPS,
  маркеры схемы, витрина (имена ассетов), плагин, справочник районов,

## 2. Потоки данных

1. **Источник** — спутниковые/аэрофотоснимки полей (вне рамок ETL-репозитория, поступают отдельным процессом), обрабатываются PIKURR: сегментация полей, цветокоррекция, модель оценки состояния посевов.
2. **ETL-БД** (`pikurr-system-db-1` на стенде, единственный правильный источник боевых пакетов с round39) — постоянно работающий контейнер, содержит только актуальный текущий год (проверено фактом дважды — round38/39 и round42: только 2025 год, 59209/21280/55784 строк по трём таблицам).
3. **Сборка пакета** (`PackageTask`) — выгружает `agrifields`/`razgrafka`/`assessment` в `vectors.gpkg` (через `pg_dump -t`/`ogr2ogr`), копирует растры года(ов) в `rasters/<год>/`, пишет `manifest.json` (версия схемы, `source_db`, `etl_git_commit`, число строк по таблицам, число растров по годам, sha256 `vectors.gpkg`). **`etl_git_commit`** (round43, блок C) — берётся из переменной окружения `ETL_GIT_COMMIT`, запечённой в образ ETL при сборке (`docker build --build-arg ETL_GIT_COMMIT=$(git rev-parse HEAD)`, `git` в runtime-образе не устанавливается); резервный путь — прямой `git rev-parse HEAD` при локальном запуске вне контейнера.
4. **Перенос пакета** — вручную/скриптом в `inbox/` на целевой машине (VPS или стенд), с проверкой sha256 до переименования в финальное имя (`.part`-суффикс защищает от преждевременного подхвата вотчдогом).
5. **Доставка** (`deliver.py`, вызывается `watchdog.py`):
   - распаковка,
   - чтение манифеста,
   - проверка версии схемы (`SwapGuardError` при несовпадении) и состава лет (`YearCompositionGuardError`, обход — `--allow-year-change`),
   - `pg_dump`-бэкап боевых `agrifields`/`razgrafka`/`assessment` (custom-формат, `REPIKURR/backups/`, ротация по числу файлов),
   - импорт векторных данных в `_stage`-таблицы,
   - **одна транзакция** переноса `_stage` → боевые (сохранение OID, без `DROP CASCADE`),
   - копирование растров года(ов) в `data/geodata/<год>/`,
   - `REFRESH MATERIALIZED VIEW CONCURRENTLY` (`assessment_ready`, `assessment_ready_latest`, `levelsagg_ready`),
   - обновление GeoServer-сторов (harvest растрового каталога, `masstruncate` GWC-кэша для затронутых слоёв),
   - запись `static/year_district.json` (источник правды для фронтенда — список год/район),
   - прогрев GWC-кэша (`seed_gwc_cache`, z10-z12, см. раздел 7),
   - встроенный `healthcheck`,
   - удаление обработанного пакета из `inbox/`,
   - запись статус-файла (`status/<имя пакета>.json` — манифест, бэкап, healthcheck, seed-результат, время каждого шага).
6. **Выход** — обновлённые боевые таблицы PostGIS, обновлённые растровые каталоги, обновлённый `year_district.json`, (частично) прогретый GWC-кэш. Фронтенд читает `year_district.json` для списка год/район, запрашивает тайлы через GWC (кэшируемые слои) или напрямую через WMS (фильтрованные/исторические слои).

## 3. Схема БД витрины

- **Версия схемы**: `SCHEMA_VERSION = 4` (`REPIKURR/deliver.py`, `PIKURR/src/sqlscripts/create_assessment_schema.sql`); на проде 4 с доставки пакета `pikurr_update_2025_2026-10-01_16-32.zip` (раунд 57). Версия 4: `assessment_ready` — одна запись на пару (`nr_user`, год), геометрия — объединение частей участка, площадь — по объединению; маркер `schema_version=4` на трёх представлениях; при смене версии `deliver.py` пересоздаёт представления.
- **Боевые таблицы** (`public`, владелец `pikurr`): `agrifields` (векторный слой полей, PostGIS геометрия, индексы `agrifields_geom_geom_idx`/`idx_agrifields_geom`/`idx_agrifields_nr_user`), `razgrafka` (векторная разграфка листов, `razgrafka_geom_geom_idx`/`idx_razgrafka_geom`), `assessment` (оценка по годам, `assessment_fid_year_key` уникальный по (fid, year), `idx_assessment_fid_year`).
- **Материализованные представления** (обновляются `REFRESH CONCURRENTLY` после каждой доставки): `assessment_ready` (индексы по `district`/`geom`/`(nr_user, year)`/`year`), `assessment_ready_latest` (индексы по `geom`/`nr_user`), `levelsagg_ready` (агрегация, один составной индекс). Все три должны быть `ispopulated = t`.
- Дополнительно в БД — служебные схемы PostGIS `tiger` (геокодер, не используется приложением напрямую) и `topology` (не используется приложением) — не часть прикладной схемы витрины, присутствуют как часть базового образа `postgis/postgis:15-3.3`.
- **Данные исходного слоя** (раунд 57, блок A): в `agrifields` 3 425 значений `nr_user` встречаются более одного раза, из них 3 424 — дубли одного и того же полигона; по-настоящему многочастный участок один (`22490000030364`, две непересекающиеся части, 0,58 + 0,63 га). Исходные полигоны не менялись; к одной записи на `nr_user` они сводятся в `save_db` и в `assessment_ready`. Подробности — `docs/round57-fixes.md`, `docs/facts/data-io.md` (п. 3.2).
- **Состояние расчёта после раунда 57**: маска обработки переносится на холст по геопривязке (`classify`), статистика листов считается по полигонам своих листов в фиксированном порядке (`save_db`), публичные растры соседних листов не перекрываются (`export`); ограничение «статистика участков на нескольких листах зависит от порядка листов» снято (`docs/round57-fixes.md`, проверка C2). Независимая проверка посадки маски по местности — `docs/round58-docs.md`.
- Проверено фактом (2026-09-28): 40 таблиц, 3 материализованных представления, 92 индекса — состав стабилен с round39 (D1-D3 предохранители работают без изменения схемы).

## 4. Слои и эндпоинты

| Слой | Путь | Кэшируется (GWC) | Примечание |
|---|---|---|---|
| `pikurr:fields_latest` (векторный, фон) | `/geoserver/gwc/service/wms&tiled=true` | Да | `CQL_FILTER` только по году; GWC **игнорирует** `CQL_FILTER`/`STYLES` (round37) |
| `pikurr:image_assessment` (растр, текущий год) | `/geoserver/gwc/service/wms&tiled=true` | Да | Обновляется каждую доставку (harvest + `masstruncate`) |
| `pikurr:fields` + `CQL_FILTER` (подсветка группы, историчные года) | `/geoserver/pikurr/wms` (НЕ через GWC) | Нет | Обязательно напрямую — GWC не поддерживает фильтрацию по подмножеству |
| `image_assessment_<год>` (историчные растры) | `/geoserver/pikurr/wms` | Нет | Не регистрировался в GWC (round32) |
| WFS `GetFeature` (попапы, счётчики группы) | `/geoserver/pikurr/wfs` | — | `resultType=hits` для проверки пустой группы |

- **Grid**: `EPSG:900913` (Web Mercator, соответствует тайлам Leaflet). `metaWidthHeight` 4×4 (не менять на VPS без нового замера — round34 показал ухудшение на большем метатайле для холодных областей на эмуляторе).
- **Квота диска GWC**: 2 GiB, персистентна через рестарт (файл `geoserver_data/gwc/geowebcache-diskquota.xml`, не REST).
- **`/geoserver/gwc/service/wms` требует полное имя слоя** (`pikurr:слой`) — без workspace-префикса в пути, в отличие от `/geoserver/pikurr/wms`.
- **Диапазон прогрева**: `GWC_SEED_ZOOM_START=9`, `GWC_SEED_ZOOM_STOP=12` (round42 сужал до 9-14→10-12 на основании ошибочного вывода "z9 никогда не досеивается"; round43 опроверг сам вывод как ошибку пути; **round44, блок A** вернул z9 в диапазон — фронтенд открывается на z9 (`MapView.jsx`, `zoom={9}`), и это фактически подтверждено смоук-сценарием: первые ~25 тайловых запросов каждой сессии — z9, зум входит в тройку самых частых (60 запросов слоя `fields_latest` за прогон). Без z9 в засеве первый визит на витрину систематически получал MISS на стартовом экране). round43, блок A установил фактом (сверкой с `tile_math.py`): засев на z9-z12 записывает на диск ровно ожидаемое число файлов, без единого расхождения — вывод round42 о "недосеве" был методологической ошибкой (неверный путь проверки, `EPSG_900913_9` вместо `EPSG_900913_09`) и неверным сравнением с наивной оценкой "×4" вместо точной геометрии bbox. HIT-доля на реально используемых тайлах (`tiles_with_data.json`) — 100%; после округления round44 отдельно проверено HIT на самих стартовых z9-тайлах после прогона `masstruncate`+засева. round43, блок B: `deliver.py` завершает ожидание засева по факту стабильности числа файлов на диске (2 опроса подряд без роста, ~30с), а не по таймауту `GWC_SEED_MAX_WAIT_S=420` (остаётся аварийным потолком, не поднимался). **round44, блок B**: это по-прежнему признак затишья, не признак достижения цели — добавлена независимая сверка итогового числа файлов с геометрическим расчётом `tile_math.tile_range_for_bbox_3857` по реальному `nativeBoundingBox` слоя (REST); недобор > 10% и > 3 тайлов пишется в статус доставки как `shortfall_warning` с обеими цифрами, доставку не останавливает (прогрев — оптимизация). На реальном прогоне (VPS, z9-z12) полный засев обоих слоёв — 136.4с (60.4с `fields_latest` + 76.0с `image_assessment`), точное совпадение факт/расчёт (1835/1835 и 1992/1992 файлов), предупреждения нет; на контрольном тесте с искусственно урезанным диском (удалена половина z12) — предупреждение сработало с верными числами (847/1835, 53.8%), после досева — снова точное совпадение.

## 5. Процедуры

### 5.1. Сборка пакета
```
docker exec pikurr-system-etl-1 python3 -c "from src.tasks.package import PackageTask; PackageTask().run()"
```
**Перед сборкой** — обязательна проверка содержимого `pikurr-system-db-1` (год(ы), число строк, `updated_at`) — правило round38, единственный правильный источник.

### 5.2. Доставка
1. Проверить sha256 пакета.
2. Перенести в `inbox/` целевой машины через `.part`-суффикс, переименовать после проверки хэша.
3. Вотчдог подхватывает автоматически (poll 10с, защита от гонки записи `_is_stable`, задержка 2с).
4. Наблюдать статус — `status/<имя>.json` (обновляется по шагам) или `journalctl -u pikurr-watchdog.service -f`.
5. **Обязательно** дождаться `ok: true` и зелёного встроенного healthcheck, приложить манифест и содержимое к отчёту при первом развёртывании из нового источника.

### 5.3. Проверка
- `REPIKURR/healthcheck.py --base-url <домен> --json` — 11 проверок по содержимому (при двух кэшируемых слоях) (не только код ответа).
- `REPIKURR/tools/smoke/smoke.mjs` (Playwright) — 23 проверки реального пользовательского сценария (число растёт с правками сценария) в браузере, обязателен после любой выкатки фронтенда.
- `REPIKURR/tools/verify_tiles_have_data.py` — доля пустых тайлов по контрольному набору.

### 5.4. Обслуживание (смена конфигурации ВМ, плановые работы)
1. **Приостановить триггер автозапуска** — `yc serverless trigger pause pikurr-autostart-timer --folder-id <FOLDER_ID>` (без этого шага ручная остановка ВМ будет отменена функцией в течение интервала триггера, сейчас 5 минут).
2. Выполнить обслуживание (смена RAM и т.п. — вручную в консоли Yandex Cloud, Claude Code эти изменения не делает).
3. Вернуть триггер — `yc serverless trigger resume pikurr-autostart-timer --folder-id <FOLDER_ID>`.
4. Проверить фактом — `healthcheck.py`, `smoke.mjs`.

### 5.5. Восстановление после сбоя
- **Данные** (после неудачной доставки/ошибочной подмены) — `pg_restore -d <db> <файл>.dump` из `REPIKURR/backups/` (создаётся автоматически перед КАЖДОЙ подменой, ротация по числу файлов, по умолчанию 10). Восстановление в ДРУГУЮ базу требует предварительного `CREATE EXTENSION postgis`.
- **ВМ остановлена/недоступна** — автозапуск поднимает её самостоятельно (round42, блок C, проверено фактом — ~3-4 минуты до полностью рабочего состояния). Если триггер был приостановлен для обслуживания и забыт — поднять вручную из консоли или `yc compute instance start`.
- **ВМ остановлена посреди доставки** — по факту round42 (блок D): автозапуск поднимает ВМ, вотчдог сам обнаруживает незавершённый пакет в `inbox/` при своём перезапуске (`Pre-existing packages`) и запускает доставку заново с нуля; прерванная транзакция подмены данных откатывается PostgreSQL автоматически (крэш-safe по конструкции — импорт в `_stage` + одна транзакция переноса). Ручных действий, кроме реакции на саму причину остановки, не требуется.
- **GeoServer завис без OOM** (переполнение очереди квоты GWC при интенсивном прогреве, round41) — единственное известное восстановление: `docker restart pikurr_vps_geoserver`. Не автоматизировано.
- **Полная потеря ВМ** (не только БД) — конфигурация GWC
  (`geoserver_data/gwc/*.xml`, `geoserver_data/gwc-layers/*.xml`) и
  секреты (`geoserver_data/security/**`, `deliver.env`, `.env`)
  бэкапятся за пределы ВМ вручную: `REPIKURR/backup_config_offsite.sh`
  (round43, блок D) — запускается с машины с SSH-доступом к VPS
  (координаторская), два раздельных архива (config/secrets, secrets —
  права 600, никогда в git). Остальная конфигурация
  (`docker-compose.vps.yml`, `Caddyfile`, `geoserver_data/workspaces`,
  `geoserver_data/styles`) уже в git — восстанавливается обычным
  клонированием репозитория. Восстановление — `./REPIKURR/backup_config_offsite.sh --restore-config-to <dir>` для config-архива, secrets — вручную распаковать нужный `secrets_*.tar.gz` (права 600) на новую ВМ. Проверено фактом на стенде (round43): GeoServer поднимается с идентичными `metaWidthHeight`/квотой, тайлы отдаются HIT.

## 7. Ограничения и известные особенности

- ~~Засев GWC-кэша структурно не доходит до 100%~~ — **закрыто round43,
  блок A**: методологическая ошибка (неверный путь проверки), реальных
  потерь тайлов нет — засев записывает на диск точно расчётное число
  файлов, полностью и быстро (5-90с). Причина долгого ожидания в
  `deliver.py` (до round43) — не в самом засеве, а в ненадёжности
  REST-статуса GWC как индикатора завершения (round43, блок A, находка
  №3); устранена в блоке B (ожидание по факту роста файлов на диске).
  **round44, блок A**: z9 возвращён в диапазон засева (был исключён
  round42 на основании того же ошибочного вывода) — это фактически
  стартовый зум фронтенда, значимая доля первых тайловых запросов
  каждой сессии.
- **REST-статус GWC (`long-array-array`) — известная особенность, не
  основной признак завершения засева** (round43, блок A; закреплено
  round44): под определённой нагрузкой начинает возвращать
  неразбираемый/усечённый JSON (`JSONDecodeError`) ещё до того, как
  реальная запись тайлов на диск завершается, а иногда продолжает
  репортить неполный прогресс уже после того, как все файлы фактически
  записаны. С round43 `deliver.py` использует стабильность числа файлов
  на диске как основной сигнал (`_count_gwc_cached_tiles`), REST-статус
  — только диагностика/резервный путь. round44 добавил независимую
  сверку итога с геометрическим расчётом (`tile_math`) поверх этого —
  см. раздел 4.
- GWC-кэш может при определённых условиях интенсивного прогрева переполнить внутреннюю очередь квоты диска и вызвать зависание GeoServer без OOM (round41, живой инцидент на 3 ГБ) — не воспроизведено на 4 ГБ (round42), но механизм не исправлен, может повториться при достаточно интенсивной нагрузке.
- Автоматическая очистка карантинных каталогов/бэкапов/просроченных пакетов на VPS не запланирована ни одним таймером (round39) — растёт со временем, не критично на горизонте нескольких месяцев (запас места достаточный на момент round42).
- Интервал триггера автозапуска — 5 минут (не рекомендованные README 2 минуты) — решение пользователя при разворачивании через консоль; увеличивает теоретический потолок времени простоя.
- Триггер автозапуска создан через веб-консоль Yandex Cloud, а не полностью через `yc` CLI — при попытке через CLI (`serverless trigger create timer` v1 и v2) стабильно возникала ошибка `PermissionDenied`, не устранённая выдачей ролей `editor`/`functions.editor` на папку; причина не выяснена до конца (round42, блок C).
- `smoke.mjs`, шаги "Подсветка" (3.1-3.3) — теоретически хрупкий сценарий (фиксированная задержка вместо событийного ожидания), изредка даёт ложный отказ (round40/41/42) — второй прогон подряд неизменно чистый.
- ~~`etl_git_commit` в манифесте пакета всегда `null`~~ — **закрыто
  round43, блок C**: механизм (`ARG`/`ENV` в `Dockerfile` +
  `docker-compose.yml` build-arg) реализован и проверен фактом, манифест
  несёт непустой git-хеш.
  ~~**Остаточная проблема (round43)**: чекаут ETL на стенде отставал от
  истории git на десятки раундов, `etl_git_commit` указывал на
  устаревшую точку истории~~ — **закрыто round44, блок C**:
  инвентаризация показала, что реальных потерянных правок не было (2 из
  3 изменённых файлов на стенде были байт-в-байт идентичны origin/main,
  третий — `docker-compose.yml` — содержал забытый при коммите round43
  build-arg, занесён в репозиторий, и специфичные для стенда SSH-ключи
  доставки, вынесенные в не попадающий в git `docker-compose.override.yml`).
  После полного бэкапа рабочего дерева стенд синхронизирован с
  `origin/main` (`git reset --hard`), образ ETL пересобран с
  `ETL_GIT_COMMIT=$(git rev-parse HEAD)`. Проверено фактом: `git status
  --porcelain` на стенде пуст, `git rev-parse HEAD` == `origin/main`,
  манифест собранного пакета несёт тот же хеш, реальная доставка этого
  пакета на VPS прошла штатно (`ok: true`, healthcheck 10/10, smoke.mjs
  13/13).
