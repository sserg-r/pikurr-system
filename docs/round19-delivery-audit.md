## A2. Сквозной прогон — найден критический дефект на шаге 8

Пакет отправлен через `PushTask().run()` реально (ETL и фронтенд физически на
одном сервере, rsync идёт по loopback, поэтому шаги 1–7 укладываются в 7 секунд).

**Шаги 1–7 прошли полностью и без ошибок**: rsync → inbox, watchdog подхватил
за один опрос, 912 TIF скопированы в `data/geodata/2025/`, `agrifields`
(59209), `razgrafka` (21280), `assessment` (55784) переимпортированы, view
`assessment_ready`/`assessment_ready_latest` пересозданы, GeoServer REST вернул
200 на `/reset`, ZIP удалён, лог пишет «Доставка завершена успешно».

**Шаг 8 фактически не выполняется — фронтенд продолжает отдавать данные
пятимесячной давности.** Проверено не по HTTP 200, а по содержимому:

- WMS `GetMap` по bbox четырёх свежедоставленных листов вернул **чистый белый
  PNG** (1 цвет на всех пробах).
- WMS `GetMap` по bbox листа, который был в мозаике **до** сегодняшней
  доставки, вернул реальный растр (7 цветов классификации).
- Индекс ImageMosaic (`2025.shp`/`.dbf`/`.properties`) датирован **17 апреля**
  (5 месяцев до сегодняшнего прогона) и содержит **139 гранул**, тогда как на
  диске уже лежит 1048 TIF-файлов (912 из сегодняшней доставки + более старые,
  см. ниже).

**Причина**: `deliver.py:_reload_one_store()` вызывает PUT на URL стора и POST
`/reset` — это сбрасывает только внутренний кэш ридеров GeoServer, но не
запускает переиндексацию персистентного каталога гранул (shapefile-индекс).
Чтобы ImageMosaic увидел новые/изменённые файлы, нужен отдельный механизм —
явный harvest (REST `POST .../coveragestores/{store}/external.imagemosaic`
со списком файлов, либо удаление индексных файлов перед reset) — которого в
`deliver.py` нет. Векторная часть (PostGIS) обновляется мгновенно и корректно;
проблема — только в растровом слое.

**Побочная находка**: `copy_rasters()` никогда не удаляет старые TIF —
только копирует/перезаписывает одноимённые. На диске уже 1048 файлов при 912
в текущем пакете — «мёртвые» растры (для листов, выведенных из состава
предыдущих пакетов) остаются в каталоге навсегда и потенциально попадут в
переиндексированную мозаику, если её когда-нибудь пересобрать.

## A3. Целевые проверки

### Обратная связь отсутствует — подтверждено

`PushTask.run()` возвращается сразу после успешного `rsync`, не проверяя,
подхватил ли watchdog файл и успешна ли доставка. Учитывая находку A2 (шаги
1–7 «зелёные», а реального результата на фронтенде нет), отсутствие обратной
связи — не абстрактный риск, а причина, по которой сегодняшний дефект был бы
не замечен без ручной проверки карты.

**Предложение (не реализовано)**: `deliver.py` в конце `deliver()` пишет файл
статуса, например `<inbox>/../status/<имя_пакета>.json` с полями
`{"zip": ..., "finished_at": ..., "ok": true/false, "step_failed": ...}`;
`PushTask.run()` после rsync с разумным таймаутом опрашивает этот файл по ssh
(`ssh ... cat status/....json`) либо просто требует от вызывающего (дэшборда)
показать «отправлено, но не подтверждено» до появления файла.

### Цикл повторов при ошибке — подтверждено экспериментально

Битый ZIP (5 МБ случайных байт) в `inbox/`:
- `deliver.py` падает на `zipfile.BadZipFile` необработанным исключением;
  `subprocess.run` в `watchdog.py` получает ненулевой код, лог пишет
  `Delivery FAILED`;
- файл **остаётся** в inbox (строка `zip_path.unlink()` — последняя в
  `deliver()`, до неё дело не доходит);
- журнал **не растёт** — `seen.add()` в `watchdog.py` вызывается ДО
  `process_zip()`, поэтому в рамках одного работающего процесса файл не
  обрабатывается повторно;
- после рестарта процесса (сообщение `Pre-existing packages (will process)`)
  файл **обрабатывается заново** — и падает с той же ошибкой. Значит:
  «отравленный» ZIP будет проваливаться **при каждом будущем рестарте
  демона**, бесконечно, пока его не удалят руками — механизм не отличает
  «повторить после временного сбоя» от «никогда не станет валидным».

### Частично переданный файл — подтверждено фактом

Передача 300 МБ файла с ограничением скорости (`--bwlimit`) показала: во время
копирования в `inbox/` лежит `.pikurr_update_..._77-77.zip.rUJBe6` (файл с
точкой, временное имя `rsync`), не совпадающий с `glob("pikurr_update_*.zip")`.
Журнал `watchdog` за всё время передачи пуст. По завершении передачи rsync
атомарно переименовывает файл — в первом же опросе (10 с) `watchdog` его
подхватывает. Защита работает как задумано.

### Выбор «последнего» пакета — баг подтверждён (аналитически, из предыдущей сессии)

И `PushTask.get_latest_package()`, и `deliver.py:find_latest_zip()` берут
`sorted(glob(...))[-1]`. Реальные имена в истории (`journalctl`) все имели
одинаковую длину `years_tag` ("2024_2025"), поэтому баг ещё не проявлялся. Но
он воспроизводится аналитически: при удлинении `years_tag`
(`"2023_2024"` → `"2023_2024_2025"`) более новый по времени пакет
лексикографически сортируется **раньше** более старого — `[-1]` выберет
устаревший пакет как «последний». Правка не внесена — согласуется отдельно.

### Повторная доставка — идемпотентна для данных, но не для схемы

Реальный пакет `pikurr_update_2025_2026-09-17_00-25.zip` доставлен дважды
подряд (исходник сохраняется в ETL `/data_output/dist/`, `rsync` его не
удаляет). Результат:

| | до 2-й доставки | после 2-й доставки |
|---|---|---|
| `agrifields` | 59209 | 59209 |
| `razgrafka` | 21280 | 21280 |
| `assessment` | 55784 | 55784 |
| `assessment_ready` | 55784 | 55784 |
| дубликаты `(fid_ext, year)` в `assessment` | — | **0** |

Дубликатов нет и view не ломается — потому что `ogr2ogr -overwrite`
**полностью пересоздаёт** таблицу при каждом импорте (не upsert, не append),
так что повторный прогон безвреден для данных.

**Но обнаружена побочная проблема со схемой**: в живой БД у `assessment` НЕТ
ограничения `UNIQUE (fid_ext, year)`, объявленного в
`create_assessment_schema.sql` (`CONSTRAINT assessment_fid_year_key`). Причина
— порядок шагов в `deliver()`: шаг 3 (`import_vectors`, `ogr2ogr -overwrite`)
создаёт таблицу `assessment` **раньше**, со своей схемой (столбцы `fid`, `id`,
без уникального ограничения); шаг 4 (`recreate_views`, выполняет
`create_assessment_schema.sql`) видит, что таблица уже существует
(`CREATE TABLE IF NOT EXISTS`), и пропускает её создание — ограничение
никогда не применяется. Индекс `idx_assessment_fid_year` при этом создаётся
(`CREATE INDEX IF NOT EXISTS` срабатывает, так как такого индекса у ogr2ogr не
было), но он не уникальный. Сейчас это не создаёт видимых проблем (данные не
дублируются благодаря `-overwrite`), но если в будущем какой-то код станет
рассчитывать на это ограничение (например, `INSERT ... ON CONFLICT`), тихий
дефект схемы проявится.

### Побочная находка вне плана A3: `SIGTERM` не считается сбоем для `Restart=on-failure`

При проверке поведения при рестарте демон был остановлен через `kill -TERM`
(имитация внешнего завершения) — сервис перешёл в `inactive` и **не
перезапустился**, хотя в юните задано `Restart=on-failure`. Причина —
`SIGTERM` явно исключён из списка «сбоев» в `systemd.service(5)`: рестарт
происходит для ненулевого кода выхода или **необработанного** сигнала, но не
для `SIGHUP`/`SIGINT`/`SIGTERM`/`SIGPIPE`. Практическое следствие: если
процесс когда-либо будет завершён внешне «мягким» способом (не через
`systemctl stop`, а, например, скриптом или OOM-killer, использующим SIGTERM),
автоматического восстановления не будет — доставка молча остановится без
предупреждения. `sudo` на сервере недоступен (подтверждено повторно), поэтому
самостоятельно вернуть юнит в работу не удалось — сейчас процесс запущен
вручную вне systemd (см. предупреждение в начале документа).
