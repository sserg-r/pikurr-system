## Задача 2. Что делает `recreate_views()` на каждой доставке

**Сделано на тестовом стенде** (`pikurr_srv_*`, `192.168.251.190`,
`log_statement='all'` включён на время экспериментов через `ALTER SYSTEM`
+ `pg_reload_conf()`, затем работа шла без модификации кода — только
наблюдение). Стенд предварительно смигрирован на текущую схему (первая
доставка round23-пакета), дальше — **повторные** доставки того же пакета,
как и просит задача.

### 2.1-2.2. Фактический SQL — и находка, меняющая картину

**По факту (лог PostgreSQL, не код)**: на каждой повторной доставке
происходит:

```
DROP TABLE "public"."agrifields" CASCADE     -- делает ogr2ogr -overwrite, НЕ recreate_views()
... (пересоздание agrifields, COPY данных)
DROP TABLE "public"."razgrafka" CASCADE
DROP TABLE "public"."assessment" CASCADE
...
DO $$ ... DROP VIEW assessment_ready CASCADE ... $$    -- текст DO-блока залогирован целиком,
                                                         -- ветка DROP VIEW не должна исполняться,
                                                         -- т.к. assessment_ready уже materialized —
                                                         -- но это не имеет значения, см. ниже
CREATE MATERIALIZED VIEW IF NOT EXISTS assessment_ready AS ...
CREATE UNIQUE INDEX IF NOT EXISTS idx_assessment_ready_nr_user_year ...
CREATE INDEX IF NOT EXISTS idx_assessment_ready_year ...
CREATE INDEX IF NOT EXISTS idx_assessment_ready_district ...
CREATE INDEX IF NOT EXISTS idx_assessment_ready_geom ...
DROP MATERIALIZED VIEW IF EXISTS assessment_ready_latest
CREATE OR REPLACE VIEW assessment_ready_latest AS ...
REFRESH MATERIALIZED VIEW assessment_ready;
```

**Обнаружено и подтверждено прямым замером OID** (`select oid from
pg_class where relname='assessment_ready'` до и после доставки): OID
меняется на каждой доставке (325324 → 356229 в одном из прогонов) —
**`assessment_ready` реально уничтожается и создаётся заново на КАЖДОЙ
доставке, не только при первой миграции**.

**Механизм**: `ogr2ogr -overwrite` при импорте `agrifields` выполняет не
"перезаписать данные", а буквально `DROP TABLE agrifields CASCADE`
(видно в логе как `execute <unnamed>: DROP TABLE "public"."agrifields"
CASCADE`) — а `assessment_ready` зависит от `agrifields` (через `JOIN`).
CASCADE в PostgreSQL распространяется на материализованные представления
так же, как на обычные — CASCADE **безусловно** уничтожает
`assessment_ready` раньше, чем до него доходит очередь у
`recreate_views()`. То, что в SQL-скрипте написано `DROP VIEW ... CASCADE`
внутри `DO $$ IF EXISTS (SELECT ... FROM pg_views) $$` — не имеет
значения: объекта уже нет к моменту, когда этот код исполняется, будь в
нём условие или нет.

**Ответ по пунктам ТЗ**:
- удаляется ли `assessment_ready` при каждой доставке, не только при
  миграции — **да**, подтверждено фактом (OID меняется каждый раз);
- создаётся ли материализованное представление с данными или `WITH NO
  DATA` — **с данными** (нет `WITH NO DATA` в определении) — то есть
  `CREATE MATERIALIZED VIEW` сам по себе выполняет полную сборку данных
  (не быстрый скелет), и следом `REFRESH` пересобирает ЕЩЁ РАЗ — **представление
  собирается дважды на каждой доставке**, не только при миграции, как
  предполагалось в round23;
  - время `CREATE MATERIALIZED VIEW ... AS` (включая 4 индекса) — от
    начала `DO`-блока (50.766) до конца последнего индекса (52.574) —
    **~1.8с** в одном из прогонов;
  - время `REFRESH MATERIALIZED VIEW` отдельно — **1.75-2.34с** (3 замера
    на этом стенде: 2.18с, 2.34с, 1.75с);
  - итого ~2 сборки на доставку, а не одна — реальная стоимость
    `recreate_views()`+`refresh_materialized_view()` вместе — около
    4 секунд, не 2, как считалось в round23 (там измерялся только сам
    `REFRESH`, без учёта того, что `CREATE` перед ним — не no-op).
- удаляется ли каскадом `assessment_ready_latest` — **да**, подтверждено
  (`DROP VIEW assessment_ready CASCADE` в логе; отдельно скрипт ещё раз
  явно делает `DROP MATERIALIZED VIEW IF EXISTS assessment_ready_latest`
  перед `CREATE OR REPLACE VIEW` — избыточно, но не вредно).

Непрерывный опрос (первый заход — раз в 0.5с, 51 запрос за всю доставку,

первой). Пользователь, открывший карту или кликнувший по полю именно в
этот момент, получит пустой/битый ответ, который любой мониторинг по
коду ответа не заметит.

**Вывод по задаче 2**: подтверждено полностью, с находкой более серьёзной,
чем предполагало ТЗ — окно недоступности существует **на каждой
доставке**, не только при первой миграции, и оно **невидимо для
мониторинга по коду ответа** (round22-23 не могли бы его найти тем

проверено):

SELECT count(*) FROM assessment_ready WHERE district IS NULL; -- → 0

**Подтверждено**: эквивалентность `LEFT(nr_user,4)` ↔ `substring(0,4)`
выполняется без исключений на всех 55784 строках (единая длина 14, нет

| WMS `GetMap` | работает, отдаёт реальный PNG с классификацией |
| WFS `GetFeature` | работает, отдаёт реальные атрибуты и геометрию (обычный VIEW пересчитывается на каждый запрос — работает, просто без выигрыша от материализации) |

**Важный факт**: несмотря на падение, WMS и WFS **продолжают отдавать
корректные, свежие данные** — потому что `assessment_ready` откатился на
ОБЫЧНЫЙ VIEW (который просто пересчитывается при каждом обращении), а не
исчез совсем. Деградация — не в доступности, а в **производительности**
(снова оплачивается полный пересчёт на каждый запрос — после фиксов round22
это ~2.3с, не 14мс) и в **синхронизации `year_district.json`/индекса
мозаики**, которая в этом конкретном случае осталась незамеченной только
потому, что содержимое данных не изменилось между старым и новым пакетом.
Если бы данные ДЕЙСТВИТЕЛЬНО отличались (новый год, новые районы,
изменённые растры) — витрина продолжала бы показывать старую версию
`year_district.json` и старую мозаику неопределённо долго, до следующей
УСПЕШНОЙ доставки.

**Последний шаг, после которого рассогласование остаётся при падении**:
любое падение на шаге `refresh_materialized_view` **или позже**
(`write_year_district_lookup`, `reload_geoserver`) оставляет
`year_district.json` и/или индекс мозаики устаревшими — сами данные в
PostGIS (agrifields/assessment/assessment_ready) при этом уже свежие,
рассинхронизация только в производных артефактах. Падение **раньше**
(`import_vectors` или `copy_rasters`) оставило бы саму БД/растры в
непоследовательном виде (частично импортированные векторы либо частично
скопированные растры) — не проверялось отдельно в этой задаче (см. задачу
5, где именно это и тестируется через `kill -9` на разных шагах).

**Сценарий законного отката на предыдущий пакет — не существует.**
`deliver.py` не делает транзакционный откат через шаги: SQL-операции
коммитятся по мере выполнения, файлы копируются немедленно. Единственный
механизм восстановления — **следующая корректная доставка**, полагающаяся
на идемпотентность (`-overwrite`, `CREATE ... IF NOT EXISTS`,
`CREATE OR REPLACE`).

**Проверено фактом — следующая корректная доставка полностью
самовосстанавливает систему**: доставлен тот же (новый, round23-схема)
пакет повторно — `relkind` `assessment_ready` вернулся к `m`
(материализованное), `REFRESH` прошёл (1.79с), `year_district.json`
переписан, мозаика переиндексирована. Без единого ручного вмешательства.

## Задача 5. Прерывание доставки (`kill -9` на каждом шаге)

**Сделано на тестовом стенде.** Скрипт запускал `deliver.py` в фоне,
дожидался появления маркерной строки в логе (без опроса через ssh —
цикл ожидания работал локально на самом стенде, чтобы не терять окно из-за
сетевой задержки — доставка на этом стенде занимает всего ~15-20с
целиком), затем `kill -9` самого процесса и всех его детей
(`pkill -9 -P`).

| шаг прерывания | восстановилось само (следующей доставкой) | что осталось |
|---|---|---|
| копирование растров (сразу после чтения манифеста, до начала копирования) | да | растры/БД не тронуты (старые, от прошлой доставки); **статус-файл не написан вовсе** |
| импорт векторов (сразу после копирования растров) | да | растры новые, БД (assessment/agrifields) старая — `assessment_ready` не тронут (`relkind=m`, не упал) |
| `recreate_views` (между `ogr2ogr -overwrite` и завершением `CREATE MATERIALIZED VIEW`) | да, но **до восстановления сайт сломан** | `assessment_ready` **не существует вовсе** — WFS/карта по векторному слою отдают `HTTP 200` + `ServiceExceptionReport` (не 1.7с, как в задаче 2, а **до следующей доставки**, потенциально долго) |
| `REFRESH` (сразу после старта, могла не успеть выполниться) | да | безвредно в этом прогоне — `CREATE MATERIALIZED VIEW` уже успел заполнить данные полностью (та же находка, что в задаче 2 — `REFRESH` во многом избыточен) |
| запись `year_district.json` (сразу после завершения `REFRESH`) | да | БД полностью свежая, `year_district.json` — **устаревший** (не переписан) |
| `reload_geoserver` (сразу после записи JSON) | да | в этом конкретном прогоне мозаика оказалась исправной — харвест на стороне GeoServer, судя по всему, уже был запущен и продолжился независимо от клиента (`202 Accepted` — асинхронная операция); **более раннее** прерывание внутри этого же шага (до отправки harvest-запроса, сразу после удаления файлов индекса) осталось непроверенным отдельно — велик риск, что это могло бы оставить мозаику без индекса вовсе |

**Статус-файл при `kill -9` — не пишется никогда** (не только на шаге
"растры" — это общее свойство: `SIGKILL` не даёт сработать `finally:` в
`main()`). `PushTask`, ожидающий подтверждения, в этом случае просто не
увидит файл статуса и в конце концов получит **обычный таймаут**, без
какой-либо информации о причине — неотличимо от "сеть недоступна" или
"сервер не отвечает".

**Проверка через реальный `watchdog` (не прямой вызов `deliver.py`)**:
пакет положен в `inbox/`, `pikurr-watchdog.service` (поднят автоматически
через `Restart=always`, round21, после более раннего `kill -9` в рамках
этого же раунда) подхватил его на следующем опросе (10с) и доставил
успешно без вмешательства — `journalctl`/`watchdog.log`:
`Processing: pikurr_update_wdtest_...` → `Delivery SUCCESS`. Подтверждает:
после рестарта ВМ (`Restart=always` подтверждён живым инцидентом в этом же
раунде — я случайно убил демон `kill -9`, и он поднялся сам) файл,
оставшийся в `inbox/`, действительно передоставляется автоматически, как и
предполагает механизм `seen` (round21, A1) при сбросе состояния процесса.

**Итог по задаче 5**: почти все прерывания безопасны в том смысле, что
следующая доставка чинит всё сама — но **окно "recreate_views"
качественно отличается**: если ВМ остановится именно в этот момент,
витрина остаётся **видимо сломанной** (не просто медленной) до следующей
успешной доставки, которая может случиться нескоро при текущей частоте
поставок ("несколько раз в год").

## Задача 6. Заглушка на действительно чистом инстансе

Путь «заглушка → первый старт GeoServer → первая доставка» не проверялся в
раунде 23 (там проверялась миграция уже живого, ранее наполненного VIEW).
Полностью чистые тома PostGIS/GeoServer на стенде поднять без потери
текущего состояния стенда было бы разрушительно — вместо этого создана
**отдельная** БД (`pikurr_r24_clean`) и **отдельные** workspace/datastore/
featuretype в том же GeoServer (`r24test`/`r24_clean`/`assessment_ready`),
изолированные от боевых объектов стенда. Это даёт тот же самый путь
«заглушка → создание слоя в GeoServer → первая доставка», только без
полного передёргивания томов.

### 6.1. Типы колонок заглушки vs реального представления

$ psql -h 192.168.251.190 -U pikurr -d pikurr_r24_clean -c '\d+ assessment_ready'

**Расхождения**:

| колонка | заглушка | реальное представление | совпадает? |
|---|---|---|---|
| `district` | `text` | `character varying(4)` | нет (несущественно — приводимые типы) |
| `geom` | `geometry` (без типа/SRID) | `geometry(MultiPolygon,4326)` | **нет** |
| `stats` | `jsonb` | `character varying` | **нет** |

| `valuation` | отсутствует в заглушке | `character varying` | **отсутствует колонка** |

Заглушка (`bootstrap_empty_schema.sql`) — это упрощённый, не
синхронизированный 1:1 набор колонок, а не точная копия реальной схемы.
Практического вреда от этого в проверенном сценарии не обнаружено (см.
6.3 — после реальной доставки `create_assessment_schema.sql` пересоздаёт
представление целиком со своим собственным полным набором колонок,
несовпадение заглушки не переносится дальше момента миграции), но сам
факт расхождения — не проверенное ранее наблюдение.

### 6.2. Состояние GeoServer до первой доставки

После создания workspace/datastore/featuretype поверх пустой заглушки
(featuretype создан REST POST, БД пуста — заглушка отдаёт 0 строк):

```
$ curl -s -u admin:*** \
  http://192.168.251.190:8080/geoserver/rest/workspaces/r24test/datastores/r24_clean/featuretypes/assessment_ready.json
{
  "featureType": {
    "name": "assessment_ready",
    "nativeCRS": "GEOGCS[\"Unknown\", ...]"  // не указан явно, GeoServer подставил заглушку
    "srs": "EPSG:404000",
    "nativeBoundingBox": {"minx":0,"maxx":-1,"miny":0,"maxy":-1,"crs":"EPSG:404000"},

`EPSG:404000` — служебный placeholder-код GeoServer для «CRS не удалось

В `pikurr_r24_clean` добавлены минимальные синтетические строки в
`agrifields`/`razgrafka`/`assessment` (с реальной геометрией в EPSG:4326),

`PIKURR/src/sqlscripts/create_assessment_schema.sql` — тот же файл, что
использует боевой `deliver.py`. Выполнение завершилось успешно, материа-
лизованное представление собралось с 1 строкой (`SELECT count(*) → 1`).

**Не изменилось ни на одно поле** по сравнению с 6.2 — тот же

(а не молча предполагает 4326), получит неверную систему координат для
геометрически верных данных.

**Причина (подтверждено по коду)**: `deliver.py:reload_geoserver()` (см.
`REPIKURR/deliver.py:654`) обрабатывает **только** растровые
ImageMosaic-сторы — `_rebuild_mosaic_index()` и `_reload_one_store()`
(строки 497, 585). В файле нет ни одного обращения к REST API
featuretype/векторного слоя вообще (проверено `grep` — нет
`nativeBoundingBox`, `featuretype`, `recalculate` ни в одном месте файла).

**не выполняется никогда** — ни при обычной доставке, ни тем более при
первой.

**Почему это не проявилось на `geobotany.of.by`**: проверено отдельным
запросом к продакшену —

```
$ curl -s -u admin:*** https://geobotany.of.by/geoserver/rest/workspaces/pikurr/datastores/postgis_pikurr/featuretypes/fields.json
srs: EPSG:4326
nativeBoundingBox: {'minx': 26.44..., 'maxx': 30.91..., 'miny': 54.83..., 'maxy': 56.11..., 'crs': 'EPSG:4326'}
```

На проде bbox/CRS правильные — но **не потому, что доставка их
пересчитывает**, а потому, что слой `pikurr:fields` на VPS никогда не
создавался REST-путём с нуля на пустых данных: `geoserver_data/`
переносился (round22) с уже рабочей конфигурации, где featuretype был
однажды настроен вручную/через штатный редактор поверх уже наполненной
БД, и с тех пор просто не пересоздавался. Сценарий «пустая заглушка →
первый REST-конфиг слоя → первая реальная доставка», описанный в задаче
6 этого раунда, ранее **не проходил** ни на одном реальном инстансе —
только на новом чистом тесте только что.

**Вывод по вопросу задачи 6.3** («Совпадают ли атрибуты и bbox слоя с
реальными данными без ручной перенастройки слоя?»):
- по атрибутам и геометрии в теле ответа — **подтверждено**, совпадают;
- по `nativeBoundingBox`/`srs` в REST-метаданных слоя и по полю `crs` в
  самом WFS-ответе — **опровергнуто**: остаются от момента создания слоя
  поверх пустой заглушки и не обновляются автоматически ни при миграции
  схемы, ни при последующих доставках. Нужен явный REST-вызов
  пересчёта (`PUT .../featuretypes/<name>.json?recalculate=nativebbox,latlonbbox`
  либо аналогичная операция) — сейчас такого вызова нигде в пайплайне
  нет.

Очистка временных объектов: `DROP DATABASE pikurr_r24_clean;` и удаление
workspace `r24test` (каскадом удаляет datastore/featuretype) выполнены
на стенде после завершения задачи.

## Задача 7. Геодезическая площадь — только замер

Машина замера — тестовый стенд `192.168.251.190` (12 vCPU, 62 ГБ RAM,

### 7.1. Время создания: геодезический вариант vs текущий `REFRESH`

Создано отдельное временное представление `assessment_ready_geo_test` —
точная копия определения `assessment_ready` из
`create_assessment_schema.sql`, с единственным отличием: `area_ha`
считается как `ROUND((ST_Area(a.geom::geography) / 10000)::numeric, 2)`
вместо `ROUND((a.shape_area / 10000)::numeric, 2)`.

```
$ CREATE MATERIALIZED VIEW assessment_ready_geo_test AS ...   (3 прогона, DROP между ними)
Time: 3954.904 ms
Time: 3954.093 ms
Time: 3939.520 ms

$ REFRESH MATERIALIZED VIEW assessment_ready;                 (3 прогона, та же машина)
Time: 1868.462 ms
Time: 1889.693 ms
Time: 1936.807 ms
```

**Подтверждено**: геодезический расчёт (`ST_Area(geom::geography)`)
стабильно ~**2.05×** дороже, чем текущий способ (`shape_area` из
исходного файла) — ~3.94-3.95с против ~1.87-1.94с на одинаковом наборе
из 55784 строк, на одной машине, с минимальным разбросом между
прогонами (обе серии — под 1.5% дисперсии).

### 7.2. Расхождение shape_area vs геодезический расчёт

Для `nr_user=22490000030364` (строка, которая в раунде 23 отмечена как
«явно бракованная», ~100% отклонение при прежнем способе расчёта):

```
    nr_user     | shape_area_ha | geodesic_ha | diff_ha | diff_pct
22490000030364 |          1.21 |        0.63 |   -0.58 |   -47.93
```

Свежий замер даёт **-47.93%**, не ~100% из round23 — цифры не совпадают
буквально (что и предписано ТЗ: не подстраивать под round23), но
направление то же — эта строка остаётся выраженной аномалией на фоне
всей выборки.

По всей выборке (55784 строк, `r.area_ha > 0`):

```
   n   | avg_abs_rel_pct | avg_signed_rel_pct | max_abs_rel_pct | total_shape_ha | total_geodesic_ha
 55784 |          0.0236 |            -0.0236 |           47.93 |      363322.58 |         363222.84
```

Средняя относительная погрешность метода `shape_area` — **0.0236%**
(систематически чуть больше геодезического — знак `avg_signed_rel_pct`
отрицательный, т.е. геодезический расчёт в среднем даёт немного меньшую
площадь). Суммарно по всей выборке разница — **99.74 га** на 363 тыс. га
(0.027% от общей площади). Максимальное отклонение — 47.93% (та самая
строка `22490000030364`). Величины близки к данным round23
(«0.026% средняя, ~0.086% систематическая»), но не идентичны — ожидаемо,
поскольку это самостоятельный, а не повторный замер.

### 7.3. Очистка

```

Это ровно тот сценарий: 12.52с — замер из сквозного прогона round23,

исчерпания CPU-кредита от предыдущей I/O-интенсивной операции», а не с
альтернативами «холодный кэш страниц» (кэш страниц, наоборот, должен

причина разброса — долевой (burstable) vCPU прерываемой ВМ, теряющий
производительность сразу после интенсивной I/O-операции (копирование
растров), а не кэш или случайный шум. Прямого повторного эксперимента
«убить CPU-кредит и замерить REFRESH сразу после» на самой VPS в этом
раунде не проводилось (ТЗ запрещает разрушающие эксперименты на
`geobotany.of.by` — это задача 2/4/5/6, выполненная на тестовом стенде;
задача 7 такого эксперимента не предписывает) — вывод основан на
сопоставлении зафиксированных ранее фактов о конфигурации ВМ и порядка
операций в самом сквозном прогоне round23, а не на новом измерении
именно этого эффекта, поэтому это не то же самое, что «подтверждено

### 8.3. Формулировка для README: как остановить ВМ для обслуживания

**Задача явно требует только сформулировать текст, не вносить его в
README** — ниже предлагаемый текст шага (не применён к файлу):

> **Обслуживание: как остановить ВМ так, чтобы функция автозапуска её
> не поднимала обратно.**
> Функция реагирует на таймерный триггер каждые 2 минуты и запускает ВМ,
> если её текущий статус не `RUNNING`. Простой `yc compute instance
> stop <id>` не помогает — на следующем срабатывании триггера функция
> снова увидит статус, отличный от `RUNNING`, и вызовет `start`.
> Перед плановой остановкой ВМ на обслуживание нужно сначала
> приостановить сам триггер:
> ```
> yc serverless trigger pause <TRIGGER-NAME>|<TRIGGER-ID>
> yc compute instance stop <INSTANCE-NAME>|<INSTANCE-ID>
> ```
> После завершения обслуживания — обратный порядок:
> ```
> yc compute instance start <INSTANCE-NAME>|<INSTANCE-ID>
> yc serverless trigger resume <TRIGGER-NAME>|<TRIGGER-ID>
> ```
> Если триггер не приостановить, максимальное окно, в течение которого
> ВМ гарантированно остаётся выключенной, — не больше интервала
> триггера (2 минуты) минус время между остановкой ВМ и следующим
> срабатыванием.

### 8.4. Формулировка поведения функции для нештатных статусов ВМ

**Также только формулировка, не реализация** — код функции
(`cloud-function-autostart/`) сейчас не проверялся на обработку этих
двух случаев отдельно от «не RUNNING → start»; предлагаемое поведение:

> **Статус `STOPPING`.** Функция не должна вызывать `start` для
> инстанса в статусе `STOPPING` — это переходный статус (инстанс либо
> остановлен пользователем/обслуживанием, либо самой облачной
> инфраструктурой, и процесс остановки уже запущен). Попытка запустить
> ВМ, которая ещё останавливается, либо будет отклонена API с ошибкой,
> либо (хуже) создаст состояние гонки. Функция должна: увидеть
> `STOPPING`, залогировать это как штатное промежуточное состояние и
> ничего не делать до следующего срабатывания триггера (через 2
> минуты) — на следующем вызове статус уже будет `STOPPED`, и обычная
> логика `start` сработает корректно.
>
> **Ошибка запуска из-за нехватки ресурсов для прерываемой ВМ.**
> Прерываемая (preemptible) ВМ может не подняться, если в момент
> запроса `start` в пуле недостаточно ресурсов нужной конфигурации —
> Yandex Cloud вернёт ошибку по этому конкретному вызову API, не
> исключение уровня функции. Функция должна: залогировать код/текст
> ошибки API (не проглатывать её), не делать бесконечных ретраев внутри
> одного вызова функции (сам следующий запуск триггера через 2 минуты
> и есть естественный ретрай), и не переводить это в статус,
> неотличимый от «ВМ запущена нормально» — иначе следующий цикл проверки
> ошибочно решит, что всё в порядке. Если такие сбои начнут повторяться
> подряд несколько раз — это сигнал для отдельного алерта (не
> реализуется в этом раунде, только формулировка), а не для тихого
> молчания функции.

2. **`ogr2ogr -overwrite` каскадно удаляет и заново создаёт
   `assessment_ready` на КАЖДОЙ доставке**, не только при первой миграции
   (задача 2). Механизм: `ogr2ogr -overwrite` выполняет `DROP TABLE
   "agrifields" CASCADE`, что каскадно роняет зависящее материализованное
   представление; `CREATE MATERIALIZED VIEW IF NOT EXISTS` в
   `recreate_views()` после этого — не no-op, а полноценная пересборка
   каждый раз (подтверждено сравнением OID до/после и `log_statement=all`).

3. **WFS/WMS отдают HTTP 200 с телом-исключением GeoServer в течение
   окна недоступности `assessment_ready` на каждой доставке** (задача 2).
   Механизм: OGC-протокол WFS 1.0.0/WMS `GetMap` возвращает
   `ServiceExceptionReport`/`se_xml` с кодом 200 — мониторинг по коду
   ответа не увидит эту ~1.7-1.8с недоступность ни разу.

4. **Прерывание доставки именно во время `recreate_views()` (`kill -9`
   после `DROP ... CASCADE`, до завершения `CREATE MATERIALIZED VIEW`)
   оставляет витрину видимо сломанной до следующей УСПЕШНОЙ доставки**,
   не до следующего перезапуска процесса (задача 5). Механизм: DROP и
   CREATE — разные statement'ы в одном `psql -f`; если процесс убит между
   ними, объект просто не существует, и это не самовосстанавливается
   через watchdog/systemd — нужна ещё одна полная доставка.

5. **При `kill -9` статус-файл не пишется вообще** — `write_status()`
   вызывается только в `finally:` `main()`, а `SIGKILL` не даёт `finally`
   исполниться (задача 5). Механизм: `PushTask` в этом случае получает
   только общий таймаут без диагностической информации о том, на каком
   шаге и почему упала доставка.

6. **REST-метаданные векторного featureType (`nativeBoundingBox`, `srs`)
   не обновляются автоматически после первой доставки на чистый инстанс**
   — остаются от момента создания слоя над пустой заглушкой (`EPSG:404000`,
   вырожденный bbox) (задача 6). Механизм: `deliver.py:reload_geoserver()`
   обрабатывает только растровые ImageMosaic-сторы
   (`_rebuild_mosaic_index`/`_reload_one_store`); в файле нет ни одного
   REST-вызова, относящегося к векторным featuretype. На `geobotany.of.by`
   это не проявилось только потому, что `geoserver_data/` был перенесён с
   уже рабочей конфигурации (round22), а не создан REST-путём с нуля —
   то есть настоящий путь «заглушка → первая доставка» на бою никогда не
   проходил.

7. **`pikurr-watchdog.service` в рабочем каталоге тестового стенда
   (`~/repikurr/pikurr-watchdog.service`) — устаревшая копия
   (`Restart=on-failure`, апрель 2026), не совпадающая с реально
   установленным юнитом (`Restart=always`, актуальный round21-фикс)**
   (задача 9.5). Механизм: юнит был обновлён напрямую в
   `/etc/systemd/system/`, копия рядом с проектом не синхронизирована;
   переустановка юнита из этой копии откатит round21 A4.

8. **Заглушка (`bootstrap_empty_schema.sql`) не синхронизирована по
   типам колонок с реальным представлением** — `stats: jsonb` вместо
   `character varying`, отсутствуют `area_ha`/`valuation`, `geom` без
   объявленного типа/SRID (задача 6.1). Механизм: заглушка писалась
   отдельно от `create_assessment_schema.sql` и не следит за его
   изменениями; на проверенном сценарии миграции вреда не нанесла (схема
   пересоздаётся целиком при реальной доставке), но именно расхождение
   типа `geom` — прямая причина дефекта №6 выше.

9. **Легитимного сценария отката на предыдущий пакет при падении
   доставки не существует** (задача 4). Механизм: `deliver.py` не хранит
   предыдущую версию растров/векторов/схемы — восстановление возможно
   только через повторную, корректную доставку вперёд, не назад.

10. **`year_district.json` снятие с учёта `users.xml` подготовлено, но
    не закоммичено** (задача 9.2) — незначительный хвост, но фиксирует
    незавершённое действие в рабочем дереве.

11. **`vite.config.js` — dev-прокси указывает на `geobotany.xyz`**, не
    на актуальный `geobotany.of.by` (побочная находка задачи 5/3). Не
    влияет на боевую сборку, но артефакт до-VPS-переезда.

## Предлагаемые исправления (без реализации в этом раунде)

- Переписать историю `origin/main` (`git filter-repo`/BFG) для удаления
  `deliver.env` из всех коммитов, где он присутствовал в открытом виде;
  после этого — принудительная синхронизация всех клонов репозитория;
  независимо от переписывания истории — считать пароли из утечки
  скомпрометированными постоянно (сама ротация уже сделана, но стоит
  сверить, что она затронула ВСЕ секреты из утёкшего файла, не только
  `GEOSERVER_PASSWORD`/`FRONTEND_DB_PASSWORD`).
- В `deliver.py:recreate_views()` — рассмотреть перенос `REFRESH` в ту же
  транзакцию/скрипт, что и `CREATE MATERIALIZED VIEW`, либо иной способ
  сделать окно недоступности атомарным относительно кильнутого процесса
  (например, создание нового представления под временным именем и
  атомарный `ALTER ... RENAME` в конце — тогда обрыв между DROP и CREATE
  не оставляет систему без представления вовсе).
- Добавить мониторинг WFS/WMS **по содержимому ответа** (парсинг
  `ServiceExceptionReport`), а не только по HTTP-коду — иначе окна
  недоступности из задачи 2 и разбитое состояние из задачи 5 остаются
  невидимыми для существующих проверок.
- Записывать частичный статус-файл на каждом шаге (не только в
  `finally`), либо использовать `signal.signal(SIGTERM, ...)` и
  документировать, что `SIGKILL` — единственный сигнал, который
  гарантированно этого не даст (и явно предупредить об этом в
  документации по прерываемым ВМ).
- Добавить в `deliver.py:reload_geoserver()` REST-вызов пересчёта
  bbox/CRS для векторных featuretype (`?recalculate=nativebbox,latlonbbox`
  или аналог) — особенно важно для по-настоящему первой доставки на
  чистый инстанс, а не только для миграции уже наполненного VIEW.
- Синхронизировать типы колонок `bootstrap_empty_schema.sql` с
  актуальным `create_assessment_schema.sql` (особенно `geom` — объявить
  тип/SRID явно, чтобы GeoServer не подставлял `EPSG:404000` уже на
  этапе заглушки).
- Обновить/удалить устаревшую копию `pikurr-watchdog.service` в
  `~/repikurr/` на тестовом стенде, привести в соответствие с реально
  установленным юнитом, и стандартизировать процедуру деплоя юнита
  (единый источник правды — либо репозиторий, либо `/etc/systemd/system/`,
  не оба независимо).
- Сформулировать (задача 4) и реализовать отдельным раундом сценарий
  легитимного отката на предыдущий пакет — либо хранением предыдущей
  версии данных, либо явной процедурой повторной доставки известного
  хорошего архива.
- Закоммитить уже подготовленное снятие `users.xml` с учёта.
- Проверить и, при необходимости, обновить `vite.config.js` (домен
  dev-прокси).
