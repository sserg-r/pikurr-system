# Раунд 37: подсветка выбранной группы, цена прогрева

Запрос пользователя: при выборе области/района/землепользователя поля
выбранной группы должны быть видны отчётливо, остальные — приглушены
(не скрыты). Решение пользователя: приглушение на клиенте, не скрытие,
не второй стиль на сервере.

Отчёт по формату задания: задача → доказательства → вердикт. Блоки A,
B, D1 — закоммичены, задеплоены на прод (VPS) и подтверждены фактом
там же. Блок C — не начат (см. "Что не сделано" в конце).

---

## Блок A. Подсветка выбранной группы

### A1. Устройство — проверено фактом

Три предпосылки схемы, все подтверждены на VPS (`geobotany.of.by`)
перед написанием кода:

1. **`CQL_FILTER` через `/geoserver/gwc/service/wms` — игнорируется.**
   Три запроса на один и тот же тайл `pikurr:fields_latest` (без
   фильтра / с `CQL_FILTER=nr_user LIKE '2208%'` / с
   `STYLES=line`) дали **байт-в-байт идентичный ответ**
   (md5 `e06f36da08f3314f769f72c794cf90d9` во всех трёх) и
   `geowebcache-cache-result: HIT` во всех трёх. GWC не отказывает и не
   ошибается — молча отдаёт нефильтрованный кэшированный тайл. Это же
   объясняет исходную жалобу пользователя: до этого раунда код уже
   передавал `CQL_FILTER` в GWC-запрос для `fields_latest`, и фильтр
   тихо ничего не делал.
2. **`STYLES`, отличный от дефолтного, через GWC — тоже игнорируется**
   (тот же эксперимент, см. выше).
3. **Изменение `opacity` слоя на клиенте не меняет URL тайла.**
   Проверено по исходнику Leaflet (`leaflet-src.js`): `GridLayer.
   setOpacity()` вызывает `setOpacity(el, opacity)` →
   `el.style.opacity` — чисто CSS-свойство DOM-элемента, отдельная
   кодовая ветка от `getTileUrl`/построения WMS-параметров. Подтверждено
   косвенно и рабочим прогоном (`smoke.mjs`, шаги 3.1–3.3): во всех
   трёх уровнях выбора GWC-запросы фонового слоя идут БЕЗ
   `CQL_FILTER` (0 из N), т.е. приглушение не просачивается в URL фона.

**Вердикт**: все три пункта подтверждены, ни один не опровергнут —
работа по предложенной схеме продолжена без пересмотра.

### A2. Реализация

Изменённые файлы: `constants.js`, `services/geoserver.js`, `App.jsx`,
`Sidebar.jsx`, `MapView.jsx`.

1. **Три уровня выбора.** Область — новый уровень (раньше существовал
   только как локальный UI-фильтр списка районов в `Sidebar.jsx`, но НЕ
   передавался в фильтр карты — реальный, отдельный от задачи A2 баг,
   исправлен попутно: `handleSelectOblast` в `App.jsx`, состояние
   области поднято из `Sidebar` наверх, чтобы не расходиться с
   `App.selectedOblast`). Код фильтра для всех трёх уровней —
   `nr_user LIKE '<код>%'`: 2 цифры для области (`22`), 4 для района
   (`2208`), полный код для землепользователя. Логика переиспользована
   из уже существующей (популяр карточки), не продублирована — единая
   сборка в `App.jsx` (`groupCqlExpr`), используется и верхним слоем, и
   `FeatureInfo`.
2. **Непрозрачность фона** — именованная константа `DIMMED_OPACITY =
   0.25` (`constants.js`). Скриншот с текущим значением — см. ниже,
   пользователь может попросить другое.
3. **Порядок отрисовки** — два независимых `WMSTileLayer` (не один слой
   с двумя стилями): фон `zIndex=500` (без изменений, кроме
   `opacity`), подсветка `zIndex=600`, рендерится, только когда группа
   активна. Подтверждено визуально (скриншот ниже) — выбранная группа
   рисуется в полную силу поверх приглушённой копии себя же в фоне, не
   смешивается.
4. **Клик и попап** — без изменений в логике, фильтруются тем же
   `highlightCqlExpr` (год+группа), что и верхний слой (было —
   `cqlExpr`, переименовано по месту).
5. **Приближение к границам группы** (WPS bbox) — работает для всех
   трёх уровней (для области раньше не работало вовсе, т.к. `Sidebar`
   не сообщал о выборе области наружу — тоже часть попутного
   исправления в п.1).
6. **Пустая группа** — WFS `resultType=hits` (`getFeatureCount`,
   `services/geoserver.js`) при смене группы; при `0` — жёлтый баннер
   над картой ("В выбранной группе нет полей..."), не пустая карта без
   объяснений.

**Побочная находка (не входила в ТЗ, но блокировала приёмку A2):**
параметр WMS `time` подставлялся буквально как строка `'loading'` до
ответа `/static/year_district.json` — GeoServer трактует `time` как
WMS-размерность TIME, `'loading'` не парсится как дата →
`ServiceExceptionReport` с HTTP 200 (та самая ловушка "200 ≠ успех" из
CLAUDE.md). До этого раунда это уже било по историчному слою `fields`
(видно при выбранном годе, узкое окно), round37 расширил число
потребителей (добавился верхний слой) и сделал проявление предсказуемым
при разработке. Исправлено — `time` не передаётся вовсе, пока версия
данных не известна (`MapView.jsx`, `cacheBuster`). Зафиксировано в
CLAUDE.md ("Ловушки").

**Визуальное подтверждение** (Playwright, дев-сервер с проксированием
на прод-GeoServer, только GET-запросы — прод не изменялся):
выбран Браславский район, вид отдалён так, чтобы в кадре были и его
поля, и соседние: выбранная группа — насыщенный красный (полная
непрозрачность), поля вне группы — бледно-розовые (приглушены,
видны, не скрыты). Скриншоты приложены к сессии.

**Вердикт**: A2 подтверждено по всем 6 пунктам — визуально и через
сетевые проверки `smoke.mjs`.

### A3. Замеры (VPS, `geobotany.of.by`)

Инструменты: `REPIKURR/tools/round37_a3_measure.sh` (одиночные тайлы,
3 условия × 3 тайла × 3 повтора = 45 запросов, порядок перемешан одним
`shuf` по всем тройкам сразу, не блоками) и
`REPIKURR/tools/round37_a3_screen.sh` (экран из 12 тайлов, параллелизм
6). Тайлы — из `docs/round32_assets/tiles_with_data.json` (первые 3/12,
Браславский район — единственная область с данными на этой витрине:
`nr_user LIKE '22%'` = 55784 объектов = весь датасет, проверено WFS
`resultType=hits`).

**Одиночный тайл, HTTP `time_total`, секунды (n=9 на условие):**

| условие | avg | median | min | max | доля <2КБ |
|---|---|---|---|---|---|
| `gwc_hit` (фон, кэш, HIT, без фильтра) | 0.644 | 0.661 | 0.578 | 0.697 | 0/9 |
| `direct_nofilter` (тот же слой, мимо GWC, без фильтра) | 0.674 | 0.682 | 0.547 | 0.750 | 0/9 |
| `oblast` (`nr_user LIKE '22%'`, 55784 объектов) | 0.668 | 0.664 | 0.578 | 0.736 | 0/9 |
| `district` (`nr_user LIKE '2208%'`, 15936 объектов) | 0.738 | 0.779 | 0.598 | 0.866 | 0/9 |
| `landuser` (`nr_user LIKE '22080000010%'`, 17 объектов) | 0.591 | 0.556 | 0.456 | 0.882 | **9/9** |

Правило непустых тайлов: `landuser` — все 9 ответов по 1784 байта,
ниже порога 2 КБ. Это НЕ пустые тайлы (PNG валиден, содержит реальные
контуры малой группы — 17 объектов на 3 разных тайлах физически не
могут заполнить 256×256 px плотнее) — правило сформулировано для
случая "пустой тайл = нет данных вообще", здесь малый размер —
ожидаемое следствие малой группы, не сигнал поломки. Явно указано,
раз порог формально превышен.

**Наблюдение, опровергающее часть гипотезы задания**: предположение
"фильтр по малой группе дешевле полного слоя" подтвердилось для
`landuser` (0.591с — быстрее и фона, и полного нефильтрованного
рендера), но **не подтвердилось для `district`** — 0.738с, МЕДЛЕННЕЕ,
чем `direct_nofilter` (0.674с) и `oblast` (0.668с), при том что в этих
трёх конкретных тайлах рендерится идентичный набор объектов (все три —
внутри Браславского района, размер ответа совпадает у `district`,
`oblast` и `direct_nofilter` на каждом из 3 тайлов). Правдоподобное
объяснение: `LIKE '2208%'` сканирует/фильтрует 15936-из-55784 строк
даже когда результат рендера не отличается от нефильтрованного — сама
проверка `CQL_FILTER` стоит времени независимо от того, отсекает ли
она что-то в конкретном тайле. Не проверено отдельным экспериментом
(например, `EXPLAIN` на стороне GeoServer/PostGIS) — открытый вопрос,
не блокирует приёмку (район всё ещё заметно быстрее полного экрана
ниже, а не в 2 раза медленнее).

**Экран из 12 тайлов, суммарное время при параллелизме 6 (n=3, порядок
перемешан):**

| условие | значения, с | avg |
|---|---|---|
| без выбора (только фон, 12 запросов) | 1.596 / 1.645 / 1.675 | 1.639 |
| с выбором района (фон 12 + подсветка 12 = 24 запроса) | 3.166 / 3.356 / 3.548 | 3.357 |

**Методологическая оговорка**: скрипт делает два ПОСЛЕДОВАТЕЛЬНЫХ
залпа по 6 (сначала все 12 фоновых, потом все 12 подсветки) — реальный
браузер отправит все 24 запроса почти одновременно (до лимита
соединений на хост), поэтому 3.36с — консервативная (завышенная)
оценка, не точное время реального рендера экрана в браузере.

**Подтверждение доли HIT фона**: не упала — гарантировано архитектурой
(фон никогда не несёт `CQL_FILTER` группы, код не тронут) и подтверждено
`smoke.mjs` (0 GWC-запросов с `CQL_FILTER` из N на всех трёх уровнях,
3 отдельных прогона).

**Вердикт**: A3 выполнено с оговорками — оговорка по методологии
"экрана из 12" (последовательные, не параллельные залпы) и открытый
вопрос по стоимости `LIKE` на district-уровне.

## Блок B. Цена прогрева для пользователей

Проведено на VPS (`geobotany.of.by`) с явного согласия пользователя —
реальный `masstruncate` + `POST /gwc/rest/seed` (тот же REST-путь, что
использует `deliver.py`, воспроизведён напрямую) для обоих слоёв
(`pikurr:fields_latest`, `pikurr:image_assessment`), дважды —
`threadCount=2` (текущий дефолт) и `threadCount=1`. Кэш в конце обоих
прогонов подтверждён тёплым (`geowebcache-cache-result: HIT` на обоих
слоях) — боевой кэш не оставлен в деградированном состоянии.

**Инцидент в процессе замера** (сам по себе полезная находка): первая
попытка запуска отправила `seedRequest` как XML вместо JSON (как
на самом деле шлёт `deliver.py`) — GWC тем не менее принял его и тихо
поставил в очередь реальную задачу, а мой код ошибочно решил, что
запуск не удался, и запустил ВТОРОЙ (корректный, JSON) запрос поверх
первого. В результате `image_assessment` в прогоне `threadCount=2`
недолго досеивался ДВУМЯ параллельными задачами (4 потока вместо 2) —
это ровно тот сценарий "конкуренции потоков при последовательном
засеве", что уже отмечен в CLAUDE.md как открытый вопрос (round36), с
той разницей, что здесь он был вызван моей же ошибкой, а не реальной
гонкой в `deliver.py`. Итоговое время `image_assessment` при
`threadCount=2` (493.5с) — НЕ чистое измерение (искажено дублем),
приведено только для полноты лога; для `fields_latest` при
`threadCount=2` дублирования не было — то число валидно.

**Время полного засева z9-14 (VPS, по логу REST-статуса задачи):**

| слой | threadCount=2 | threadCount=1 |
|---|---|---|
| `fields_latest` | 256.6с (валидно, без дублей) | 304.5с |
| `image_assessment` | 493.5с (⚠ искажено дублем задачи, см. выше) | 493.9с |

Разница `threadCount=2` → `threadCount=1` для `fields_latest`
(256.6с → 304.5с, ×1.19) — заметно МЕНЬШЕ ожидаемого ×2. Правдоподобное
объяснение — по `docker stats` ниже: и при `threadCount=1`, и при
`threadCount=2` CPU контейнера GeoServer доходил до 200–293% (из
теоретических 200% для 2 vCPU — прерываемая ВМ, burst), т.е. узкое
место не в количестве потоков самого сидера, а в стоимости рендера
одного тайла (БД/JVM), которая не масштабируется линейно с
`threadCount` на этой машине.

**`docker stats`/`vmstat` во время засева (снято каждые ~15-18с)**:
CPU контейнера `pikurr_vps_geoserver` — 200–293% в ОБОИХ прогонах
(т.е. `threadCount=1` не снижает нагрузку на CPU заметно). Память —
доходила до **3GiB из лимита 3GiB** (контейнерный cap) в обоих
прогонах — не блокирует этот раунд, но сигнал: полный засев z9-14
вплотную подходит к границе OOM независимо от `threadCount`; отдельный
вопрос на будущее, не входил в ТЗ round37.

**Цена для посетителей — экран из 12 тайлов (те же bbox из
`tiles_with_data.json`, параллелизм 6, непрерывно в течение всего окна
засева, порядка 30 замеров на прогон):**

| состояние | n | avg, с | min | max | ошибок |
|---|---|---|---|---|---|
| спокойное (до засева) | 3 | 1.44 | 1.427 | 1.451 | 0/36 |
| во время засева, `threadCount=2` (оба слоя, ~750с) | 34 | 1.674 | 1.453 | 2.370 | 0/408 |
| во время засева, `threadCount=1` (оба слоя, ~800с) | 31 | 1.693 | 1.451 | 2.634 | 0/372 |

**Главный результат блока B**: цена для посетителей — небольшая и НЕ
зависит заметно от `threadCount`. Средний экран из 12 тайлов
замедляется примерно на **+0.23-0.25с** (~16-17%) относительно
спокойного состояния, отказов (не-200 ответов) не зафиксировано ни
разу (0 из 780 запросов суммарно по обоим прогонам). Это заметно
менее тревожная картина, чем предполагала постановка задачи (там речь
шла о стоимости самого времени засева 299,76с, round36 — не о
стоимости для посетителя во время него).

**Методологическая оговорка**: тестировались 12 ЗАВЕДОМО известных
tile-bbox (`tiles_with_data.json`) на кэшируемом векторном слое
(`fields_latest`) — эти же bbox, вероятно, попадают в число первых
досеиваемых (зум 13 из диапазона 9-14, порядок сидинга зумо-восходящий)
и уже переставали быть `MISS` к моменту первого замера (замер стартовал
через ~15-20с после truncate — первые несколько секунд истинно
холодного состояния ВСЕХ тайлов сразу после `truncate` не пойманы).
Стоимость для посетителя, который попадёт именно на тайл, ещё не
досеянный к его конкретному моменту (глубокие зумы в конце очереди),
может быть выше измеренного среднего — не измерено отдельно в этом
раунде.

**Вердикт по рекомендации (B.4)**: сохранить текущие дефолты
(`threadCount=2`, полный диапазон z9-14) — оснований сужать диапазон
или снижать `threadCount=1` не найдено: `threadCount=1` не даёт
измеримой выгоды ни по нагрузке на CPU, ни по цене для посетителя, а
общее время засева при этом дольше. Единственная находка, заслуживающая
отдельного внимания (вне объёма этого раунда) — память GeoServer
подходит вплотную к контейнерному лимиту 3GiB при полном засеве
независимо от `threadCount`.

## Блок C. Сквозная доставка с прогревом на VPS

Проведено с явного согласия пользователя. Пакет собран штатной
командой пакетирования (`docker compose run --rm etl python -m
src.tasks.package` — локальная ETL-БД `pikurr_refactor-db-1`
запущена отдельно, была остановлена; данные на volume сохранились),
доставлен на прод `rsync` в `~/repikurr/inbox/` (628 МБ, годы
2024/2025), подхвачен штатным `pikurr-watchdog.service`.

**Главная находка — не про прогрев, а про сам механизм доставки.**
Первый прогон (статус `pikurr_update_2024_2025_2026-09-24_09-41.zip.json`,
