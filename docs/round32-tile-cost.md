# Раунд 32: из чего складывается секунда на тайл, и кэширование

См. `prompts/PROMPT_tile_cost_round32.md`. Наблюдение пользователя:
тайлы с данными весят 2-73 КБ, ответ сервера — до 1.25с, при SQL-плане
~21мс. Вопрос раунда: куда уходит остальное время и что устранимо
кэшированием.

**Правило непустых тайлов** (действует с этого раунда, зафиксировано
в `CLAUDE.md`): любой замер скорости делается на тайлах с реальными
данными; в каждом отчётном замере — доля ответов < 2 КБ; замер с
долей > 20% выводом не считается.

**Набор тайлов раунда** — `docs/round32_assets/tiles_with_data.json`,
20 фиксированных bbox (z=13, сетка Web Mercator) по центроидам полей
(`agrifields TABLESAMPLE SYSTEM(3)`, VPS), каждый проверен фактом на
непустой ответ WMS `fields_latest` (18.5-55.1 КБ, доля < 2КБ — **0%**
из 20). Список сохранён в репозитории для последующих раундов.

(доля секунды на loopback).

### A.4. Снаружи, через домен (машина: координатор → VPS через
интернет)

**Холодное соединение** (новый TCP+TLS на каждый запрос), 5 прогонов,
порядок перемешан (индексы: 3, 4, 2, 1, 0):

| тайл | time_appconnect | time_starttransfer | time_total | size |
|---|---|---|---|---|
| 3 | 501мс | 689мс | 767мс | 31453 |
| 4 | 405мс | 601мс | 765мс | 52375 |
| 2 | 371мс | 581мс | 691мс | 22344 |
| 1 | 426мс | 638мс | 813мс | 37353 |
| 0 | 479мс | 697мс | 914мс | 43774 |

Медиана `time_total` — **767мс**. TLS-хендшейк (`time_appconnect`)
съедает **371-501мс** сам по себе — округляется с round31 C:
внешний RTT до VPS (см. ниже) умножается на несколько раундов
TLS-рукопожатия.

**С переиспользованием соединения** (`--next`, одно TCP+TLS на все
5, как реально делает браузер внутри одной сессии/HTTP keep-alive):

| тайл | time_appconnect | time_starttransfer | time_total | size |
|---|---|---|---|---|
| 0 (первый, TCP+TLS) | 619мс | 856мс | 1148мс | 43774 |
| 1 | 0 (переиспользовано) | 185мс | 283мс | 37353 |
| 2 | 0 | 181мс | 322мс | 22344 |
| 3 | 0 | 229мс | 384мс | 31453 |
| 4 | 0 | 211мс | 325мс | 52375 |

После первого (холодного) запроса `time_total` падает до
**283-384мс** — всё ещё в разы больше, чем сумма точек 1-3
(SQL+GeoServer+Caddy+TLS-на-VPS ≈ 1мс+19мс+54мс≈74мс). Разница —
**сетевой RTT координатор↔VPS**, отдельно измеренный `ping`:

```
5 пакетов, rtt min/avg/max/mdev = 53.3/86.8/171.9/44.6 мс
```

RTT крайне нестабилен (53-172мс, разброс почти в 3×) — типичное
поведение прерываемой (burstable) ВМ с долевым vCPU (CLAUDE.md,
правило замеров производительности) и/или переменного сетевого пути
до неё. `starttransfer` при переиспользованном соединении (185-229мс)
≈ 1 RTT (в среднем ~87мс, но с разбросом до 172мс) + обработка на
VPS (Caddy+TLS-decrypt+GeoServer ≈ 54-74мс по точкам 2-3) — сходится
по порядку величины с наблюдаемым.

### Разложение секунды на тайл (по медианам, «тёплое» соединение —
ближе к реальному поведению браузера, чем холодное)

| участок | вклад | доля от типичного тёплого ответа (~320мс) |
|---|---|---|
| SQL (п.1) | ~0.5-1.2мс | <1% |
| + GeoServer (рендер/кодирование, п.2−п.1) | ~+15-20мс | ~5-6% |
| + Caddy/TLS-decrypt на VPS (п.3−п.2) | ~+33-40мс | ~11-13% |
| + внешняя сеть/RTT координатор↔VPS (п.4тёплое−п.3) | ~+130-230мс | **~55-70%** |
| ИТОГО (тёплое соединение) | ~230-320мс | 100% |
| + TCP+TLS на холодное соединение (первый запрос сессии) | ещё +400-800мс | — |

**Главный вывод блока A**: основная доля секунды — это **внешняя
сеть** (RTT до VPS плюс — на холодном соединении — TLS-хендшейк),
а не SQL и не GeoServer. GeoServer-рендер и Caddy/TLS на самой VPS
вместе дают ~50-60мс — заметно, но не определяюще. SQL после
round31-материализации — не узкое место вообще (доли миллисекунды).
Наблюдавшиеся пользователем «до 1.25с» правдоподобно объясняются
холодными/новыми TCP-соединениями (браузер открывает несколько
параллельных соединений на пачку тайлов, каждое — новый TLS-
хендшейк) в сочетании с нестабильным RTT до burstable VPS.

### B.4. Инвалидация при доставке — проверено фактом на эмуляторе

В `deliver.py` уже существовала функция `_truncate_gwc_layer_if_cached()`
(round21, A2) — она была написана НА ВЫРОСТ («если для слоя когда-
нибудь включат тайловое кэширование») и до этого раунда была no-op
для всех слоёв (GWC ничего не кэшировал). Добавлен явный вызов для
векторных слоёв сразу после `refresh_materialized_view()`
(`REPIKURR/deliver.py`, шаг `truncate_gwc_vector_layers`, вызывает
существующую функцию для `fields_latest` и `fields` — для `fields`
она корректно определяет, что слой не в GWC, и ничего не делает).
Растровый `image_assessment` уже вызывал эту функцию из
`_reload_one_store()` — теперь, когда слой реально в GWC, вызов
перестал быть no-op.

**Проверка фактом на эмуляторе** (те же GWC-слои временно созданы и
там же, специально для этого теста):
1. Тайл `fields_latest` (tx=4701,ty=2572,z=13) прогрет до `HIT`.
2. Реальная доставка (`python3 deliver.py`, пакет
   `pikurr_update_2025_2026-09-23_06-42.zip`, собран той же
   `PackageTask`, что и на стенде) — лог подтверждает:
   ```
   [fields_latest] слой кэшируется в GWC — очищаю тайловый кэш (masstruncate)
   [fields_latest] тайловый кэш GWC очищен
   [fields] слой не зарегистрирован в GWC (404) — очистка тайлового кэша не нужна
   ...
   [image_assessment] слой кэшируется в GWC — очищаю тайловый кэш (masstruncate)
   [image_assessment] тайловый кэш GWC очищен
   ```
3. Тот же тайл сразу после доставки — **`MISS`** (кэш действительно
   очищен, не просто залогировано). Содержимое (md5) тайла до и после
   совпало — честно: данные 2025 года в тестовом пакете не менялись
   по существу, поэтому байт-в-байт совпадение ожидаемо и НЕ
   опровергает инвалидацию — проверяемый факт здесь именно смена
   `HIT`→`MISS`, то есть реальная очистка кэша GWC, а не совпадение/
   несовпадение содержимого.

Отдельно, не связанная с этой правкой находка: доставка на эмуляторе
завершилась с `ok:false, step_failed:"delete_zip"` (`FileNotFoundError`)
— на эмуляторе, помимо ручного запуска, постоянно работает свой
`watchdog.py` (`ps aux`: PID активен с 17 сентября), который подхватил
тот же файл из `inbox/` параллельно с ручным `python3 deliver.py` и,
по всей видимости, удалил его первым в своём собственном успешном
прогоне — гонка окружения теста, не дефект round32-правки (весь
содержательный путь — REFRESH, truncate GWC, healthcheck — успешно
отработал и залогирован ДО этой ошибки на последнем шаге).

**Подтверждено**: инвалидация при доставке работает — факт `HIT`→
`MISS` сразу после доставки, для обоих типов слоёв (векторный и
растровый), лог явно показывает труncate для обоих.

### B.5. Замер после включения (машина: VPS, все 20 bbox)

**Через `localhost:8090` (без Caddy/TLS, как в точке A.2)**, холодный/
тёплый, один запрос каждого подряд:

| | n | медиана | диапазон |
|---|---|---|---|
| MISS | 8 | ~206мс | 143-535мс |
| HIT | 32 | ~9.5мс | 5-20мс |

(Из 20 «холодных» — те же 8 истинных MISS, что и на эмуляторе, по
той же причине метатайлинга — часть тайлов из общего набора уже
делят метатайл с ранее запрошенными в блоке A/B тестах.)

**Через публичный домен, сеть+TLS** (кэш явно очищен перед серией —
`masstruncate` на `fields_latest`), порядок перемешан (seed=4032):

Холодное соединение (новый TCP+TLS на каждый запрос), 20 прогонов:
`MISS` — 12 из 20 (60%), `HIT` — 8 из 20 (40%, метатайлинг). Времена
почти не различаются по группам — **493-874мс на оба исхода** —
внешние TCP+TLS накладные расходы (см. Блок A) полностью маскируют
экономию GWC на холодном соединении.

Тёплое (переиспользуемое) соединение, повторный проход по тем же 20,
**после** первого прохода (теперь у всех `HIT`, доля попаданий —
**100%**, 20/20): `165-290мс` (кроме первого тайла серии — 623мс,
всё ещё новое TCP+TLS для самого первого запроса цепочки).

**Честный вывод B.5**: на **самой VPS** (без сети) выигрыш GWC —
кратный (медиана MISS/HIT ≈ 206/9.5 ≈ **22×**, того же порядка, что
и потолок на эмуляторе). Но **для одиночного случайного
пользователя, впервые открывающего страницу**, выигрыш почти не
заметен — доминирует сетевой TCP/TLS-оверхед (Блок A), не
GeoServer/SQL. Кэш даёт максимальную пользу там, где несколько
запросов идут к ОДНОЙ и той же области — повторные визиты, несколько
пользователей на одном участке карты, зум/сдвиг назад к уже
просмотренному месту — именно тогда GWC устраняет MISS-издержки
(143-874мс на холодном рендере) полностью, а не только на ~5-6% как
GeoServer-рендер сам по себе.

### C.2. Проверка: задача round29 A6 по-прежнему решена

round29 A6: у `fields_latest` не было cache-buster'а вообще →
случайный `HTTP 503` "залипал" навсегда в HTTP-кэше браузера. Решение

Проверено фактом на эмуляторе (браузерный перехват недоступен —

в C.4 ниже; проверка сделана на уровне HTTP напрямую):
1. `GET /static/year_district.json` дважды подряд, БЕЗ доставки между

   (`20260923095712`).
2. Реальный вызов `write_year_district_lookup()` (та же функция, что

**Подтверждено**: URL тайла стабилен между перезаходами без доставки

### C.3. `tiled=true` и отдельный эндпоинт GWC — установлено фактом

Проверено фактом (эмулятор и VPS): обычный `/geoserver/pikurr/wms`
**не** проксируется через GeoWebCache даже с параметром `tiled=true`
или `TILED=true` — заголовок `geowebcache-cache-result` в ответе
отсутствует в любом случае (значит, «прямая интеграция WMS↔GWC» в
этой конфигурации GeoServer не задействована). Единственный путь,
который реально отдаёт кэшированные тайлы (проверено — `geowebcache-
cache-result: HIT/MISS` в ответе, `geowebcache-tile-bounds` совпадает
с расчётной сеткой) — отдельный эндпоинт `/geoserver/gwc/service/wms`
с параметром `tiled=true`.

Добавлена константа `WMS_GWC_BASE_URL` (`constants.js`) и множество
`GWC_CACHED_LAYERS = {'pikurr:fields_latest', 'pikurr:image_assessment'}`
(ровно те два слоя, что зарегистрированы в GWC в блоке B3 — не
включает `fields` с `CQL_FILTER` и историчные `image_assessment_<year>`,
которые в GWC не регистрировались). `MapView.jsx` выбирает URL и
добавляет `tiled: true` в параметры **только** для слоёв из этого
множества; остальные идут через прежний `WMS_BASE_URL` без изменений.

Отдельная находка по пути, не входившая в изначальный вопрос C.3, но
существенная для самого блока C (браузерное кэширование): GWC по
умолчанию отдавал `Cache-Control: no-cache, no-store, must-revalidate`
(`expireClients` не был задан явно → GWC-дефолт «не кэшировать у
клиента» — даже при стабильном URL браузер НЕ сохранял бы тайл
локально). Установлен явный `expireClients=86400` (1 день — безопасно
именно потому, что URL меняется вместе с `dataVersion` при реальной
смене данных, так что более длинный TTL не создаёт риска отдать
устаревший тайл под старым URL) на обоих зарегистрированных GWC-слоях,
на эмуляторе и на VPS. Проверено фактом:
```
до:    Cache-Control: no-cache, no-store, must-revalidate
после: Cache-Control: max-age=86400, must-revalidate
```

### C.4. Проверка перехватом в браузере — не выполнено своими силами

### D.3. Ответ раунда

**Сколько занимает тайл с данными — до и после**:
- SQL: было ~236-293мс (round30, до материализации) → стало
  **0.3-1.2мс** (round31, подтверждено заново в этом раунде, блок A.1).
- Полный внешний ответ БЕЗ кэша, тёплое TCP-соединение (реалистичный
  сценарий работы браузера внутри одной сессии): **~230-320мс**
  медиана (блок A.4) — из них SQL <1%, GeoServer-рендер ~5-6%,
  Caddy/TLS-на-VPS ~11-13%, **внешняя сеть/RTT ~55-70%**.
- С кэшем GWC (после блока B/C, при повторном обращении к той же
  области — HIT): **165-290мс** на тёплом соединении внешне (блок
  B5) — экономит именно ту часть, что раньше шла на SQL+GeoServer+
  часть Caddy (~50-75мс), но НЕ устраняет сетевой RTT, который
  остаётся доминирующим фактором для одиночного случайного
  пользователя.
- Итоговый замер этого раунда (k6, VU=1-3, тот же кэшируемый путь):
  медианы **71-710мс** в зависимости от параллелизма и сетевого
  джиттера VPS (правило CLAUDE.md — VPS burstable, разброс на порядок
  между прогонами при одинаковых условиях — не аномалия, а
  задокументированное свойство машины).

**Что осталось узким местом**: внешний сетевой RTT координатор↔VPS
(53-172мс, наблюдаемый разброс почти в 3× — round32 A.4) и
холодные TCP+TLS соединения (+400-800мс на первый тайл каждой новой
сессии/вкладки) — оба фактора вне досягаемости серверных оптимизаций
этого раунда (SQL/GWC). GWC решает задачу ПОВТОРНЫХ обращений к
одной и той же области (несколько пользователей, зум туда-обратно) —
здесь выигрыш кратный (медиана MISS/HIT ≈ 22× на VPS, блок B5) — но
не помогает одиночному новому пользователю на новой TCP-сессии.

**Нужен ли ещё рычаг**: да, если приоритет — именно первый визит
одиночного пользователя, тогда следующий кандидат — HTTP/2 (уже
включен, `alt-svc: h3` виден в заголовках, но TLS-хендшейк всё равно
занимает несколько RTT) или сокращение числа отдельных TCP-соединений,
которые открывает браузер на пачку тайлов (сейчас видно, что даже
внутри одной страницы держится больше одного соединения). Это НЕ
исследовано в этом раунде — обозначено как открытый вопрос для
следующего, не решение задним числом.
