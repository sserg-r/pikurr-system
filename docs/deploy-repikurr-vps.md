# Развёртывание REPIKURR на VPS

Черновая инструкция для развёртывания с нуля на чистом хосте (round21,
часть B). **Не выполнять до аренды VPS и домена.** Всё ниже подготовлено
заранее, чтобы развёртывание после аренды заняло часы, а не дни.

---

## 1. Подготовка сервера

- чистый Linux-хост (Ubuntu 22.04/24.04 или аналог), Docker + Docker Compose
  v2 (проверить: `docker compose version` — v2 нужна для раскрытия `~` в путях
  томов, см. round19);
- непривилегированный пользователь для эксплуатации (не root); `docker`-группа
  этому пользователю НЕ нужна после того, как `deliver.py` перестал вызывать
  `docker exec` (round21, A3) — единственное оставшееся использование docker
  CLI на этом хосте — сам `docker compose`, которым управляет оператор, а не
  автоматика доставки;
- открыть на файрволе только 80/443 (nginx) и SSH-порт для канала доставки
  (раздел 4). PostGIS (5432) и GeoServer (8090) слушают только `127.0.0.1` —
  открывать их наружу не нужно и не следует.

## 2. `.env`

```
cp REPIKURR/.env.example REPIKURR/.env
```

Заполнить (round21, B1 — без значений стек не поднимется, `docker-compose.vps.yml`
падает с `:?...` при отсутствии переменной):

```
POSTGRES_PASSWORD=<сгенерировать>
GEOSERVER_ADMIN_PASSWORD=<сгенерировать>
DOMAIN=<домен>
```

Отдельно — `REPIKURR/deliver.env` (копия `deliver.env.example`, не коммитится):
`FRONTEND_DB_PASSWORD` и `GEOSERVER_PASSWORD` должны совпадать с тем, что
задано выше в `.env` (это два места с одним и тем же паролем — `deliver.py`
подключается к тем же сервисам напрямую через `127.0.0.1`, минуя nginx).

### Ротация паролей (порядок)

1. Остановить `pikurr-watchdog.service` (иначе внутри доставки, начавшейся
   между сменой пароля БД и обновлением `deliver.env`, `ensure_unique_constraint`/
   `import_vectors` упадут на аутентификации — не опасно, ZIP уйдёт в `failed/`
   и будет переобработан после починки, round21 A1, но лучше не создавать
   лишний шум в логе);
2. сменить пароль в самой БД: `docker exec -it pikurr_vps_postgis psql -U pikurr -c "ALTER USER pikurr WITH PASSWORD '...'"`;
3. обновить `POSTGRES_PASSWORD` в `.env` и `FRONTEND_DB_PASSWORD` в `deliver.env`;
4. `docker compose -f docker-compose.vps.yml up -d` (пересоздаёт только то, что
   зависит от изменившейся переменной);
5. то же для GeoServer: сменить пароль admin через `/geoserver/web` (под
   basic-auth, раздел 3) или REST, обновить `GEOSERVER_ADMIN_PASSWORD` в
   `.env` и `GEOSERVER_PASSWORD` в `deliver.env`;
6. `systemctl start pikurr-watchdog.service`.

## 3. Первая доставка на чистый инстанс — заглушки перед первым запуском GeoServer

**Обязательный шаг на новом развёртывании, до первого старта GeoServer.**
На `geobotany.of.by` (round22) это не было сделано заранее — GeoServer при
первом обращении к слою `pikurr:fields` (virtual table с фиксированной SQL
`SELECT * FROM assessment_ready`) обнаружил отсутствие этого view и ушёл в
агрессивный (тысячи запросов/сек) цикл опроса, насыщая пул соединений
PostGIS и мешая первому реальному импорту пройти. Разбор и временное ручное
исправление — `docs/round22-vps-deploy.md`. Round23 формализует это в
процедуру:

1. Поднять **только** PostGIS: `docker compose -f docker-compose.vps.yml up -d postgis`;
2. подождать, пока контейнер станет `healthy` (`docker compose ps`);
3. выполнить заглушки:
   ```
   PGPASSWORD=<POSTGRES_PASSWORD> psql -h 127.0.0.1 -p 5432 -U pikurr -d pikurr \
     -v ON_ERROR_STOP=1 -f PIKURR/src/sqlscripts/bootstrap_empty_schema.sql
   ```
   (файл создаёт пустые `assessment` и `assessment_ready`/`assessment_ready_latest`
   — обычные `VIEW`, возвращающие ноль строк; настоящую схему при первой
   доставке создаст `create_assessment_schema.sql` — он сам мигрирует эту
   заглушку в `MATERIALIZED VIEW`, миграционный путь уже заложен именно под
   этот случай);
4. только теперь поднять остальной стек:
   `docker compose -f docker-compose.vps.yml up -d`.

**Почему заглушка на уровне процедуры, а не проверка внутри `deliver.py`**:
проверка внутри `deliver.py` (создавать структуры "если их нет" при первом
вызове) не закрывает разрыв между моментом, когда GeoServer поднимается
впервые, и моментом первой РЕАЛЬНОЙ доставки — эти события могут быть
разделены днями. Заглушка должна существовать до первого старта GeoServer,
то есть это забота процедуры развёртывания, а не времени выполнения
`deliver.py`.

## 4. Домен и сертификат

Фронтальный прокси и TLS — Caddy (`docker-compose.vps.yml` + `Caddyfile`,
round22, задача 1), не nginx+certbot — тот вариант сохранён в
`docs/legacy/nginx.vps.conf.template`, не используется (см. пояснение там).

Caddy сам получает и продлевает сертификаты (проверяет срок при каждом
старте и периодически в фоне) — никакого отдельного bootstrap-порядка не
требуется, но на первом прогоне лучше не бить по боевому лимиту ACME.
Порядок, фактически выполненный и подтверждённый на `geobotany.of.by`
(round22, задача 6):

1. **Staging ACME первым.** В `Caddyfile` раскомментировать строку
   `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory` внутри
   глобального блока — лимит боевого эндпоинта на неудачные проверки
   (5/час/имя) легко исчерпать при отладке проксирования/портов;
2. поднять стек, убедиться, что staging-сертификат выдан для домена и
   `www.`-поддомена (видно в `docker logs pikurr_vps_caddy` — строки
   `certificate obtained successfully`, `issuer=...staging...`);
3. **Переключить на боевой ACME**: закомментировать `acme_ca` обратно,
   **удалить тома `caddy_data`/`caddy_config`** (иначе Caddy останется со
   staging-сертификатом — браузеры ему не доверяют):
   ```
   docker compose -f docker-compose.vps.yml stop caddy
   docker rm pikurr_vps_caddy
   docker volume rm repikurr_caddy_data repikurr_caddy_config
   docker compose -f docker-compose.vps.yml up -d caddy
   ```
4. проверить боевой сертификат: `curl` **без `-k`** должен пройти (доверенная
   цепочка), `openssl s_client ... | openssl x509 -noout -issuer` должен
   показать `Let's Encrypt` (не `STAGING`);
5. продление — Caddy получает ACME Renewal Info сразу после выпуска и сам
   планирует момент продления (видно в логе: `got renewal info`,
   `recheck_after`) — отдельный cron не нужен.

Basic-auth файл для админки GeoServer — не файл на диске, а хеш в `.env`
(`GEOSERVER_BASIC_AUTH_HASH`, читает `Caddyfile` через переменную окружения
контейнера). Сгенерировать:
```
sudo docker run --rm caddy:2-alpine caddy hash-password --plaintext '<пароль>'
```
**Осторожно**: результат — bcrypt-хеш вида `$2a$14$...`. Docker Compose
интерпретирует `.env` рекурсивно и портит любой `$` в значении (пытается
подставить его как ссылку на другую переменную) — экранировать каждый `$`
как `$$` при записи в `.env` (проверено фактически на живом инциденте:
без экранирования хеш обрубался с 60 символов до 38, `basic_auth` не пускал
даже с верным паролем).

### Окно недоступности слоя при переиндексации

Замер round20: пересборка каталога гранул (удаление индекса → harvest →
финальный reset) занимает **14–15 секунд на 912 файлах**. В это окно WMS по
затронутому слою может вернуть пустой или частично устаревший ответ — на
локальном стенде это не имело значения, на публичном сайте с реальными
посетителями это заметно.

**Смягчение, которое можно сделать без доработки `deliver.py` прямо сейчас**:
планировать `PushTask` на минимально посещаемое время (ночь по местному
времени аудитории) — самое простое и достаточное при текущей частоте
доставок (несколько раз в год, судя по истории).

**Предложение на будущее (не реализовано)**: staging-каталог. Копировать
новый год не в `data/geodata/{year}/` напрямую, а во временный
`data/geodata/{year}_staging/`, харвестить индекс ТАМ (это можно делать сколь
угодно долго — публичный слой ничего не знает про staging-каталог и продолжает
отдавать старые данные без сбоев), и только когда staging-индекс полностью
готов и проверен по числу гранул — одним быстрым `PUT` переключить `url`
стора `image_assessment` на staging-каталог и переименовать каталоги
(`{year}` → `{year}_prev`, `{year}_staging` → `{year}`). Видимое окно
сокращается с ~15с до времени одного `PUT` + `reset` (доли секунды) за счёт
того, что тяжёлая часть (харвест 900+ файлов) происходит до переключения, а
не во время него. Требует доработки `deliver.py` — не входило в объём этого
раунда.

## 5. Канал доставки (B3 — предложение, не внедрено в `push.py`)

Сейчас `push.py` использует `-o StrictHostKeyChecking=no` — на машине в
интернете это снимает защиту от подмены хоста. План для VPS:

1. **Отдельный пользователь на VPS** только для приёма пакетов, без
   интерактивного shell (`/usr/sbin/nologin`), без доступа к остальной
   файловой системе, кроме `~/repikurr/inbox/` и (см. пункт 4) чтения статуса.

2. **known_hosts с зафиксированным отпечатком** вместо
   `StrictHostKeyChecking=no`:
   ```
   ssh-keyscan -H <домен_или_ip> >> known_hosts_pikurr_delivery
   ```
   путь передаётся новой переменной `DELIVERY_KNOWN_HOSTS`, `push.py` (при
   внедрении) заменит `-o StrictHostKeyChecking=no` на
   `-o UserKnownHostsFile=$DELIVERY_KNOWN_HOSTS -o StrictHostKeyChecking=yes`.

3. **Ограниченный ключ и конфликт с опросом статуса — решение**.
   `command=` в `authorized_keys` пускает ключ только на ОДНУ команду — но
   `PushTask` использует SSH дважды по-разному: `rsync` (пишет ZIP в inbox) и
   `cat status/<имя>.json` (читает статус, round20/21). Прямое ограничение
   одной командой их не разделяет. Два рабочих варианта:

   **Вариант проще — диспетчер-скрипт.** Один ключ,
   `command="/home/pikurr_delivery/bin/dispatch.sh"` в `authorized_keys`
   (плюс `no-port-forwarding,no-agent-forwarding,no-X11-forwarding`), скрипт
   разбирает `$SSH_ORIGINAL_COMMAND` и пускает ровно два паттерна:

   ```bash
   #!/bin/bash
   set -eu
   case "$SSH_ORIGINAL_COMMAND" in
     "rsync --server"*)
       # rrsync (входит в пакет rsync) держит запись строго внутри каталога
       exec /usr/bin/rrsync -wo /home/pikurr_delivery/repikurr/inbox
       ;;
     cat\ /home/pikurr_delivery/repikurr/status/pikurr_update_*.zip.json)
       # без переменных путей — только фиксированный каталог + маска имени
       exec $SSH_ORIGINAL_COMMAND
       ;;
     *)
       echo "Операция не разрешена" >&2
       exit 1
       ;;
   esac
   ```
   `rrsync` — стандартный ограничивающий враппер, идущий в комплекте с
   `rsync` (обычно `/usr/share/doc/rsync*/scripts/rrsync` или уже в `$PATH`
   как `rrsync`), сам не даёт выйти за пределы указанного каталога и
   запрещает `--delete`/чтение произвольных путей при `-wo` (write-only).

   **Вариант проще для аудита, но два ключа.** Ключ 1: `command="rrsync -wo
   .../inbox"` — только приём файла. Ключ 2: `command="cat .../status/*.json"`
   не работает буквально (shell-глоб в `command=` не раскрывается для
   произвольного имени пакета) — тогда либо второй диспетчер поменьше (только
   валидация имени + `cat`), либо вместо чтения по ssh отдать статус через
   маленький HTTP-эндпоинт на loopback, который `PushTask` дёргает через тот
   же SSH туннель. Это уже сложнее первого варианта без явной выгоды —
   рекомендация: диспетчер-скрипт (вариант 1).

4. Изменения в `push.py`, которые всё это предполагает (`DELIVERY_SSH_KEY`
   отдельный от прочих, `DELIVERY_KNOWN_HOSTS`) — **только предложены**,
   код не менялся, согласовать отдельно перед внедрением.

## 6. Сайзинг

По измерениям раунда 19 и структуре пакета:

| величина | значение |
|---|---|
| один пакет (год целиком) | ~390 МБ (сжатый) |
| растры одного года после распаковки | ~1.27 ГБ |
| три года растров | ~3.8 ГБ |
| PostGIS фронтенда (agrifields ~59К объектов + assessment) | пока не критично на фоне растров, растёт с числом лет × полей |
| **итого диск, с запасом** | **25–30 ГБ** (растры на несколько лет + PostGIS + образы Docker + место на переходный `_removed_`/`status`/`failed` до срабатывания retention, round21 A5) |
| **RAM** | **4 ГБ** — GeoServer (JVM heap) + PostGIS + nginx на одном хосте; это минимальный, а не комфортный запас — при живом трафике первое, что стоит нарастить |
| скорость канала | пакет 390 МБ: ~5 мин на 10 Мбит, ~1 мин на 50 Мбит, ~30с на 100 Мбит — при увеличении частоты доставок или объёма (больше лет) может понадобиться инкрементальный обмен вместо полного пакета |

`DELIVERY_RETENTION_DAYS` (round21, A5, по умолчанию 30) — держать под
контролем на маленьком диске; `deliver.py --cleanup --dry-run` до включения
автоматической очистки по cron.
