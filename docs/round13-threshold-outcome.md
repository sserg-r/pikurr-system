## Задача 3. Починить склейку

Реализовано в `PIKURR/src/utils/image.py` (`merge_tiles`),
`PIKURR/src/tasks/segmentate.py` (`process_trapeze`),
`PIKURR/src/tasks/package.py` (`check_missing_sheets`). Математика
`merge_imageset` не менялась — только то, что в неё передаётся.

### Что изменилось

- `merge_tiles` теперь строит сетку сборки по **диапазону координат**
  присутствующих файлов (`min_x..max_x × min_y..max_y`), а не подсчётом их
  числа. Недостающая ячейка заполняется чёрным плейсхолдером на своей
  истинной позиции — остальные тайлы больше не сдвигаются.
- Если пропуски есть — пишется `<лист>_gaps.json` рядом с папкой листа (не
  внутри неё, по аналогии с `_missing.json` раунда 2): координаты, причина
  (`no_tile_file` / `unreadable_tile_file`), `missing_fraction`.
- `process_trapeze` логирует `WARNING` с долей плейсхолдер-пикселей, если
  `gaps.json` создан.
- `package.py`: `check_missing_sheets` сверяет собранные `.tif` со списком
  листов проекта и пишет `ERROR` по отсутствующим.

**Отступление от буквы ТЗ (осознанное)**: ТЗ называет источником сверки
`razgrafka` — но это общенациональная сетка 1:10000, **21280** листов на
всю Беларусь, а не список листов проекта. Прямая сверка с ней давала бы
**~20000 «отсутствующих» на каждый прогон** — не сигнал, а шум, полностью
бесполезная проверка. Использовал `trapeze_serv` (912 строк) — тот же
источник, что уже использует `SegmentationTask.get_trap_list()`
(`settings.dbtables.trap`). Без этой замены задача была бы формально
выполнена, а по факту бесполезна — проверено сравнением (тест ниже).

### Проверки (все 4 из ТЗ — на сервере, не в проде)

1. **Единичный пропуск в середине листа** (`N-35-10-А-а-2`, удалён 1 из 672
   тайлов): исключения нет, плейсхолдер на месте пропуска (проверено
   попиксельно — блок нулевой), `gaps.json` содержит ровно эту координату,
   сосед не сдвинут (побайтово совпадает с эталоном).
2. **Полностью отсутствующий X-столбец** (тот же лист, удалён весь столбец
   x=75946, 28 тайлов) — **главная проверка раунда**:
   - исключения нет, размер канваса **не уменьшился** (6144×7168, как у
     полного листа);
   - **все 644 проверенных блока вне столбца-пропуска побайтово совпадают
     с эталонной сборкой того же листа без пропуска** — сдвига нет;
   - для контраста прогнан тот же сценарий **старым** кодом: он не падал
     (28 и 644 делятся нацело — совпадение делимости), но канвас вышел
     **на 256px уже** (5888×7168 вместо 6144×7168), и на абсолютной позиции
     пропавшего столбца оказался пиксель-в-пиксель тайл его **соседа**
     (сдвинутый на позицию влево) — именно тихая порча, предсказанная
     диагнозом раунда 12, теперь воспроизведена и устранена.
3. **Полный лист без пропусков**: merge_tiles нового кода даёт **побайтово
   идентичный** результат старому коду (`np.array_equal` = True) — фикс не
   меняет поведение на штатном случае.
4. **`package.py` сообщает об отсутствующем листе**: синтетический тест
   (20 имён из `trapeze_serv`, 3 намеренно не положены в `.tif`-каталог) —
   `check_missing_sheets` корректно называет ровно эти 3 (плюс честно
   перечисляет остальные реально отсутствующие в тестовом каталоге).

### Известное остаточное ограничение (не устранено, вне минимального объёма ТЗ)

Фикс закрывает пропуски **внутри** bbox присутствующих файлов. Если у листа
отсутствует тайлы **за пределами** этого bbox (весь один угол/сторона
никогда не скачивались — ровно случай `O-35-142-В-б-3`, 274/672, пропуски
вне охваченной присутствующими файлами области), `merge_tiles` не может
узнать об их существовании только по содержимому папки — тот же
принципиальный предел уже был у `get_bbox_for_tileset` (геопривязка тоже
строится по bbox присутствующих файлов). С новым кодом такой лист **больше
не падает** и получает `.tif`, но лишь по фактически охваченной площади
(2560×7168 вместо полных 6144×7168 для `O-35-142-В-б-3`) — без явного
предупреждения, что почти 60% площади листа вообще отсутствует в
результате (не плейсхолдер, а полностью вне канваса). Раньше такой лист
хотя бы не попадал в пакет вовсе (падал); теперь может попасть как
частичный, без пометки. Для полного решения нужен внешний источник истинной
границы листа (геометрия `razgrafka`), а не только присутствующие файлы —
это отдельная задача, не входившая в минимальный объём ТЗ («не менять
математику `merge_imageset`» и явный список из 4 проверок, которые все
пройдены). Обозначаю как открытый риск для человека.

### Главный результат: доля тайлов выше порога — значительно более резкий переход, чем средний `B−R`

По требованию ТЗ зависимость посчитана дважды: по среднему `B−R` листа и по
доле из 15 тайлов листа с `B−R>30` (правило раунда 10, `frac30`).

### Где проходит порог

Порог по `frac30` **устойчиво выходит за пределы «шумового» режима
начиная с 0.53** (8 из 15 тайлов) — это **дословно правило раунда 10**

## Задача 4. Вторая популяция брака — безлиственный период

### Признак найден: `G − R`

Проверены все три кандидата из ТЗ на 3 известных безлиственных листах

как ограничитель («умеренная яркость» из ТЗ, 50–150), чтобы не путать

нужно было бы для «исправления» недосчитанного леса.

**Вывод**: смена источника на Esri лечит дымку (раунд 12), но **не лечит
безлиственную съёмку** — эффект не в источнике снимка, а в сезоне съёмки
и/или самой модели, которая не обучена узнавать голый лес. Это отдельная
проблема, требующая отдельного решения (не перевода источника), если её
вообще решать.

### Для решения человека

- **Порог детектора дымки**: раунд 13 указывает на `frac30≥0.53` (≥8 из 15
  тайлов выше `B−R=30`) как точку, где последствия становятся
  систематическими — это исходное правило раунда 10, теперь подтверждённое
  через прямое измерение последствий, а не через прокси. Финальный выбор
  порога — за человеком, включая то, взвешивать ли ещё и блайнд-обзор
  раунда 12 (который предполагал более мягкий эффективный порог ~24–25 по
  среднему `B−R`, но не проверялся через `frac30` и не через последствие).
- **Перевод поражённых листов на Esri**: аргументы за (раунд 12: не
  насыщение, реальное улучшение на нелесных листах) и предупреждения
  (раунд 13, задача 3: остаточный риск с крайне неполными листами вроде
  `O-35-142-В-б-3`, где Esri-канвас соберётся по частичной площади без
  явной пометки) — накоплены за 6 раундов (8–13), решение не принималось
  нигде специально, чтобы оставить его человеку.
- **Безлиственная съёмка** (54 листа, 6.0%, независимо от дымки) — новая
  находка этого раунда, ни один из раундов 8–12 её не касался. Смена
  источника не помогает; если решите исправлять — понадобится другой
  подход (пересъёмка/сезонная фильтрация источника/дообучение модели), не
  затронутый ни одним из проведённых раундов.
- **Развёртывание фикса склейки** (задача 3) — код готов и протестирован,
