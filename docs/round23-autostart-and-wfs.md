## Задача 1. Список годов/районов — статика вместо WFS

**Разведка подтвердила предположение ТЗ.** `loadYearDistrictData()`
(`src/services/geoserver.js`) используется только для:
- `availableYears` — список годов для выпадающего списка;
- `districtsByYear` — множество кодов районов по году (фильтрация
  выпадающего списка районов в `Sidebar.jsx`).

Никакого поэлементного соответствия «поле → год» не строится — нужна
именно агрегация (уникальные годы/районы), не проекция колонок. Облегчённый
virtual table (предложение раунда 22) действительно лечил бы не то: он всё
равно вернул бы все 55784+ объекта.

**Реализовано самое дешёвое решение**:
- `deliver.py:write_year_district_lookup()` — после обновления
  материализованного представления выполняет
  `SELECT DISTINCT year, district FROM assessment_ready ...` и пишет
  `static/year_district.json` (атомарно, `.tmp` + `rename`);
- `Caddyfile`: `handle_path /static/* { root * /srv/static; file_server }`
  с `Cache-Control: public, max-age=300`; `docker-compose.vps.yml`
  монтирует `./static` (host, пишет `deliver.py`) в Caddy как `bind mount`
  (не именованный том — это не состояние Caddy, а файл, который переписывает
  внешний процесс);
- `geoserver.js:loadYearDistrictData()` — теперь `fetch('/static/year_district.json')`,
  без WFS. Образ React пересобран (вне ВМ, `192.168.251.190`, тег
  `repikurr-react:latest`), задеплоен.

**Замер до/после** (одинаковый bbox/сценарий, публичный домен):

| | время |
|---|---|
| WFS `pikurr:fields`, `propertyName=year,nr_user` (до) | **~12с** |
| `/static/year_district.json` (после) | **~0.5с** |

Ускорение ~24×. Остаточные 0.5с — сетевой/TLS оверхед, не обработка (сам
файл — 104 байта).

**Альтернатива через отдельный SQL-view в GeoServer** — описана в ТЗ как
вариант, не реализовывалась: она была бы дороже (та же тяжёлая передача
через JDBC/virtual table для 55784+ строк) и медленнее при том же
результате — облегчение виртуальной таблицы само по себе не убирает
фундаментальную проблему «GeoServer тянет полные строки независимо от
`propertyName`».

## Задача 2. `assessment_ready` — материализованное представление

`assessment_ready`/`assessment_ready_latest` в
`PIKURR/src/sqlscripts/create_assessment_schema.sql` — `assessment_ready`
теперь `MATERIALIZED VIEW`, `assessment_ready_latest` остался обычным
`VIEW` (базовая таблица уже материализована и индексирована — `DISTINCT
ON` по ней быстр сам по себе, без нужды материализовывать и её).

**Индексы**: `idx_assessment_ready_year` (year), `idx_assessment_ready_district`
(district — новая колонка, `LEFT(nr_user, 4)`, материализована прямо в
representation ради этого), `idx_assessment_ready_nr_user_year` (уникальный,
nr_user+year), `idx_assessment_ready_geom` (GIST по geom).

**`REFRESH` без `CONCURRENTLY` — решение и обоснование**: обычный `REFRESH`
берёт `ACCESS EXCLUSIVE` лок на время пересборки, `CONCURRENTLY` избегает
блокировки, но требует уникальный индекс (уже есть — на будущее это чисто
техническая правка) и держит вдвое больше места на диске + сам по себе
медленнее. На витрине с редкими доставками (несколько раз в год) и
невысоким постоянным трафиком несколько секунд блокировки на чтение не
обосновывают эту сложность — выбран обычный `REFRESH`.

**Порядок в `deliver.py`**: `import_vectors()` → `ensure_unique_constraint()`
→ `recreate_views()` (создаёт структуру при самой первой доставке на чистый
инстанс) → **`refresh_materialized_view()`** → `write_year_district_lookup()`
→ `reload_geoserver()`. REFRESH — до перезагрузки слоёв GeoServer, как и
требовало ТЗ («GeoServer не должен обращаться к слою в момент обновления»).

**Замеры** (`EXPLAIN ANALYZE`, серверное время выполнения, идентичный
запрос на всём протяжении раундов 22-23):

| момент | `SELECT * FROM assessment_ready` |
|---|---|
| до фиксов round22 | 7.6с (в основном — `jsonb_each_text`, ~108 тыс. вызовов) |
| после фиксов round22 (jsonb_each_text + shape_area) | 2.3с |
| после материализации (round23) | **14.2 мс** |

Итоговое ускорение относительно исходного состояния — **~535×**. WMS
`GetMap` не затронут этой правкой (растровые тайлы не проходят через
`assessment_ready`) — стабильно ~0.5-0.7с до и после, без изменений.

**Стоимость `REFRESH`, добавленная к каждой доставке**: замерено на боевых
данных VPS — **8.7 секунды** (полная пересборка представления + 4 индекса
на 55784 строках с геометрией). Это разовая стоимость на доставку (несколько
раз в год), не на каждый запрос пользователя — ключевой смысл всей правки.

**Место на диске**: материализованное представление с индексами —
**92 МБ** (`pg_total_relation_size`). Свободно на диске VPS — 18 из 29 ГБ
(до этой правки), после — 18 ГБ минус 92 МБ, разница не влияет на общую
картину сайзинга.

## Задача 3. Заглушки для первой доставки на чистый инстанс

**Выбранный вариант**: заглушка на уровне **процедуры развёртывания**
(`PIKURR/src/sqlscripts/bootstrap_empty_schema.sql`, новый файл), не
проверка внутри `deliver.py`.

**Обоснование**: проверка "создавать структуры, если их нет" внутри
`deliver.py` не закрывает разрыв между моментом первого старта GeoServer
и моментом первой РЕАЛЬНОЙ доставки — эти события могут быть разделены
днями (именно так и произошло на `geobotany.of.by` в round22). Заглушка
должна физически существовать до первого старта GeoServer — это забота
процедуры развёртывания, а не времени выполнения `deliver.py`.

Скрипт создаёт `assessment` (пустая, `CREATE TABLE IF NOT EXISTS`) и
`assessment_ready`/`assessment_ready_latest` (пустые обычные `VIEW`,
`WHERE FALSE`, набор колонок близок к реальному представлению). Реальную
схему при первой доставке создаёт `create_assessment_schema.sql` — он сам
мигрирует заглушку (обычный `VIEW` → `MATERIALIZED VIEW`), миграционный
путь для этого случая уже заложен (проверено фактически в этом же раунде —
именно так мигрировал живой `assessment_ready` на VPS с round22-версии).

Процедура (`docs/deploy-repikurr-vps.md`, новый раздел 3): поднять только
PostGIS → выполнить заглушку → поднять остальной стек. Задокументировано.

## Сквозная проверка (после всех правок)

Полный цикл: `PushTask` (реальный, новый пакет, пересобранный
`PackageTask` после всех правок) → `watchdog` → `deliver.py` (растры,
векторы, `REFRESH MATERIALIZED VIEW`, статика, `GeoServer reload`) →
проверка по содержимому (WMS, WFS, `/static/year_district.json`) —
результат ниже (заполняется по факту прогона).

**Побочная находка при тестировании**: повторная доставка СТАРОГО (не
пересобранного) zip-файла с более ранним содержимым `create_assessment_schema.sql`
корректно провалилась на `REFRESH MATERIALIZED VIEW` (`"assessment_ready"
is not a table or materialized view`) — ожидаемо и правильно: старый пакет
пересоздаёт `assessment_ready` как обычный `VIEW` (по своей, более старой,
копии схемы), а `REFRESH MATERIALIZED VIEW` требует именно материализованный
объект. Это не баг механизма, а артефакт повторной доставки исторического
пакета в целях теста — в реальной эксплуатации каждый новый пакет несёт
актуальную версию `create_assessment_schema.sql` (копирует её `PackageTask`
на момент сборки). Статус-файл (`step_failed: "refresh_materialized_view"`)
корректно отразил причину падения — задачи 3-4 раунда 20/21 (обратная
связь) сработали как задумано даже на этом неожиданном сценарии.
