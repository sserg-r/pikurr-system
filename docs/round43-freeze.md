## Блок A. Недосев кэша: дефект или норма

### Метод

1. Получены реальные границы (native bounding box) слоёв `fields_latest`
   (векторный, featuretype) и `image_assessment` (растровый, coverage)
   через REST GeoServer, переведены в EPSG:3857 стандартной формулой
   Меркатора.
2. Через `tile_math.py` (`tile_range_for_bbox_3857`, round36) посчитано
   точное ожидаемое число тайлов на z9-z12 для обоих слоёв.
3. Число файлов на диске (`geoserver_data/gwc/pikurr_<слой>/EPSG_900913_<зум>`)
   сверено с расчётом напрямую.

### Находка №1: методологическая ошибка round42 — неверный путь

При проверке обнаружено: реальные каталоги зумов в GWC называются с
**ведущим нулём** (`EPSG_900913_08`, `EPSG_900913_09`, ...,
`EPSG_900913_15`), а не `EPSG_900913_9` без нуля. В round42 все команды
проверки z9 (`find .../EPSG_900913_9 -type f`) обращались к
**несуществующему пути** — отсюда стабильный, воспроизводимый "0 файлов
всегда", который был неверно истолкован как структурный дефект засева
z9. При правильном пути (`EPSG_900913_09`) на момент начала round43
на диске обнаружено 28 файлов z9 для `fields_latest` — ровно столько,
сколько показывает расчёт (см. ниже) — тайлы там были всё это время.

### Находка №2: полное совпадение расчёта и факта на z10-z12

| Слой | Зум | Ожидалось (`tile_math.py`) | Записано на диске | Разница |
|---|---|---|---|---|
| `fields_latest` | z9 | 28 | 28 (после переисследования пути) | 0 |
| `fields_latest` | z10 | 91 | 91 | **0** |
| `fields_latest` | z11 | 364 | 364 | **0** |
| `fields_latest` | z12 | 1352 | 1352 | **0** |
| `image_assessment` | z9 | 32 | 0 (см. объяснение ниже) | 32 |
| `image_assessment` | z10 | 98 | 98 | **0** |
| `image_assessment` | z11 | 378 | 378 | **0** |
| `image_assessment` | z12 | 1484 | 1484 | **0** |

Границы слоёв (EPSG:3857, использованы в расчёте):
- `fields_latest`: `[2943630.171387046, 7328833.515549753, 3441209.40858, 7579346.677623108]`
- `image_assessment`: `[2942825.5889792857, 7321138.569154181, 3443946.7464169012, 7583470.450228905]`

**round42's вывод "z12 недосеян на ~7% (1352 против ожидаемых
~1456)" был неверен** — "1456" получалось наивной эвристикой "91×4×4"
(округлением до степени двойки квадродерева), не реальной геометрией
bbox. Настоящий bbox — прямоугольник, не квадрат и не выровнен по
границам тайлов на грубых зумах, поэтому рост числа тайлов между
уровнями НЕ обязан быть ровно ×4 — 1352 является точным, а не
приближённым результатом.

`image_assessment` z9 = 0 файлов объясняется отдельно (не тем же
механизмом, что z10-z12): в текущей конфигурации (`GWC_SEED_ZOOM_START=10`)
z9 в засев вообще не входит; 28 файлов `fields_latest` на z9,
обнаруженные в начале round43, — след **более ранних** тестов round42
(до применения `GWC_SEED_ZOOM_START=10`), где z9 засевался explicitly.
`image_assessment` z9, по всей видимости, не получил ни одного
органического запроса на этом зуме за прошедшее время (растровый слой
включается пользователем отдельной кнопкой, обычно уже на более
крупном зуме) — то есть отсутствие тайлов там не про "недосев", а про
"эта зона сетки ещё ни разу не запрашивалась", что штатно (тайл
рендерится по требованию).

### Находка №3 (решающая): расхождение — не в файлах, а в отчёте GWC о прогрессе

Чистый тест (truncate `fields_latest` → seed z10-z12 → опрос каждые 5с
одновременно (а) числа файлов на диске и (б) статуса задачи через REST):

```
5с   files_on_disk=1807  gwc_active=[[1040,2096,...],[1024,2096,...]]  (~49% по репортёру)
10с  files_on_disk=1807  gwc_active=ERR (JSON-парсинг сломался на статусе)
...  files_on_disk=1807  (без изменений) — вплоть до 203с (конец теста)
```

**1807 = 91+364+1352 — точно полный ожидаемый набор для z10-z12,
записанный на диск уже к 5-й секунде.** Внутренний счётчик прогресса
GWC (`long-array-array`) в этот момент показывал лишь ~49% (`done/total`
по одному из потоков), при этом реальная работа (запись блобов на
диск) была уже полностью завершена. После первого опроса REST-статус
вовсе перестал корректно отвечать (`JSONDecodeError`) — отдельная,
не связанная с завершённостью засева, проблема самого REST-эндпоинта
статуса под этой нагрузкой (не влияет на результат — тайлы уже
записаны).

**Вывод**: несовпадение `tilesTotal`/`done` в отчёте GWC с реальным
числом тайлов — известная категория проблем этого GWC (см. round36:
там была найдена и исправлена похожая ошибка подсчёта, где каждый
поток репортил одно и то же `tilesTotal`). round42's "засев не
укладывается в 420с и не доходит до 100%" описывало **не отставание
записи файлов**, а **неполноту/некорректность self-reported прогресса
GWC**, из-за которой `deliver.py` ждал полные 420с, хотя вся полезная
работа заканчивалась за 5-90 секунд.

### Однозначный вывод блока A

**Это норма, не дефект.** Тайлы записываются полностью и корректно,
без потерь, в разы быстрее заявленного таймаута. Правки в
`docs/system-state.md`:
- раздел 7: убрана формулировка о "детерминированной остановке записи,
  root cause не установлен" — заменена на констатацию нормального
  поведения с указанием настоящей причины долгого ожидания (расхождение
  отчёта прогресса GWC, не потеря данных).
- раздел 8: убран пункт "полный root cause недосева GWC-кэша требует
  декомпиляции" — причина найдена без декомпиляции, тремя быстрыми
  проверками, как и предполагало ТЗ.

Пункт 2 ТЗ (пустые тайлы) отдельно не потребовался — полное числовое
совпадение факта с расчётом уже само по себе исключает версию
"тайлы пропущены/не сохранены", независимо от того, сохраняет ли GWC
пустые тайлы как отдельные файлы или нет.

## Блок C. Прослеживаемость версии программы

### Выбор и обоснование

Два варианта из ТЗ: (а) установить `git` в образ ETL, (б) передавать
хеш коммита при сборке образа через build-arg + переменную окружения.
**Выбран (б)**: не тянуть системную зависимость (`git` + метаданные
`.git/`) в runtime-образ ради однократного вызова на этапе сборки;
build-arg фиксирует коммит РОВНО на момент сборки образа — надёжнее
рантайм-вызова `git rev-parse` внутри контейнера, значение которого
зависело бы от того, что в этот момент лежит в смонтированной
директории (может разойтись с тем, чем образ был собран, если
чекаут на хосте уехал вперёد, а старый образ продолжает работать).

### Реализация

- `PIKURR/Dockerfile`: `ARG ETL_GIT_COMMIT=unknown` + `ENV ETL_GIT_COMMIT=${ETL_GIT_COMMIT}`.
- `/home/user/pikurr-system/docker-compose.yml` (стенд): в `etl.build` добавлен блок `args: {ETL_GIT_COMMIT: "${ETL_GIT_COMMIT:-unknown}"}` — читает переменную окружения ХОСТА при сборке (`docker compose build`), с дефолтом `unknown`, если не задана.
- `PIKURR/src/tasks/package.py`, `_git_commit()`: сначала читает `ETL_GIT_COMMIT` из окружения контейнера (то самое, запечённое в образ), при его отсутствии — резервный путь, прежний `git rev-parse HEAD` (для локального запуска вне контейнера, где `git` есть).
- Команда сборки: `ETL_GIT_COMMIT=$(git rev-parse HEAD) docker compose build etl`, затем `docker compose up -d --force-recreate etl` (обязательно — `restart`/пересборка образа без force-recreate не заставляют контейнер подхватить новый образ, известная ловушка round32).

### Находка в процессе внедрения: чекаут ETL на стенде расходится с репозиторием сильнее, чем документировано

При применении правки обнаружено: `/home/user/pikurr-system` на стенде
(где реально собирается `pikurr-system-etl-1`) — тот же git-репозиторий
(`origin` совпадает), но `git log` там застрял на **round30**
(`a2f92aeca073cdae71ea0ffc9844babb97f6ce92`), при этом рабочее дерево
вручную донесено до состояния, эквивалентного round42 репозитория
(включая манифест v2.1 из round38, полностью совпадающий текст
`_git_commit()` до этой правки) — как несохранённые изменения
(`git status` показывает файлы модифицированными, не закоммиченными).
Это тот же класс проблемы, что CLAUDE.md уже фиксировал ("стенд git
отстал от репозитория", round38), но выяснилось, что расхождение
глубже одного раунда — фактически десятки раундов разницы в истории
при почти идентичном рабочем дереве. Правка round43
(`_git_commit`/`Dockerfile`) применена тем же способом — прямой правкой
файлов на стенде (не через `git pull`, чтобы не спровоцировать
конфликт с уже накопленными несохранёнными изменениями), с бэкапами
(`docker-compose.yml.bak_pre_round43_*`).

**Практическое следствие**: `git rev-parse HEAD` на стенде возвращает
коммит round30, а не реальное состояние кода (которое правильнее было
бы отсчитывать от репозитория на координаторской машине, доведённого
до round43). Механизм передачи хеша в манифест реализован и работает
корректно — но **значение, которое он в данный момент передаёт,
указывает не на настоящую версию кода**, а на устаревшую точку git-
истории стенда. Это не дефект реализации block C, а следствие отдельной,
уже известной и не входящей в объём этого раунда проблемы (рассинхрон
git на стенде) — честно вынесено в `system-state.md`, раздел 7, как
открытое ограничение.

### Проверка фактом (пункт 2 ТЗ)

```
ssh 192.168.251.190 'cd /home/user/pikurr-system && git rev-parse HEAD'
→ a2f92aeca073cdae71ea0ffc9844babb97f6ce92

docker exec pikurr-system-etl-1 printenv ETL_GIT_COMMIT
→ a2f92aeca073cdae71ea0ffc9844babb97f6ce92

# После пересборки образа (--force-recreate) и сборки тестового пакета:
manifest.json → "etl_git_commit": "a2f92aeca073cdae71ea0ffc9844babb97f6ce92"
```

**Значение манифеста, `git rev-parse HEAD` на стенде и `ETL_GIT_COMMIT`
внутри контейнера — совпадают в точности.** Механизм подтверждён
фактом ровно так, как требует пункт 2 ТЗ. `etl_git_commit` больше не
`null` ни при одной сборке образа с явно переданным build-arg.

### Итог блока C

Сделано и проверено: манифест несёт непустой, воспроизводимый git-хеш.
Правки внесены как в координаторский репозиторий (`PIKURR/Dockerfile`,
`PIKURR/src/tasks/package.py`), так и напрямую в рабочий чекаут на
стенде (тот же файл, идентичная правка, с бэкапами) — иначе сборка на
стенде продолжала бы использовать старую версию `_git_commit()` до
следующей (неопределённо когда случающейся) синхронизации. Честно
зафиксирован остаточный, не входящий в объём этого блока факт: сам
git-хеш стенда сейчас не отражает реальную версию кода — это ограничение
уже существовавшей проблемы (рассинхрон истории), не новой.

Откат: убрать `ARG`/`ENV` из `Dockerfile`, убрать `args:` из
`docker-compose.yml` (бэкап — `docker-compose.yml.bak_pre_round43_*`
на стенде), вернуть прежнюю версию `_git_commit()` в `package.py`.

### Реализация (пункт 2 ТЗ)

`REPIKURR/backup_config_offsite.sh` — запускается с машины, у которой
уже есть рабочий SSH-доступ к VPS (координаторская; **прямого SSH
стенд↔VPS нет**, проверено фактом — `Permission denied (publickey)` в
обе стороны, установка нового доверия ключей — отдельное решение по
безопасности, не в этом раунде). Два раздельных архива:
- `config_<таймстамп>.tar.gz` — `geoserver_data/gwc/*.xml`,
  `geoserver_data/gwc-layers/*.xml` (не секрет).
- `secrets_<таймстамп>.tar.gz` — `geoserver_data/security/**`,
  `deliver.env`, `.env` (права 600 сразу после скачивания, никогда не в
  git — `config_backups_offsite/` добавлен в `.gitignore`).

Ротация — по числу файлов (по умолчанию 10, как `REPIKURR/backups/` для
БД). Флаг `--restore-config-to <dir>` — распаковка последнего
config-архива для проверки/восстановления.

Оба архива реально собраны и скачаны при подготовке этого блока:
`config_backups_offsite/config_20260928_115713.tar.gz` (1.4 КБ, 4
файла), `config_backups_offsite/secrets_20260928_115713.tar.gz` (7.4
КБ, права 600, 50 файлов внутри дерева `security/` + `deliver.env` +
`.env`).

**Не реализовано в этом раунде**: автоматический запуск по расписанию
(systemd timer). Причина — единственная подходящая для расписания
машина (стенд, всегда включён) не имеет прямого SSH до VPS; ставить
timer на координаторскую машину (эта сессия Claude Code) бессмысленно
— она не работает непрерывно. Решение (заводить ли SSH-ключ стенд→VPS
специально под этот бэкап, с каким скоупом прав) — оставлено
пользователю, задокументировано как открытый вопрос
(`system-state.md`, раздел 8). Скрипт готов к вызову и вручную, и из
любого будущего расписания.
