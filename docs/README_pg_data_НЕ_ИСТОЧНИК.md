# `outputs/pg_data/` — НЕ источник для сборки боевых пакетов

(Файл лежит в `docs/`, а не в `outputs/pg_data/` — том владеет процесс
Postgres внутри контейнера, запись внутрь снаружи недоступна без root;
`outputs/` вдобавок не отслеживается git — см. `.gitignore`.)

**Контейнер**: `pikurr_refactor-db-1` (`docker-compose.yml` в корне
`PIKURR_REFACTOR`, том — `outputs/pg_data`).
**Остановлен вручную в round39** (2026-09-25) и должен оставаться
остановленным, если явно не понадобится для отладки.

## Что внутри и почему это опасно

Разбор round38 (`docs/round38-data-incident.md`) установил, что эта
база содержит **слипшиеся вместе фрагменты минимум трёх независимых
прогонов ETL**, не единый срез на дату:

| Год  | Строк  | `assessment.updated_at`         |
|------|--------|----------------------------------|
| 2023 | 316    | 2026-04-16 10:48:40 (единая метка) |
| 2024 | 72001  | 2026-04-16 10:48:40 (та же метка)  |
| 2025 | 3844   | 2026-01-22 — 2026-01-27 (СТАРШЕ 2024!) |

Round37 поднял этот контейнер (был остановлен) и собрал из него пакет
`pikurr_update_2024_2025_2026-09-24_09-41.zip` **без проверки
содержимого** — пакет доставлен на прод, витрина получила три года
вместо ожидаемого одного текущего 2025. Round38 разобрал инцидент и
восстановил данные; round39 остановил этот контейнер и написал этот
файл, чтобы это не повторилось молча ещё раз.

## Единственный правильный источник боевых пакетов

**`pikurr-system-db-1`** на стенде `192.168.251.190`
(`~/pikurr-system`, роль ETL) — работает постоянно, не поднимается
специально под сборку, содержит только актуальный текущий год. См.
`CLAUDE.md`, раздел "Ловушки" (запись round38/39 про непроверенные
локальные ETL-базы).

## Если всё-таки нужно поднять эту базу (отладка, эксперимент)

Данные НЕ удалены — только контейнер остановлен, том цел. Перед тем,
как поднимать:
1. Понимать, что внутри — три разновозрастных снимка, не текущее
   состояние ETL.
2. **Никогда** не собирать из неё пакет для доставки на прод/VPS —
   ни напрямую, ни "на скорую руку для теста", если тест-пакет может
   случайно попасть в `inbox` реального сервера.
3. После использования — снова `docker stop pikurr_refactor-db-1`.
