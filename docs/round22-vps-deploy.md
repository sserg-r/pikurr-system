## Задача 7. Канал доставки — сделано, со сложной отладкой

- отдельный пользователь `pikurr_delivery` (группа `pikurr-delivery`,
  `sgr` — вторичный член для доступа к `inbox/`), shell `/bin/bash`
  (`/usr/sbin/nologin` **блокирует форс-команду тоже**, не только
  интерактивный вход — это отдельная находка: безопасность даёт
  `command=`, не тип шелла);
- диспетчер `/home/pikurr_delivery/bin/dispatch.sh` — пропускает ровно
  `rsync --server...` (через `rrsync -wo`, ограничено `inbox/`) и `cat
  .../status/pikurr_update_*.zip.json` (с проверкой через `realpath`,
  так как `case`-маска с `*` в bash не останавливается на `/` и формально
  пропустила бы путь с `../` — защита не в самой маске, а в канонизации
  пути);
- `known_hosts` с зафиксированным отпечатком (`ssh-keyscan`, сверен при
  первом подключении) вместо `StrictHostKeyChecking=no`;
- `push.py`: `DELIVERY_KNOWN_HOSTS`, `DELIVERY_STATUS_DIR` (status/ у
  ограниченного пользователя доставки не сосед `inbox/` — другое дерево
  каталогов), пустой `DELIVERY_INBOX` для канала через `rrsync` (путь
  назначения фиксирован на сервере, клиентский путь создаёт вложенный
  подкаталог — проверено фактом);
- `.env` ETL-контура на `192.168.251.190` обновлён: новые
  `DELIVERY_HOST/USER/SSH_KEY`, `DELIVERY_STATUS_DIR`, `DELIVERY_KNOWN_HOSTS`;
  старый ключ `id_rsa` (для локального стенда на себя) не тронут — новый
  ключ смонтирован отдельным путём в контейнер `etl`.

### Найденные и исправленные дефекты при отладке сквозной доставки

1. **Латентный баг дублирования `ogr2ogr` в аргументах** (существовал с
   раунда 19-20, никогда не проявлялся на `192.168.251.190`, так как там
   `ogr2ogr` не было на хосте и код всегда шёл через `docker exec`). На VPS
   я поставил `gdal-bin` прямо на хост (чтобы не тащить зависимость от
   `docker`, в духе A3 раунда 21) — и код собирал команду
   `ogr_prefix + ["ogr2ogr", "-f", ...]`, что при `ogr_prefix=["ogr2ogr"]`
   давало `ogr2ogr ogr2ogr -f PostgreSQL ...` — GDAL трактовал второй
   `"ogr2ogr"` как имя **выходного** датасета и пытался создать БД с таким
   именем, откуда загадочная (и не связанная по смыслу с реальной причиной)
   ошибка `"PostgreSQL driver doesn't currently support database
   creation"`. Воспроизводилось на 100% пяти отдельных прогонов подряд.
   Исправлено: `_ogr2ogr_cmd()` теперь сам включает `"ogr2ogr"` в префикс
   (для обоих вариантов — хост и `docker exec`), вызывающий код больше не
   дублирует.
2. **Права на `/home/sgr`**: каталог `750`, `pikurr_delivery` не входил в
   группу `sgr` — не мог даже пройти внутрь, чтобы прочитать
   `status/*.json`, хотя сам файл статуса и вложенные каталоги были
   открыты. `PushTask` из-за этого не мог получить подтверждение и уходил
   в ожидание до таймаута молча (без явной ошибки — просто "статус не
   появился"). Исправлено точечно: `chmod o+x /home/sgr` (только проход,
   не листинг).
3. **Первая доставка на пустую БД**: GeoServer до появления
   `assessment_ready` (создаётся только после первого успешного импорта)
   агрессивно (тысячи запросов/сек) опрашивал несуществующее view,
   насыщая соединения к PostGIS в момент, когда `import_vectors()` пытался
   подключиться. Это одноразовая проблема **только для самой первой
   доставки на чистый инстанс** — на 192.168.251.190 такого не было, там
   `assessment_ready` существовало с раунда 16. Разово создал
   заглушки-view той же структуры вручную (с вашего разрешения), чтобы
   разорвать цикл — дальше проблема не повторялась.

**Проверка по содержимому — подтверждена полностью, включая финальный
чистый прогон через сам `PushTask`** (не только вручную вызванный

# Дополнение: инцидент после развёртывания — пустая карта, 503

Обнаружено пользователем сразу после развёртывания: в браузере на
`https://geobotany.of.by` — пустая оболочка, только публичные подложки,
данных с GeoServer нет; отдельно — нестабильные ошибки 503. Разбор в
несколько шагов, с находками на каждом.

## Шаг 1. Ресурсы ВМ — RAM поднята пользователем до 6 ГБ

Первичная гипотеза — нехватка памяти. Пользователь поднял RAM ВМ 4→6 ГБ. Но
`docker stats` в момент проверки показал: **PostGIS — 94.47% от лимита
`mem_limit: 768m`** (лимиты в `docker-compose.vps.yml` были захардкожены под
старые 4 ГБ и не растут сами при апгрейде ВМ). Одновременно `iostat`
показал `w_await ~105мс` (много для SSD) и `load average 8.23` при 2 vCPU —
реальный узкий момент был скорее в диске, чем в RAM конкретно, но лимиты
всё равно стоило поднять, раз память появилась.

**Сделано**: `mem_limit` — postgis 768m→1536m, geoserver 2g→3g;
`shared_buffers` 256MB→512MB, `work_mem` 16MB→32MB, `effective_cache_size`
512MB→1GB; `MAXIMUM_MEMORY` (JVM) 1536M→2048M. Деплой (`docker compose up
-d`, пересоздал оба контейнера), проверено `docker stats` — комфортный
запас после. Серия из 8 подряд WMS-запросов — все `200`, 0.5-2.2с, без
единого сбоя (раньше — нестабильно, `HTTP 000`/таймауты вперемешку с
быстрыми ответами).

## Шаг 2. Найдена настоящая причина — медленный SQL в `assessment_ready`

Более тяжёлый тест (широкий bbox, полный WFS-запрос `pikurr:fields` — тот
самый, что фронтенд вызывает при загрузке для списка годов/районов,
`loadYearDistrictData()`) показал **12-14 секунд** на запрос — именно это,
вероятнее всего, и есть причина «пустой оболочки»: если у браузера или
Caddy таймаут короче, критичный для инициализации фронтенда запрос просто
не успевает.

`EXPLAIN ANALYZE SELECT * FROM assessment_ready` показал: подзапрос
`SELECT SUM(val) FROM jsonb_each_text(stats)` (знаменатель доли
леса/кустарника в `create_assessment_schema.sql`) выполнялся **~108 тысяч
раз** (дважды на каждую из 55784 строк) — 7.6с чистого времени SQL.

**Согласовано с пользователем и исправлено**: заменил динамический перебор
всех ключей JSON на явную сумму 6 известных классов (0-5, документированы
ещё в раунде 17) через `COALESCE`. Семантика не изменилась — `stats` всегда
содержит только эти ключи. Применено на боевой БД VPS немедленно
(`CREATE OR REPLACE VIEW`) и синхронизировано в `PIKURR/src/sqlscripts/create_assessment_schema.sql`
(активная копия — подтверждено через `settings.paths.sqlscripts`; вторая,
устаревшая копия в `PIKURR/sqlscripts/` не используется, не трогал), чтобы
попало в будущие доставки.

**Результат**: `EXPLAIN ANALYZE` — 7.6с → без нового замера ещё оставалось
~7.5с (см. шаг 3), подзапросы `jsonb_each_text` — «never executed» в плане,
подтверждено.

## Шаг 3. Вторая, отдельная причина — `ST_Area(geom::geography)` и слабый CPU ВМ

После шага 2 полный `SELECT * FROM assessment_ready` всё ещё занимал ~7.5с.
Изолировал: `ST_Area(a.geom::geography)` (геодезическая площадь поля для
`area_ha`) сама по себе добавляла **~4.8с** на 55784 строках.

**Ключевая находка по прямому запросу пользователя** — сравнил тот же
изолированный запрос на `192.168.251.190` (тот же датасет, 59209 строк):

| | `ST_Area(geom::geography)`, весь датасет |
|---|---|
| 192.168.251.190 | **0.98с** |
| VPS (`geobotany.of.by`) | **5.47с** |

**Разница ~5.6×** на идентичных данных и идентичной операции — процессор
этой прерываемой ВМ (2 vCPU, гарантированная доля 50%) заметно слабее на
CPU-интенсивных вычислениях, чем локальный сервер, даже при похожих
формальных лимитах памяти/дисков. Это подтверждает то, что пользователь
подозревал заранее («на локальном сервере с приблизительно теми же
ограничениями по ресурсам таких задержек нет») — задержка была не только от
неэффективного SQL (шаг 2), но и от объективно слабее CPU конкретно на этой
операции.

**Проверка альтернативы перед правкой**: в `agrifields` уже есть готовое
поле `shape_area` (из исходного файла), которое **не требует вычисления
геометрии заново**. Сравнил его с точным геодезическим расчётом на всех
59209 строках:

- средняя относительная погрешность — **0.026%**;
- всего 1 строка (`nr_user=22490000030364`) с большим отклонением
  (~93-108%) — единичный дефект исходных данных этого поля, не аргумент
  против метода;
- все остальные строки — стабильно ~0.086% (систематическая, предсказуемая
  мелкая разница, не случайный шум).

**Согласовано с пользователем и исправлено**: `area_ha` теперь считается из
`shape_area / 10000`, не `ST_Area(geom::geography) / 10000`. Применено на
боевой БД (та же процедура, `CREATE OR REPLACE VIEW`) и синхронизировано в
исходный SQL-файл.

**Результат**: `EXPLAIN ANALYZE SELECT * FROM assessment_ready` —
**7.6с → 2.28с** (после обоих исправлений, серверное время выполнения SQL).

## Шаг 4. Остаточное узкое место — не исправлено, описано, ждёт решения

Несмотря на падение SQL-времени в 3+ раза, сам WFS-эндпоинт (через
публичный домен, тот самый запрос фронтенда) всё ещё отдаёт **~12 секунд**.
Причина — не в SQL: `pikurr:fields` — GeoServer "virtual table" с
**фиксированной** SQL-строкой `SELECT * FROM assessment_ready` (без
push-down проекции колонок). Даже когда фронтенд просит только `year,
nr_user` через `propertyName`, GeoServer сначала тянет **все** колонки
(включая геометрию каждого из 55784 полей) через JDBC, и только потом
отбирает нужные два свойства на своей стороне — тяжёлая передача данных
происходит независимо от того, что реально нужно клиенту.

Дальнейшее ускорение требует отдельного, облегчённого virtual table/слоя
специально под этот запрос (без геометрии, `bzdz`, `valuation` — только
`year, nr_user`) — это уже правка конфигурации слоя GeoServer, отдельная
от SQL-схемы. **Не сделано, ждёт решения** — предложено пользователю,
ответ на момент этого отчёта не получен.
