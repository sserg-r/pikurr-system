## Блок A. Корректность

### A1. Годы — скрытая ошибка в статистике — **подтверждено и исправлено**

**Факт**: `pikurr:fields` (все годы, без фильтра года) и
`pikurr:fields_latest` дают СЕЙЧАС идентичные числа:
```
fields (все годы) nr_user=2212000055%: 1     fields_latest: 1
fields (все годы) district=2212:      9039  fields_latest: 9039
distinct years в fields для района 2212: {2025}
```
Единственная причина совпадения — на проде один год. Реального стенда
с двумя годами не нашлось (эмулятор `192.168.251.190` тоже с одним
годом на момент проверки) — прямая демонстрация задвоения через
реальные данные не выполнена, сказано прямо, как и просило ТЗ (A1.1,
запасной вариант).

**Исправление** (единая точка построения фильтров, `pikurr.py::_build_filters()`):
- год не выбран ("последние данные") → `typeName=pikurr:fields_latest`,
  без условия года;
- выбран год → `typeName=pikurr:fields`, `year = <год> AND <группа>`.
  Применено ко всем трём запросам (слой, `vec:Bounds`, `vec:Aggregate`)
  — раньше все три были независимыми копиями логики и могли разойтись
  молча.

**Находка при сверке с витриной** (важно для будущих раундов):
собственные WPS-шаблоны витрины (`REPIKURR/repikurr/public/
getstatsbyuser.xml`, `getbboxbyuser.xml`) **вообще не фильтруют по
году** — используют `pikurr:fields` без условия года, в отличие от
слоя карты (`App.jsx`, `vectorTypeName`), который год учитывает. Это
означает, что при появлении второго года **сама витрина** будет
считать статистику/границы по ВСЕМ годам, а не по выбранному — отдельный,
пока не проявившийся баг фронтенда, вне объёма этого раунда (плагин
не трогает исходники фронтенда). Приёмка A1.3 ("сверять с запросом
витрины") выполнена буквально для слоя карты; для статистики/границ
плагин сделан СТРОЖЕ витрины (сознательно, по прямой инструкции ТЗ),
что при появлении второго года даст плагину и витрине РАЗНЫЕ числа —
зафиксировано как открытый вопрос для будущего раунда, не для этого.

Проверено фактом (headless, E2E-тест): эталон 2212000055 —
1 объект/5.6 га/tillage читается из виджета таблицы, «Весь район»
2212 — 9039/84731.8 га, совпадает с независимым WFS-запросом.

### A2. «Весь район» — **подтверждено и исправлено**

**Факт по всем районам с данными на проде**:
```
2212: nr_user-префикс "2212%" = 9039, district='2212' = 9039 (совпадает)
2208: nr_user-префикс = 15936, district='2208' = 15936 (совпадает)
2255, 6204: оба способа дают 0 (нет данных)
```
Проверка distinct 5-символьных префиксов кодов землепользователей
района 2212 — единственный вариант `22120` на все 9039 записей.
**Сегодня расхождений нет**, но способ (`usids[0][:5]`) структурно не
гарантирован — он предполагает, что 5-й символ кода ВСЕГДА один и тот
же для всего района, что нигде не проверяется и не является частью
схемы данных.

**Исправление**: фильтр «Весь район» — `district = '<код>'` (атрибут,
не префикс кода). Проверено фактом: E2E-тест сверяет "Весь район 2212"
через сам плагин с независимым прямым WFS-запросом — совпадение
9039 объектов / 84731.8 га в обоих случаях.

### A3. Проверка доступности сервера — **подтверждено и исправлено**

**Факт**: `curl https://geobotany.of.by/geoserver` (без слэша, старый
код) —
```
200, Content-Type: (см. вывод curl) — тело не WPS/WMS, а фронтенд
```
подтверждено отдельно: `/geoserver` (200), `/geoserver/` (302),
`/geoserver/web/` (401 — за basic auth), `/geoserver/wps` (200,
реальный WPS). Старая проверка (`{url}/geoserver`, без слэша) технически
получала 200 и на боевом сервере, и на любом чужом SPA-сайте — не
могла отличить эти случаи.

**Исправление**: `check_service_availability()` теперь шлёт POST
`WPS GetCapabilities` на `{url}/geoserver/wps` (тот же путь, что все
рабочие запросы плагина), разбирает XML, проверяет корневой элемент
`Capabilities` и наличие всех трёх процессов (`gs:Query`,
`vec:Aggregate`, `vec:Bounds`).

Три сценария проверены фактом (headless, реальные адреса):
```
1. прод:                    (True, '... -> WPS Capabilities, все процессы на месте')
2. не-GeoServer адрес:       (False, '... недоступен: ... Method Not Allowed')
3. недоступный адрес:        (False, '... недоступен: Отказано в соединении')
```
Случай 2 на практике дал `405` (Caddy отвечает `Method Not Allowed`
на несопоставленный POST-путь), а не буквально "200 + HTML" — тоже
корректно распознан как "недоступен/не туда", просто через другую
ветку кода (сетевая ошибка, не парсинг XML). Три разных, осмысленных
сообщения — критерий A3.4 выполнен.

**A3.3, POST через `http://`**: подтверждено `curl -sv -L` —
`308 Permanent Redirect` → `Location: https://...` → `200` с валидным
телом `WPS Capabilities` (308 обязан сохранять метод POST по стандарту
HTTP, что и подтвердилось). Отдельно проверено через саму
`QgsBlockingNetworkRequest`: `check_service_availability('http://
geobotany.of.by')` → `(True, ...)` — редирект пройден прозрачно тем же
кодом, что и HTTPS.

### A4. Сетевой стек — **подтверждено и исправлено**

Весь сетевой код (`geoserver_client.py`) переведён на
`QgsBlockingNetworkRequest` (`_blocking_get`/`_blocking_post`) —
сетевой стек самого QGIS (`QgsNetworkAccessManager`), не `requests`.

Приёмка:
```
grep -rn "import requests" pikurr_qgis --include=*.py
  -> только в pikurr_qgis/tests/*.py (test_headless.py,
     test_plugin_e2e.py, measure_speed*.py — тестовый/замерочный код,
     не рантайм плагина)
```
Headless-тест блока D — 10/10 PASS на этом стеке.

**A4.3, проверка с реальным прокси**: не выполнена. Попытка
подтвердить через `QSettings` (`proxy/proxyEnabled` и т.д.) с заведомо
нерабочим портом не дала эффекта — запрос всё равно прошёл напрямую,
похоже, ключи `QSettings` для прокси либо называются иначе, либо
`QgsNetworkAccessManager.setupDefaultProxyAndCache()` требует
дополнительного шага, который не удалось подобрать в разумное время.
Сказано прямо, как просило ТЗ (A4.3, запасной вариант) — сам факт
использования `QgsBlockingNetworkRequest` остаётся документированно
корректным способом (это стандартная рекомендация QGIS для сетевого
кода плагинов), но эмпирически с реальным прокси не подтверждён.

### A5. Границы объекта одним запросом — **подтверждено и исправлено**

**Факт формата ответа `vec:Bounds`** (без `mimeType`, значит не JSON):
```
<?xml version="1.0" encoding="UTF-8"?><ows:BoundingBox ... crs="EPSG:4326">
  <ows:LowerCorner>30.552... 55.380...</ows:LowerCorner>
  <ows:UpperCorner>30.556... 55.383...</ows:UpperCorner>
</ows:BoundingBox>
```
Раньше код заведомо пробовал JSON-путь (провал гарантирован — ответ не
JSON), затем делал второй сырой запрос. Новая функция
`geoserver_client.wps_execute_raw()` — один запрос, сразу разбор как
GML/XML (тот же формат, что подтверждён фактом выше).

Проверено фактом (E2E-тест): зум карты к границам объекта отработал
(`_update_bounds`), панель осталась рабочей; отдельная сверка «граница
`vec:Bounds` == граница прямого WFS» отдельным числовым тестом не
делалась (ушла бы за пределы разумного времени этого раунда) —
косвенно граница уже проверяется тем, что таблица площадей и bbox
строятся по одному и тому же фильтру записей, сверенному в A2/A1
независимым WFS-запросом.

## Блок B2. Скорость — правки по результату замера

### Применено

1. **EPSG:3857 вместо CRS:84** (оба WMS-слоя) — устраняет
   перепроецирование на клиенте. Витрина всегда запрашивала целевую
   проекцию сразу — приведено к тому же.
2. **AI-оценка через WMTS/GWC**, сетка `EPSG:900913`, НЕ XYZ (явное
   предостережение ТЗ про round46-мину). Headless проверено:
   `isValid=True`, принудительный `provider.block()` — `isValid=True,
   error=''`, и **реальный HTTP-заголовок** `geowebcache-cache-result:
   HIT` при прямом запросе того же тайла через WMTS GetTile —
   подтверждает, что это действительно кэш GWC, не совпадение.
   Замер (3 повтора, тот же протокол, что B1):
   | | старый (WMS, CRS:84) | новый (WMTS/GWC, 3857) |
   |---|---|---|
   | охват района 2212, среднее | 1.177 с | 0.429 с |
   | охват землепользователя, среднее | 0.710 с | 0.363 с |
   Оба — 100% непрозрачных пикселей. **Видимость слоя в реальном GUI
   QGIS — не проверена мной** (round46: headless проходил, реальный
   GUI показывал пусто) — вынесено отдельным пунктом чеклиста E4.
3. **Списки — один раз за сеанс.** `refresh_data(force=False)`
   пропускает сеть, если данные уже загружены; кнопка «⟳» у списка
   годов — принудительное обновление. Замер:
   ```
   Открытие панели (force=True):        [0.916, 1.127, 0.904] с, среднее 0.982
   Повторное открытие (кэш, force=False): [0.0, 0.0, 0.0] с
   ```
   Полное устранение повторной сети — не оптимизация "быстрее", а
   "не платим дважды".

### Измерено, но НЕ применено (обоснование)

4. **Асинхронная сеть (`QgsTask`)** — не сделано. Синхронный
   `QgsBlockingNetworkRequest` по-прежнему блокирует событийный цикл
   QGIS на время сетевого вызова (~0.4-2.3с по замерам), панель как
   `QDockWidget` (C1) решает только проблему "нельзя работать с картой,
   пока открыт диалог" (модальность), не проблему "интерфейс замирает
   на время запроса". Перевод на `QgsTask` требует аккуратной
   потокобезопасности сетевого стека и отдельного тестирования — риск
   выше разумного объёма правки в этом раунде. Оставлено для будущего
   раунда, эффект ограничен (замирания по замеру — доли секунды -
   единицы секунд, не критично для однопользовательского десктоп-
   сценария).
5. **Подавление `GetCapabilities` при создании слоя** — не сделано.
   Замер (блок B1) показал, что это разовая цена за сеанс на объект
   слоя (~1-4с первый раз, ~0.09с далее), не за каждый клик — эффект
   правки был бы заметен только на самое первое открытие панели,
   несоразмерно риску (нестандартная инициализация провайдера).

### C2. Выбор — подтверждено

- Год: «последние данные» по умолчанию + список из

### C4. Таблица площадей — подтверждено
