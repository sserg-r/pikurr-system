# Round 36: почему встал засев, правильный диапазон зумов, прогрев без GWC-seed

ТЗ: `prompts/PROMPT_seeding_fix_round36.md`. Продолжение round35
(`docs/round35-seeding.md`, блок C2) — там был найден, но не объяснён
факт: внутренний засев GWC стабильно останавливался на ~50% заявленной
цели без ошибок в логах.

## Итог одной строкой

**Реального зависания не было.** Причина — баг в СОБСТВЕННОМ коде
`deliver.py` (не в GWC): при `threadCount=2` каждый поток репортит
ОДНО И ТО ЖЕ полное значение цели (`tilesTotal`), а прежний код эти
значения суммировал — искусственно удваивая цель и создавая ощущение
"дошло только до половины", хотя задача уже легитимно завершилась.
Засев включён по умолчанию (`GWC_SEED_ENABLED=true`).

## Блок A. Причина остановки — три гипотезы

Все опыты — на эмуляторе (`192.168.251.190`), 2 vCPU-потока засева,
слой `pikurr:image_assessment`, z9-14.

### A1. Квота — ОПРОВЕРГНУТА

Решающая проверка: квота диска поднята с 2 GiB до 8 GiB (прямой файл
`geoserver_data/gwc/geowebcache-diskquota.xml`, не REST — см. CLAUDE.md,
"Ловушки"; `docker compose restart geoserver`, подтверждено через
`GET /gwc/rest/diskquota.xml` → `<bytes>8589934592</bytes>`).

Засев на 8 GiB квоте: **остановился в ТОЙ ЖЕ ТОЧКЕ** — 29960 файлов,
78 474 012 байт (~74,85 MiB). Диск использован на 0,9% от 8 GiB — квота
физически не могла быть исчерпана. **Опровергнуто.**

Снимок каждые ~6с (полный лог — `размер/число файлов/CPU/статус задачи`
каждые 5с) показывает монотонный, равномерный рост числа файлов вплоть
до точки завершения, без плато перед остановкой:

```
t=0s    files=1709   cpu=314%
t=6s    files=3956   cpu=298%
...
t=92s   files=29960  cpu=4%     status: [[16128,32208,102,1,2],[16048,32208,0,2,2]]
t=99s   files=29960  cpu=0.3%   status: []   ← EMPTY_TASK_LIST
```

Пятый элемент статуса (код состояния задачи) перешёл `1→2` ровно в
момент остановки роста файлов — не `-1` (DEAD), а легитимный переход
в другое состояние (расшифровка — блок A2 ниже).

### A2. Отвалившаяся нить — ОПРОВЕРГНУТА

Коды состояния задачи расшифрованы фактом — декомпиляцией байткода GWC
1.24.2 прямо внутри контейнера `pikurr_srv_geoserver`
(`jar xf gwc-core-1.24.2.jar org/geowebcache/seed/GWCTask...` +
`javap -p -c`):

- `GWCTask.STATE`: `UNSET=0, READY=1, RUNNING=2, DONE=3, DEAD=4` (ordinal).
- `TileBreeder.stateCode(STATE)` — маппинг в то же число, что видно в
  REST-ответе: `READY/UNSET → 0`, `RUNNING → 1`, `DONE → 2`, `DEAD → -1`.

Значит, наблюдённый переход `1 → 2` — это **`RUNNING → DONE`**,
легитимное завершение, не `DEAD`. Ни разу за все прогоны round36 код
`-1` (DEAD) не встретился.

Дополнительно расшифрован `TileBreeder.getStatusList()`:
`long[5] = {tilesDone, tilesTotal, timeRemaining, taskId, stateCode}`
— и, что оказалось решающим, **`tilesTotal` берётся у каждой задачи
из `GWCTask.getTilesTotal()`, которая едина на задачу, не делится
между потоками**. При `threadCount=N` REST возвращает N строк
(по одной на поток), и **у ВСЕХ N строк одинаковый `tilesTotal`**.

Проверка с `threadCount=1`: тот же слой, тот же диапазон, один поток —
цель `32208` (одно число, без дублирования), итог **29960 файлов** —
тот же результат, что и с 2 потоками. `getStatusList()` вызывает
`drain()`, который физически убирает DONE/DEAD задачи из пула — пустой
список ПОСЛЕ завершения ожидаем и корректен, не "потеря" информации.

**Опровергнуто**: смерть потока не воспроизвелась ни разу (12/12
прогонов на эмуляторе + прогоны на VPS — везде чистое `RUNNING→DONE`).

### A3. Уборка квоты (`cacheCleanUpFrequency`) — ОПРОВЕРГНУТА (по касательной)

Отдельный эксперимент с отключением уборки не проводился — в этом нет
смысла: A1 уже показал, что при 8 GiB квоте (использовано <1%) уборке
физически нечего убирать, конкурировать не за что. Раз квота никогда
не приближалась к исчерпанию, гипотеза о конфликте с уборкой отпадает
автоматически.

### Настоящая причина (не входила в три гипотезы ТЗ)

`deliver.py` (round35, блок C2, функция `_seed_gwc_layer`) в цикле
опроса статуса делала:
```python
total = sum(t[1] for t in active)   # СУММА по потокам
```
При `threadCount=2` и едином `tilesTotal=32208` на каждый поток это
давало отображаемую цель `64416` — вдвое больше настоящей. Наблюдатель
(round35) видел на диске реальные ~29960 файлов против отображаемой
цели 64416 → `29960/64416 ≈ 46,5%` → "встало на полпути". На самом деле
прогресс к НАСТОЯЩЕЙ цели (32208, без задвоения) составлял
`29960/32208 ≈ 93%`, а сама задача была уже полностью завершена.

Исправлено (`deliver.py`, `_seed_gwc_layer`): `total = max(t[1] for t
in active)` — берётся представительное значение, не сумма; `done`
по-прежнему суммируется (это реальный, РАЗНЫЙ прогресс каждого
потока — суммирование здесь корректно).

## Блок B. Прогрев обычными HTTP-запросами

`REPIKURR/tools/gwc_http_seed.py` (новый) — строит список тайловых URL
по сетке GWC (через `tile_math.tile_range_for_bbox_3857`, см. блок D)
для заданного слоя/bbox/диапазона зумов, опрашивает тем же эндпоинтом,
что фронтенд (`/geoserver/gwc/service/wms&tiled=true`), N потоками.
Пишет NDJSON-лог по каждому ответу (код, размер, `geowebcache-cache-result`,
время), умеет продолжать с места остановки (`--resume`, читает уже
успешные записи из `--log`), завершается по `SIGINT`/`SIGTERM` без
потери прогресса. Критерий завершения — контрольный повторный проход
без `--resume`: доля `hit` в финальной JSON-сводке, а не факт "скрипт
закончился". Предупреждает, если доля мелких/пустых ответов (<2 КБ)
выше 20% (правило непустых тайлов, round32).

Проверен фактом на VPS (3 тайла z15-16, слой `pikurr:fields_latest`):
корректно построил список, получил 1 HIT + 2 MISS, посчитал сводку.

**Не сделано в этом раунде**: полноценное сравнение цены (время
прогрева HTTP-скриптом против внутреннего засева на одном диапазоне
зумов) — после того как блок A показал, что внутренний засев GWC
реально надёжен (просто неверно интерпретировался), приоритет полного
сравнения снизился. Скрипт остаётся в репозитории как независимый
способ прогрева "с видимостью каждого ответа" — пригодится, если
версия GWC или конфигурация изменится и внутренний засев снова начнёт
вести себя непрозрачно.

## Блок D. Расхождение расчёта и цели GWC

ТЗ предполагало "цель GWC вдвое больше расчёта" — по факту это
**два независимых, наложившихся друг на друга эффекта**:

1. **"Вдвое" — это баг блока A выше** (задвоение `tilesTotal` при
   суммировании по потокам в `deliver.py`), не свойство самого GWC.
   Исправлено там же.

2. **Меньший, отдельный эффект: цель GWC (по метатайлам) больше
   реального числа файлов на ~7,5%** (32208 против 29960 для
   image_assessment, z9-14). Причина установлена фактом:
   - GWC считает `tilesTotal` по сетке МЕТАТАЙЛОВ (`metaWidthHeight=4×4`,
     round34 C) — диапазон тайлов расширяется до границы метатайл-блока
     на краях, что добавляет "лишние" тайлы за пределами реальной bbox
     слоя.
   - В логах `pikurr_srv_geoserver` во время засева видны десятки
     `ServiceExceptionReport` (`SE_XML`) с `GWC_SEED_INTERCEPT=true` —
     это именно краевые метатайлы, полностью выходящие за bbox слоя;
     GeoServer отвечает исключением, GWC засчитывает метатайл как
     обработанный (`tilesDone` растёт), но файл на диск не пишет.
   - Независимый пересчёт (`tile_math.tile_range_for_bbox_3857`,
     точная bbox без снаппинга) даёт **29960** — совпадает с реальным
     числом файлов на диске в 100% прогонов (12/12 на эмуляторе).
     Пересчёт с ручным снаппингом на границу метатайл-сетки даёт
     **32208** — совпадает с целью GWC.

`tile_math.py` (round35) дополнен функцией `tile_range_for_bbox_3857()`
— диапазон тайлов, пересекающих bbox, на заданном зуме. Попутно найден
и исправлен тонкий баг с плавающей точкой: на координатах, почти точно
совпадающих с границей тайла (что для реальных bbox — обычный случай,
т.к. bbox слоя сам является объединением целых тайлов), `int(x //
tile_size)` и `math.floor(x / tile_size)` дают РАЗНЫЙ результат
(off-by-one) из-за разных путей округления double. Сверка с реальным
числом файлов на диске подтвердила верным `math.floor(x / tile_size)` —
используется он; self-check (20/20 точек round32) по-прежнему проходит.

## Блок E. Внедрение

Критерий ТЗ выполнен: прогрев устойчиво доходит до цели и проверяется
по содержимому — не только по факту опустения списка задач GWC, но и:
- по совпадению итогового числа файлов на диске с независимым расчётом
  (`tile_math`) в 12/12 прогонов на эмуляторе (все 4 диапазона × 3
  повтора) и во всех прогонах на VPS;
- по `HIT` на контрольных заведомо непустых тайлах
  (`docs/round32_assets/tiles_with_data.json`) после засева — проверено
  и на эмуляторе, и на VPS.

**Сделано**:
1. `deliver.py`: исправлен баг суммирования `tilesTotal` (блок A),
   добавлено логирование последнего известного прогресса перед
   опустением списка задач (диагностика "готово ≠ сделано" на будущее).
   `GWC_SEED_ENABLED` — дефолт изменён на **`true`** (было `false`).
   `GWC_SEED_MAX_WAIT_S` поднят **300→420с** (реальный факт VPS z9-14 —
   299,76с, почти на пределе прежнего значения).
2. Эмулятор: прямой вызов `deliver.seed_gwc_cache()` через реальный код
   `deliver.py` (не имитация REST-вызовов вручную) — `fields_latest`
   завершился штатно; `image_assessment` — см. итог ниже.
   Дополнительно подтверждено на слое `fields_latest` (векторный,
   другая bbox, `EX_GeographicBoundingBox` → 28203 расчётных тайлов
   через `tile_range_for_bbox_3857`) — реальное число файлов на диске
   после засева совпало ТОЧНО (28203) в двух независимых прогонах.
3. VPS: полноценной доставки пакета через `deliver.py` в этом раунде
   **не выполнено** — тестового ZIP-пакета в `inbox/` не было, а
   собирать пакет с нуля вне ETL-контура выходит за рамки раунда.
   Вместо этого на VPS проверена САМА механика прогрева (прямые
   REST-вызовы, тот же протокол, что использует `_seed_gwc_layer`):
   3 диапазона (z9-11/12/13, по 1 прогону) + 1 полный прогон z9-14 —
   все успешны, подтверждены по содержимому (файлы + HIT). Это
   частично закрывает требование ТЗ "одна реальная доставка с
   прогревом на VPS" — сама механика проверена реальными вызовами к
   боевому GeoServer, но не через оркестрацию `deliver.py` целиком.
   **Открыто**: прогнать полноценную доставку через `deliver.py` с
   `GWC_SEED_ENABLED=true` на VPS при следующей настоящей доставке
   данных и подтвердить как обычно (healthcheck + smoke.mjs).

**Побочное наблюдение** (не по одной из трёх гипотез блока A): первый
end-to-end прогон `seed_gwc_cache()` на эмуляторе шёл ОДНОВРЕМЕННО с
посторонней нагрузкой от других экспериментов этого же раунда — засев
`fields_latest` не уложился в старый предел 300с (клиент перестал ждать
и перешёл к `image_assessment`), при этом GWC ПРОДОЛЖИЛ досеивать
`fields_latest` в фоне — на короткое время оба слоя засеивались
одновременно (реальная конкуренция за 2 vCPU эмулятора). Оба слоя тем
не менее завершились корректно (проверено по числу файлов). Во втором,
"чистом" прогоне (без постороннего фонового трафика) переход между
слоями визуально завис на несколько минут — расследование показало,
что процесс всё это время был жив (`nanosleep`, не мёртв) и в итоге
всё-таки отправил запрос засева для `image_assessment` (это видно по
4 строкам long-array-array вместо 2 — второй засев того же слоя,
запущенный вручную для диагностики параллельно, слился с настоящим
запросом `deliver.py`); оба сошлись на верном итоге — 29960 файлов.
Причина задержки самого запуска (не самого засева) не установлена
фактом — вероятная причина: параллельные ssh-сессии этого же раунда
создавали нагрузку/конкуренцию за планирование процессов на эмуляторе.
В изолированных условиях без постороннего трафика такой задержки не
случилось ни разу за 13 других чистых прогонов (только этот один,
14-й, оказался смешан с посторонней нагрузкой). Итоговый счёт по всем
прогонам раунда — **15/15 точных совпадений** реального числа файлов с
независимым расчётом `tile_math`. Риск каскада при аномальной нагрузке
