## Блок A. Работоспособность у внешнего пользователя

### A1. Адрес сервера — **подтверждено**

Угадывание (`localhost:8080` → несуществующий `geobotany.xyz`) убрано.
Новый модуль `pikurr_qgis/geoserver_client.py`:
- `DEFAULT_GEOSERVER_URL = "https://geobotany.of.by"` — прод по HTTPS;
- `get_geoserver_url()`/`set_geoserver_url()` — хранение в `QSettings`
  (ключ `pikurr/geoserver_url`), пусто → сброс к прод-значению;
- `check_service_availability()` — не бросает исключений, возвращает
  `(ok, detail)`, detail заполнен всегда (что именно проверялось).

В диалоге (`pikurr_dialog_base.ui`) добавлено поле «Сервер:» +
кнопка «Применить» + строка статуса; `pikurr.py::load_server_data()`
вызывается при каждом открытии диалога и при нажатии «Применить», не
бросает исключений наружу — при недоступном сервере просто показывает
причину и оставляет диалог с пустыми списками (не падает).

Доказательства (без QGIS, чистый `python3`, реальные запросы к проду):
```
check_service_availability('http://geobotany.of.by')  -> (True, '... -> 200')
check_service_availability('https://geobotany.of.by') -> (True, '... -> 200')
```
HTTP и HTTPS оба дают 200 — редирект/прямой ответ Caddy прозрачен для
`requests`, `allow_redirects` по умолчанию хватает. Отдельный тест на
редирект не понадобился — оба протокола уже отвечают напрямую.

Дополнительно проверены WMS/WFS/WPS-пути плагина по HTTPS (раздел
"Headless-тест" ниже) — все три работают.

### A2. Справочник районов и землепользователей — **частично подтверждено**

Факт: у фронтенда **тоже нет серверного источника** — `distr`/`oblasts`
зашиты в `REPIKURR/repikurr/src/constants.js` точно так же, как раньше
были зашиты в плагине (только полнее — 22 района против 20 у плагина,
включает `6204`/Березинский). Единого серверного источника (таблицы,
представления GeoServer) не существует нигде в системе — это требует
изменения схемы БД или нового эндпоинта, что явно вне объёма этого
раунда (см. "Не делать" ТЗ round45/46/47) и требует отдельного решения
пользователя о том, заводить ли это в БД.

Сделано в пределах объёма:
- `REPIKURR/tools/gen_districts_ref.py` — генерирует
  `REPIKURR/repikurr/public/districts_ref.json` **из constants.js**
  (не отдельная третья копия), с режимом `--check` для обнаружения
  дрейфа. Проверено фактом: `--check` проходит сразу после генерации,
  22 района/7 областей.
- `pikurr_qgis/geoserver_client.py::fetch_districts_reference()` —
  плагин берёт названия из этого файла (тот же домен, что GeoServer,
  без CORS), не хранит собственного словаря вообще.
- Уровень «область» добавлен (`comboOblast` в UI) — код района
  (`rn`, 4 цифры) `[:2]` даёт код области; проверено фактом на реальных
  данных (`'2212'[:2] == '22'` — Витебская, совпадает с `oblasts`).
- Приёмка по содержимому: `_populate_oblast_and_district_combos()`
  строит список из **реальных кодов, присутствующих в данных**
  (`self.j['features']`), не из статического перечня; имя ищется в
  справочнике через `itemData` (`comboBox.addItem(label, code)` /
  `currentData()`), не обратным поиском по тексту — код без названия
  показывается как `"<код> (нет в справочнике)"`, не бросает `KeyError`
  (старый баг с `6204` устранён структурно, не патчем одного кода).

Не сделано: `districts_ref.json` ещё не опубликован на проде (файл
готов локально, требует деплоя фронтенда — см. пакет действий, блок E).
До деплоя `fetch_districts_reference()` корректно ловит отказ (сервер
отдаёт `index.html` вместо JSON — try_files) и показывает
пользователю "справочник недоступен", коды районов отображаются без
названий — не крash, но и не финальное состояние.

### A3. Обработка ошибок — **подтверждено**

`geoserver_client.py`:
- все WPS-запросы — через `wps_execute_json()`: таймаут (10с по
  умолчанию), проверка HTTP-кода, проверка на пустое тело,
  `_is_service_exception()` распознаёт `ServiceExceptionReport`/
  `ExceptionReport` при HTTP 200 (класс отказа №8/№13
  `HANDOFF_pikurr_v2.md`) как отказ, а не пустые данные, наконец
  проверка, что тело — валидный JSON. Любой отказ поднимает
  `GeoServerError` с понятным текстом, не даёт `json.loads()` упасть
  необработанным исключением.
- `pikurr.py::add_vec2()` — все три сетевых вызова (границы объекта,
  статистика) обёрнуты в `try/except GeoServerError`, показывают
  `QMessageBox.warning` вместо падения; попытка добавить слои без
  выбранного района/землепользователя — `QMessageBox.information`, не
  `IndexError`.

Проверено фактом (`python3`, без QGIS — функции чистые):
```
check_service_availability('http://127.0.0.1:1')
  -> (False, '... ConnectionError: ... Connection refused')
wps_execute_json('http://127.0.0.1:1', ...)
  -> GeoServerError: нет ответа от .../wps: ConnectionError: ...
check_service_availability('https://example.com')
  -> (False, '... HTTP 404')
wps_execute_json('https://example.com', ...)
  -> GeoServerError: .../wps вернул HTTP 405
```
Ни один из четырёх сценариев не поднял необработанное исключение —
все дали текст, пригодный для показа пользователю. Диалог остаётся
рабочим в обоих случаях (headless-тест ниже добавляет сеть-независимую
проверку: недоступность справочника районов — шаг 2 — не прерывает
остальные шаги теста).

## Блок B. Сопровождаемость

### B1. Совместимость с Qt6 — **подтверждено кодом, не подтверждено на реальной сборке Qt6**

Выбран путь "избавиться от `resources.py`" (предпочтительный по ТЗ):
- `resources.py` (39 КБ, жёстко `from PyQt5 import QtCore`) — удалён
  из репозитория и из публикуемого архива;
- иконка (`icon_2.png`) — грузится как обычный файл
  (`os.path.join(self.plugin_dir, 'icon_2.png')`), было
  `:/plugins/trash/icon_2.png`;
- оба WPS-шаблона (`vec:Bounds`, `vec:Aggregate`) — извлечены из
  бинарного `qt_resource_data` (ручной разбор формата Qt rcc: uncompressed/
  zlib-compressed записи, оффсеты из `qt_resource_struct_v1`) и положены
  как обычные файлы `pikurr_qgis/wps_templates/{bounds,aggregate}.xml`;
  `pikurr.py::_read_wps_template()` читает их напрямую.

Проверка по содержимому (ТЗ явно требует именно её):
```
grep -rn "PyQt5" pikurr_qgis/*.py
  -> совпадений нет (кроме одного упоминания в комментарии-истории)
```
Весь код плагина импортирует только через `qgis.PyQt`.

Не сделано фактом: реальная сборка QGIS с Qt6 недоступна на
координаторской машине (здесь установлен QGIS 3.44 на Qt5/PyQt5 —
`python3-pyqt5 5.15.10`, штатно для Ubuntu/Mint этого поколения).
Честно: совместимость с Qt6 подтверждена только устранением прямых
`PyQt5`-импортов (проверяемо `grep`, как и просило ТЗ на этот случай),
не прогоном на самой сборке. Если в будущем появится доступ к Qt6-сборке
(официальный installer QGIS.org ≥3.40 для Windows/macOS) — стоит
прогнать `tests/test_headless.py` на ней разово.

## Блок C. Что плагин запрашивает у сервера

### C.1 WPS-расширение — **подтверждено**

`docker-compose.vps.yml`: `image: kartoza/geoserver:2.24.2` — версия
запинена тегом (не `:latest`), WPS/vector-process расширения — часть
этого образа целиком, не отдельно устанавливаемый плагин. Проверено
фактом на самом проде:
```
GET /geoserver/wps?service=WPS&version=1.0.0&request=GetCapabilities
  -> содержит gs:Query, vec:Aggregate, vec:Bounds
```
Риск исчезновения при обновлении существует только если сменить
базовый образ на другой дистрибутив/урезанную сборку — не сценарий
обычного `docker compose pull` с запиненным тегом. Резервный путь через
обычный WFS (слой `pikurr:levelsagg`, `advertised=true` уже применён в
round46) прописан как рекомендация на случай будущей миграции образа —
не реализован сейчас, так как WPS работает и менять нечего по факту.

### C.2 Цена растрового слоя мимо GWC — **измерено**

Плагин (`radio_base()`) берёт растр через `/geoserver/wms` напрямую,
минуя GWC. Замер (координаторская машина → прод, через интернет — не
проекция на VPS, см. "Правила замеров"), 5 bbox из
`docs/round32_assets/tiles_with_data.json`, по 3 повтора, 256×256,
`layers=pikurr:image_assessment`:

| путь | среднее время, с |
|---|---|
| `/geoserver/wms` (прямой, путь плагина) | 0.741 |
| `/geoserver/gwc/service/wms&tiled=true` (кэш, тёплый, HIT) | 0.640 |

Разница ~14% на уровне одного тайла — на этой выборке не драматична;
основной практический недостаток прямого пути — не скорость первого
запроса, а отсутствие кэширования между повторными рендерами (панорама/
зум в плагине перерисовывает картинку с нуля каждый раз, GWC-путь
переиспользовал бы уже прогретые тайлы). Известная мина (round46):
XYZ-провайдер QGIS с `{bbox}`-подстановкой давал зелёный headless-тест,
но пустой слой в реальном GUI — если переход на GWC когда-либо будет
делаться, начинать проверку именно с реального GUI, не headless.

**Решение по результату замера**: менять сейчас не стоит — выигрыш
скромный, а миграция на XYZ-путь через GWC несёт подтверждённый на
практике риск (round46). Оставлено как есть, зафиксировано для
будущего пересмотра, если объём использования вырастет.
