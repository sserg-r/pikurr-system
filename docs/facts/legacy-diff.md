Раунд 51, блок A. Старый комплект — `pikurr20241212.zip`: «Описание
применения» (**ОП**, АРМН.46877-01 31 01), «Руководство оператора»
(**РО**, АРМН.46877-01 34 01), «Программа и методика испытаний» (**ПМИ**,
АРМН.46877-01 51 01), «Ведомость НЗ» (**ВНЗ**). Файлы лежат локально в
`docs/_legacy_local/` (в `.gitignore`, в репозиторий не попадают); в
таблицах на них ссылаются по имени документа и номеру раздела.

## Как читать

- Текст старых документов **источником не считается** — каждая строка
  «как на самом деле» проверена по коду/конфигурации/команде на момент
  раунда 51 (2026-09-30). Ссылка вида `файл:строка` — строка репозитория
  на коммите `030ec02` + правки раунда 51 (правок в код нет).
- Статусы: **верно сейчас** / **изменилось** / **больше нет** / **не
  проверяется по коду**. Где утверждение не подтвердилось ни кодом, ни
  конфигурацией — прямо написано «не подтверждено».
- Каталог `PIKURR/pyscr/` (старая реализация) лежит на координаторской
  машине, но **не отслеживается git** (`.gitignore`, строка `*` +
  белый список) — его содержимое датировано декабрём 2025 (`ls -l`),
  а не декабрём 2024; использовано только как справочный материал о
  прошлом состоянии, не как доказательство состояния «на дату комплекта».
- Сокращения путей: `src/` = `PIKURR/src/`; `dl` = `src/tasks/download.py`,
  `seg` = `src/tasks/segmentate.py`, `usab` = `src/tasks/usability.py`,
  `cls` = `src/tasks/classify.py`, `pc` = `src/utils/postclassify.py`,
  `gee` = `src/services/gee.py`.

## 0. Главные расхождения одним списком (подробности — в таблицах ниже)

1. Ранжирования тайл-сервисов по Hansen/резкости **в текущем коде нет**
   (и не было вызвано в старой реализации `pyscr` — функции определены,
   но не вызываются, см. А2-1).
2. Перекрытие фрагментов сегментации — **30 пикселей**, не 50.
3. Инференс: ONNX Runtime + CUDA, одна модель `two` (opset 13), не TF
   Serving; сервиса `tf-service` больше нет.
4. «Удаление объектов < 80 м²» в коде **нет**: `sieve` = 3 пикселя
   (≈1,4 м²) при подсчёте статистики; для маски «используемости» —
   10 пикселей по 10 м (=1000 м²).
5. Сценарии `meadow/forest/clearing/tillage` считаются **в SQL
   представлении** `assessment_ready` на стороне витрины; `tillage`
   определяется по кадастровому баллу `ball_co > 24`, а не по доле
   класса «обработка почвы».
6. Автозапуска «30 декабря» и перезапуска через час нет; запуск —
   кнопка Streamlit-дашборда или `python -m src.tasks.<задача>`.
7. Публикация в GeoServer из ETL больше не выполняется — ETL пакует
   ZIP, а `REPIKURR/deliver.py` на сервере витрины принимает пакет и
   обновляет GeoServer.
8. Появились компоненты, которых в комплекте нет вовсе: витрина
   (React), VPS, доставка/вотчдог, GWC-кэш, мониторинг, автозапуск ВМ,
   бэкапы.

### 3. Оценка хозяйственной деятельности по Sentinel-2 (ОП 3.2.3, РО 3.3.3)

- **Период**: 15 апреля – 15 октября (`gee:38`). Верно.
- **Годы**: 3 — год оценки и 2 предыдущих (`get_target_years(count=3)`,
  `usab:64-65`, `cls:42-43`). Год оценки: если месяц ≥ 11 — текущий год,
  иначе предыдущий (`src/utils/timeutils.py:7`). Верно.
- **Правило «хотя бы в одном году»** — `any(axis=0)` по годам (`cls:98`).
  Верно.
- **Классы SCL**: в анализ пикселя берутся только `4` (растительность) и
  `5` (не растительность, «голая земля») (`src/utils/analysis.py:16`);
  остальные (вода, облака и т. п.) отбрасываются. Пиксель, где после
  отбрасывания осталось меньше 4 наблюдений → «0» (`analysis.py:18-19`).
- **Правило «устойчивой смены»** (`analysis.py:21-28`): по
  временному ряду 4/5 ищется окно из 4 подряд идущих наблюдений вида
  `4,4,5,5` или `5,5,4,4`. Результат пикселя — число найденных окон
  (`uint8`), «>0» = смена. (Реализация через `np.correlate(filtered,
  1/kern, 'valid') == 4` — сравнение float на равенство; поведение
  подтверждено логикой сопоставления «каждый элемент/шаблон = 1»; на
  практике полностью соответствует описанной сути, крайние
  вычислительные случаи не исследовались.)
- **Что добавилось** (нет в старых документах):
  - Cloud Score+ (`GOOGLE/CLOUD_SCORE_PLUS/V1/S2_HARMONIZED`, полоса
    `cs_cdf`): пиксели с `cs_cdf ≤ 0,80` получают SCL=12 (то есть
    исключаются из анализа классов 4/5) — `gee:39-54`, `CLEAR_THRESHOLD =
    0.80` (`gee:43`);
  - фильтр сцен `CLOUDY_PIXEL_PERCENTAGE < 20` (`CPP = 20`, `gee:44`,
    фильтр — `gee:57-61`);
  - коллекция `COPERNICUS/S2_SR_HARMONIZED` (`gee:40`);
  - суточные мозаики (несколько снимков одного дня склеиваются) —
    `gee:63-78`;
  - предел площади листа 25 км² — иначе ошибка (`gee:34-35`);
  - масштаб 10 м, EPSG:4326, `GEO_TIFF` (`gee:86-92`); до 5 повторов с

- **Постобработка маски** (после объединения лет, `cls:98-114`):

### 6. Итоговые классы и сценарии `meadow/forest/clearing/tillage`

Считается **не в ETL-Python**, а в SQL: материализованное представление
`assessment_ready` (`PIKURR/src/sqlscripts/create_assessment_schema.sql`,
поле `valuation`). Правило (`create_assessment_schema.sql`, блок
`valuation`):

```
frac = (доля класса 0 + 1 + 2) / (сумма долей классов 0..5)   -- лес + кусты + луг закустаренный
если frac > 0.4 и ndohod_d <= 0  → 'forest'
иначе если frac > 0.3 и ndohod_d  > 0 → 'clearing'
иначе если ball_co > 24            → 'tillage'
иначе                              → 'meadow'
```

- `ndohod_d`, `ball_co` — атрибуты исходного слоя `agrifields`
  (кадастровые: `ndohod_d` — доходность, `ball_co` — балл; смысл
  показателей в репозитории не описан — см. пробелы).
- **Расхождение с комментарием в том же файле**: комментарий-шапка
  сопоставляет «tillage → class 5, meadow → class 3, clearing → classes
  1, 2, 4» (`create_assessment_schema.sql`, шапка блока `2.`), тогда как
  фактическое правило CASE использует кадастровые показатели, а
  **класс 5 («обработка почвы») в `valuation` вообще не участвует**
  (кроме знаменателя `frac`). Основание: текст CASE (см. выше).
- `bzdz` (условия хозяйствования) — категории по `ndohod_d` (>400
  «наиболее благоприятные», >300 «благоприятные», >200 «хорошие», >100
  «удовлетворительные», >0 «сложные», иначе «плохие»).
- Подписи сценариев на витрине/в плагине: `forest` — «перевод в л/х»,
  `tillage` — «пахотное с/х», `clearing` — «с/х после расчистки»,
  `meadow` — «луговое с/х» (`REPIKURR/repikurr/src/components/StatsTable.jsx:3-8`, `pikurr.py:39-44`).
- Данные ETL-БД на стенде (`pikurr-system-db-1`) для `assessment_ready`:
  обычное (не материализованное) представление; на VPS — материализованное
  (`system-state.md` §3). Причина расхождения версий схемы в ETL-БД
  и на сервере не исследовалась (см. отчёт, блок C.2).
