См. `prompts/PROMPT_capacity_round40.md`. Вопрос раунда — закрытый в
round27 как «не справляется с уверенным запасом даже при 1-5
пользователях», не переизмерялся с тех пор, хотя система изменилась

## Блок A. Модель нагрузки и процедура

### A1. Определение пользователя — проверено фактом

**Вопрос**: держит ли k6 отдельную cookie на VU (иначе `user=6` в
`controlflow.properties` считает весь трафик load-теста одним
пользователем, и вся кампания измеряет не то).

**Сделано**: диагностический k6-скрипт (3 VU × 2 запроса, машина —
стенд `192.168.251.190` как клиент, цель — прод), читающий
`http.cookieJar().cookiesForURL()` между запросами.

**Находка, важная сама по себе**: GeoServer выдаёт `GS_FLOW_CONTROL`
только на ПЕРВЫЙ запрос (см. `Set-Cookie` в ответе — подтверждено
`curl -D -` отдельно); первый запрос без cookie у всех 3 VU **истёк по
таймауту** (`request timeout`, k6 default), второй запрос (уже с
cookie) прошёл у всех троих. Не исследовано глубже в этом срезе — не
критично для самого вопроса A1, но подозрительно (возможная задержка
на анонимном/безсессионном запросе control-flow, см. «Открытые
вопросы» блока A ниже), стоит держать в уме перед первой боевой
ступенью замера.

**Результат, отвечающий на вопрос A1**: три VU получили **три разных**
значения cookie на втором запросе —
```
VU=1 GS_FLOW_CONTROL=GS_CFLOW_730a2836:1a0d75d4d97:-7ff3
VU=2 GS_FLOW_CONTROL=GS_CFLOW_730a2836:1a0d75d4d97:-7ff1
VU=3 GS_FLOW_CONTROL=GS_CFLOW_730a2836:1a0d75d4d97:-7ff2
```
k6 действительно держит cookie jar на VU по умолчанию — `user=6`
корректно моделируется как 6 независимых пользователей, не как 1.

**Подтверждено** фактом.

**Побочная находка (сеть)**: с координаторской машины (в т.ч. из
контейнера `docker run` на ней) исходящий HTTPS к `geobotany.of.by`
недоступен вообще (`curl` внутри контейнера — `000`/timeout,
воспроизведено дважды) — как и в round27/28, вся нагрузка на VPS
генерируется **со стенда** (`192.168.251.190`) как клиента, не с
координатора.

### A2. Состав действий — модель реализована, доли — стартовые из ТЗ

`REPIKURR/tools/capacity_k6.js` (новый файл, round40): сессия = VU,
каждая итерация — одно действие с паузой think-time 3-10с после:
- **70% NAV** — тайлы из `docs/round32_assets/tiles_with_data.json`
  (тот же проверенный набор round32/33), случайно `fields_latest`/
  `image_assessment`, ВСЕГДА через `/geoserver/gwc/service/wms&tiled=true`
  (ожидание HIT). Первое действие VU — **30 тайлов** (загрузка), дальше
  смесь: 80% — **4 тайла** (сдвиг), 20% — **20 тайлов** (включение
  растра);
- **20% GROUP** — 4-8 тайлов + 1 `GetFeatureInfo`, ВСЕГДА через обычный
  `/geoserver/pikurr/wms` с `CQL_FILTER=nr_user LIKE '<код>%' AND year=2025`
  (реальные коды сняты фактом через WFS `levelsagg` — `2212000055`,
  `2238000015`, `2212000077`, `2212000113`), мимо GWC — самый дорогой
  путь (CLAUDE.md «Ловушки»: GWC игнорирует `CQL_FILTER`);
- **10% MISS** — 8 тайлов, тот же bbox засеянного набора, размельчённый
  на непересекающиеся четверти (эквивалент более глубокого зума той же
  точки) — вне засеянного диапазона GWC z9-14, гарантированный `MISS`.

Каждое действие пишет в `checkBody()`: код+тело (включая
`ServiceExceptionReport` при HTTP 200 — CLAUDE.md «Критерий приёмки»),
долю `<2КБ`, `Geowebcache-Cache-Result`. Метрики по типам действия
раздельно (`action_duration_nav/group/miss`, `action_error_*`).

**Batch-размеры NAV (A1) пересняты фактом**, не взяты приближением из
round28 (устарело — до подсветки группы round37 и зачистки 2024
round39): `claude-in-chrome` в этой сессии не подключён, поэтому
написан отдельный Playwright-скрипт `REPIKURR/tools/smoke/measure_batch_sizes.mjs`
(тот же инструмент, что `smoke.mjs`, — реальный браузер, не
приближение), 3 прогона против `https://geobotany.of.by`, все три
идентичны (не случайная величина — batch определяется сеткой
тайлов viewport, не рандомом):

| Действие | round28 (устарело) | round40 (факт, 3/3 прогона совпали) |
|---|---|---|
| Первая загрузка страницы | 24 (12+12 по двум векторным слоям) | **30** |
| Сдвиг (pan) | 8 | **4** |
| Включение слоя AI-оценки | 16 | **20** |

зафиксировано как факт для этого раунда, не гипотеза о причине.
`capacity_k6.js` обновлён под эти числа.

**Дымовой прогон скрипта** (2 VU, 20с, машина — стенд→прод, это НЕ
входит в саму кампанию, только проверка работоспособности инструмента,
до обновления batch-размеров под факт выше):
```
gwc_hit_rate: 97.82% (45/46, 1 MISS — совпадает с ожиданием)

```

не определён для `responseType:'text'` (GetFeatureInfo) — давал
ложный «пустой ответ» → ложную ошибку действия GROUP (100% на первом
дымовом прогоне). Исправлено (проверка `.length` для текстовых тел).

**Подтверждено** полностью — механизм, доли и теперь и batch-размеры
NAV сняты фактом, не приближением.

прогон `capacity_k6.js` на 1 VU в течение N минут, обходящий все 20
bbox набора × оба слоя) и включена в кампанию блока C, не выполнена
отдельно в этом срезе (готовность GeoServer по содержимому проверяется

### Вывод по ступени 4 ГБ (локально)

**Критерий ТЗ (p95<2с при 15 VU) ВЫПОЛНЕН** — все 3 повтора на 15 VU

по времени ответа, но без запаса по крайним 20 пользователям.

### Открытый вопрос — финальная конфигурация прод-ВМ (НЕ решено пользователем)

ТЗ требует по завершении раунда вернуть конфигурацию в согласованное с

какую RAM оставить на проде по итогу (6 ГБ — безопасный возврат к
исходной, 4 ГБ — компромисс с запасом, 3 ГБ — максимальная экономия

отдельного рассмотрения, не выбирать сейчас**. Раунд НЕ закрывает эту
развилку сам — **прод в данный момент так и остаётся на ступени 3 ГБ**

стабильна, `healthcheck.py` зелёный) — это не «незакрытый эксперимент»,
а рабочее, самосогласованное состояние, которое можно оставить как
есть до отдельного решения. Откат к любой из пройденных ступеней —
по бэкапам `docker-compose.vps.yml.bak_pre_round40_{6,5,4,3}gb_<TS>`

не существует — часть инструкции round23/33 больше не актуальна).
