### A3. Поиск в списке землепользователей — **найдена другая, более серьёзная проблема, исправлено**

Утверждение отчёта round48 ("editable QComboBox уже фильтрует по
префиксу") **опровергнуто фактом**. Реальная диагностика (`QTest`,
реальный ввод через синтетические `QKeyEvent` — `QTest.keyClicks()`
падает на кириллице в этой сборке PyQt5, см. ниже):

```
--- "фом" + Enter ---   currentIndex=0 (Весь район), currentData=None
--- "Фоменков" + Enter ---  currentIndex=0, currentData=None
--- "2212000055" + Enter --- currentIndex=0, currentData=None
--- точный текст пункта "УО ВГАВМ" + Enter --- currentIndex=5, currentData=2212000016, activated=[5]
```
Реальная проблема — **не** "лишний пункт добавляется" (это ТЗ
предполагало неверно: `insertPolicy` в 1.2.0 УЖЕ был `NoInsert`,
проверено фактом — count не растёт), а **поиск работал только по
100%-точному совпадению текста пункта**, частичный ввод вообще не
вызывал `activated`.

Исправлено:
- `pikurr_panel.py::_make_searchable()` — `QCompleter` с
  `Qt.MatchContains` + `CaseInsensitive` на модели самого combo (не
  копии данных — работает после любого `clear()`/`addItem()`);
- код добавлен в текст пункта (`"Фоменков Г.В. · 2212000055"`,
  `"Витебский · 2212"`) — иначе поиск по коду не находил ничего
  (совпадение ищется по отображаемому тексту).

Проверено фактом (реальный ввод через синтетические `QKeyEvent`, не
`setText()` — обычный `setText()`/эмиссия `textEdited` НЕ триггерит
`QCompleter`, только реальная последовательность событий клавиатуры):
```
[PASS] A3. Подстрока из середины имени находит нужного землепользователя в popup (MatchContains)
      вариантов=1, найдено=Фоменков Г.В. · 2212000055, popup_visible=True
[PASS] A3. Код находит того же землепользователя в popup
[PASS] A3. Несуществующий текст + Enter не добавляет пункт в список
```

**Не проверено headless (честно, не выдано за сделанное)**: финальный
клик мышью (или Down+Enter внутри popup) по найденному варианту —
`popup.isVisible()==True`, вариант найден правильно, но сама
навигация/клик **внутри** popup-окна недоступна под offscreen QPA —
сам Qt печатает `"This plugin does not support raise()"` и
`"...grabbing the keyboard"` при попытке. Это ограничение платформы
тестирования, не код плагина — но факт остаётся непроверенным
автоматически, вынесен в чеклист E4 (пункт про поиск).

**Побочная находка** (стоит времени отладки, задокументирована для
будущих раундов, не в `CLAUDE.md` — специфично для тестов с юникодом,
не общий факт про `qgis --code`): `QTest.keyClicks(widget, "текст")` с
кириллицей вызывает `Fatal: ASSERT: "false" in file qasciikey.cpp`,
роняя весь процесс QGIS. Обходной путь — ручная генерация
`QKeyEvent(QEvent.KeyPress, Qt.Key_unknown, Qt.NoModifier, символ)` на
каждый символ (см. `send_unicode_text()` в тесте).

### A4. Границы и зум — **проверено, куда именно**

Раньше: "зум отработал, панель жива" — не говорило, куда. Теперь: центр

### A5. «100% непрозрачных пикселей» — **найдена и исправлена реальная причина**

Подозрение ТЗ подтвердилось: URL слоя полей **не передавал

прозрачностью по умолчанию) — правка её не касалась.

Исправлено — `pikurr.py::_update_fields_layer()`, добавлен
`&transparent=true`. Проверено фактом (рендер слоя полей БЕЗ подложки,

```
[PASS] A5. URL слоя полей содержит transparent=true
[PASS] A5. Слой полей на охвате одного участка — большая часть пикселей прозрачна

```
(75.5% прозрачных — фон; `0x805c2e03` — полупрозрачная заливка стиля
поля; `0xffff0000` — красная граница/выделение.)

## Блок B. Статистика витрины не учитывает год

### Подтверждено фактом (по коду и запросами, только чтение)

`getstatsbyuser.xml`/`getbboxbyuser.xml` (до правки) — `typeName="pikurr:fields"`,
фильтр только `nr_user LIKE`, **без условия года**, независимо от
выбора пользователя во фронтенде. Слой карты (`App.jsx::vectorTypeName`)
год учитывал. Реальными запросами подтверждено (round48 и повторно в
этом раунде): на единственном годе прода (2025) числа `fields`
(без условия года) и `fields_latest` совпадают — расхождение скрыто,
не отсутствует структурно.

### Исправлено

`REPIKURR/repikurr/src/services/fieldsQuery.js` — единая точка
семантики (`fieldsTypeName(year)`, `buildOgcFilter(year, groupCode)`),
используется и в `App.jsx` (`vectorTypeName`), и в
`geoserver.js::getStatsByUser/getBboxByUser`. XML-шаблоны
параметризованы (`{{TYPENAME}}`/`{{FILTER}}` вместо жёсткого
`pikurr:fields`).

### Приёмка — проверено реальными запросами к проду (только чтение)

```
getstatsbyuser.xml, без года:      {"tillage",1,5.6} — HTTP 200
getstatsbyuser.xml, year=2025:     {"tillage",1,5.6} — HTTP 200 (идентично)
getstatsbyuser.xml, year=2024:     AggregationResults=[] — HTTP 200, без исключения

getbboxbyuser.xml, без года:       LowerCorner/UpperCorner — реальный bbox
getbboxbyuser.xml, year=2025:      идентичный bbox
getbboxbyuser.xml, year=2024:      LowerCorner(0,0)-UpperCorner(-1,-1) — HTTP 200,
                                    вырожденный (но не ошибочный по HTTP-коду) bbox
```
**Находка**: для пустого набора `vec:Bounds` отдаёт математически
инвертированный bbox (верхний угол меньше нижнего) — это штатный ответ
GeoServer на пустой результат, не новая проблема этой правки. Если
фронтенд наивно передаст такой bbox в `fitBounds()` без проверки —
поведение карты непредсказуемо. Существующий механизм `groupEmpty`
(round37, отдельный `getFeatureCount` запрос) уже показывает баннер
"нет данных" независимо от этого — но сам вызов `getBboxByUser` с
пустым результатом не проверялся на этот случай отдельно. **Не
исправлено** (вне явного объёма блока B — только typeName/год; отдельная
находка для будущего раунда, если понадобится).

`npm run build` — 91 модуль, без ошибок (локальная сборка на
координаторской машине, не деплой).

**Выкатка** — не выполнена, идёт одним пакетом с round47/48, блок E.
