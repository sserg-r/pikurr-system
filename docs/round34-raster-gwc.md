## Блок A. Растровый слой

### A1. Причина — по телу ответа

**Реальный URL из браузера** (снят через `read_network_requests` в
`claude-in-chrome`, вкладка на `geobotany.of.by`, клик по чекбоксу
«AI оценка»):

```
GET https://geobotany.of.by/geoserver/gwc/service/wms?service=WMS&request=GetMap&
  layers=image_assessment&styles=&format=image%2Fpng&transparent=true&
  version=1.1.1&tiled=true&width=256&height=256&srs=EPSG%3A3857&bbox=...
→ HTTP 400
```

Тело ответа (снято `curl` тем же URL):

```html
<h4>400: Thread 1481 Unknown layer image_assessment. Check the logfiles,
it may not have loaded properly.</h4>
```

Тот же bbox с `layers=pikurr:image_assessment` (полное имя с workspace):

```
HTTP 200, PNG 256×256
```

**Причина**: `/geoserver/gwc/service/wms` — общий (не per-workspace)
эндпоинт GWC, требует полностью квалифицированное имя слоя
(`workspace:layer`). Обычный `/geoserver/pikurr/wms` — виртуальный
per-workspace сервис, у него workspace уже в пути, поэтому он принимает
имя слоя как с префиксом, так и без (проверено фактом ниже, оба
варианта дают идентичный `HTTP 200`, тот же PNG размером в байтах).

Источник расхождения — не конфигурация GWC-слоя (A1.3 ниже показывает,
что конфигурации `fields_latest` и `image_assessment` в GWC совпадают
по типу расхождения), а фронтенд: `REPIKURR/repikurr/src/components/MapView.jsx`,
пропс `layers` для растрового `WMSTileLayer` был `rasterLayer` (голое
имя `image_assessment`/`image_assessment_<год>`, без префикса), а не
`rasterFqName` (`pikurr:image_assessment...`). У векторного слоя
аналогичной ошибки не было — там префикс `pikurr:` зашит прямо в саму
переменную `vectorLayer` (`'pikurr:fields_latest'`/`'pikurr:fields'`),
поэтому оба эндпоинта векторный слой всегда получали полное имя.

### A1.2. Тот же bbox через обычный `/geoserver/pikurr/wms`

```bash
curl .../geoserver/pikurr/wms?...&layers=image_assessment&...   → HTTP 200, PNG (11008 байт)
curl .../geoserver/pikurr/wms?...&layers=pikurr:image_assessment&... → HTTP 200, PNG (11008 байт)
```

Работает в обоих написаниях — подтверждает, что путь `/geoserver/pikurr/wms`
не является источником проблемы.

### A1.3. Конфигурация двух GWC-слоёв

Расхождение не в конфигурации GWC-слоёв (grid subset, диапазон
масштабов, `metaWidthHeight`, форматы — идентичны по типу для обоих
кэшируемых слоёв, оба зарегистрированы в раунде 32, блок B, одним и тем
же способом). Расхождение — в том, как фронтенд ОБРАЩАЕТСЯ к слою:
`fields_latest` всегда получал полное имя, `image_assessment` — нет.
Причина не в GWC, поэтому пункт «привести конфигурацию GWC-слоя в
соответствие» из раздела A2 ТЗ не применим — применим второй пункт по
факту (правка фронтенда), но не как «запасной вариант с потерей кэша»,
а как прямое исправление без потери кэша.

### A1.4. На всех ли масштабах и участках ломается

10 тайлов (5 + 5 из `docs/round32_assets/tiles_with_data.json`,
пересчитаны в точные bbox тайловой сетки GWC для z=11/13/15 —
координаты по центроидам полей `lon`/`lat` из того же файла) ×
3 масштаба = 30 запросов с полным именем слоя:

```
z=11: 10/10 — HTTP 200
z=13: 10/10 — HTTP 200
z=15: 10/10 — HTTP 200
TOTAL fail=0/30
```

С голым именем (`image_assessment`, как слал фронтенд до фикса) — во
всех 30 случаях `HTTP 400`, без исключений. **Ломается везде и всегда**,
не зависит от масштаба и участка — ожидаемо, т.к. причина не связана с
данными или гридом, только с текстом URL.

### A2. Починка

Применён путь «привести обращение в соответствие» — правка
`layers={rasterLayer}` → `layers={rasterFqName}` в
`REPIKURR/repikurr/src/components/MapView.jsx` (растровый `WMSTileLayer`,
строка с `key={\`mosaic-...\`}`). `rasterFqName` уже вычислялся в файле
(`pikurr:${rasterLayer}`) для проверки `GWC_CACHED_LAYERS.has(...)`, но
не использовался как значение пропса `layers` — использовалась
непрефиксованная переменная. Кэш **не теряется** — используется тот же
эндпоинт `/geoserver/gwc/service/wms`, что и раньше, просто с корректным
именем слоя.

### A3. Почему это не поймали

Правка, вводящая расхождение (`layers={rasterLayer}` вместо
`rasterFqName`), — часть раунда 32, блок B/C (включение GWC-кэша для
растра). С этого момента до отчёта пользователя в раунде 34 слой был
сломан.

- **`healthcheck.py`/`external_healthcheck.sh`** (раунд 33) проверяют
  `wms_getmap` — но по всей видимости, тестовым запросом к обычному
  `/geoserver/pikurr/wms`, не к `/geoserver/gwc/service/wms` с тем же
  URL, что реально шлёт фронтенд (это ровно тот случай, о котором ТЗ
  предупреждает в A1.1: «взять реальный URL из браузера, не
  сконструированный» — сконструированный вручную URL здоровья-проверки
  не воспроизводил конкретную ошибку фронтенда).
- **Дымовой сценарий браузера раунда 33** (введён тем же раундом,
  который ввёл баг, — блок C того раунда) по формулировке в CLAUDE.md
  проверяет, что `document.body.innerText` не пуст и нет ошибок в
  консоли при ОБЩЕЙ загрузке страницы — WMS-тайл, упавший с ошибкой,
  не бросает JS-исключение и не пустит `document.body`: `WMSTileLayer`
  просто не отрисовывает конкретный тайл (`tileerror`), а баннер
  деградации (раунд 33, блок C.1) реагирует на счётчик ошибок ТОЛЬКО
  если он уже был запущен и достаточно тайлов упало за 5 секунд — в
  раунде 33 сценарий не включал сам чекбокс «AI оценка» (слой по
  умолчанию выключен), поэтому проверка ни разу не отправила запрос,
  который бы упал.

Вывод в блок B: дымовой сценарий обязан явно включать КАЖДЫЙ элемент
управления, а не только проверять, что страница в принципе
отрендерилась — это отдельно и прямо прописано в самом ТЗ раунда 34,
пункт B1.

## Блок B. Дымовая проверка в браузере как условие выкатки

### B1-B2. Сценарий и его оформление

Выбор инструмента: **Playwright**, не `claude-in-chrome`.
`claude-in-chrome` — интерактивный MCP-инструмент, управляется агентом
внутри диалога Claude Code, не может быть положен в репозиторий как
самостоятельно запускаемый артефакт (нужна живая сессия). Node 22 в
среде уже установлен (`node --version` → v22.23.2) — Playwright встал
штатной npm-зависимостью без дополнительной инфраструктуры;
`npx playwright install chromium` (без `--with-deps`, т.к. `--with-deps`
пытается поставить системные пакеты через `sudo`, а на координаторской
машине `sudo` не настроен без пароля — в отличие от VPS/эмулятора) —
хватило голого бинарника браузера, зависимости ОС на этой машине уже
были нужного состава.

Файл: `REPIKURR/tools/smoke/smoke.mjs` (+`package.json` там же).
Запуск: `cd REPIKURR/tools/smoke && npm install && npx playwright install
chromium && BASE_URL=<домен> node smoke.mjs`.

Каждый шаг — с критерием по содержимому, не по факту открытия страницы:

| Шаг | Критерий |
|---|---|
| 1. Загрузка страницы | заголовок `h2` == «ПИК УРР», сайдбар виден, 0 ошибок консоли |
| 2. Выбор года | селектор года есть только если >1 года — если есть, смена значения не роняет консоль |
| 3. Выбор района | смена района не роняет консоль, уходит WPS-запрос за bbox |
| 4a. Включение слоя AI-оценки | запросы к `gwc/service/wms` есть и ВСЕ `200` (это прямой регрессионный тест на баг блока A — до фикса здесь было бы `0 успешных из N`) |
| 4b. Выключение слоя | в DOM не осталось `<img src*="image_assessment">` |
| 5. Клик по полю | всплывает `.map-popup` с заголовком «Детали участка» и непустым содержимым (таблица статистики либо свойства участка) — перебор точек вокруг центра карты, т.к. точное совпадение клика с полигоном не гарантировано |
| 6. Зум | клик по `leaflet-control-zoom-in` не роняет консоль, уходят новые тайловые запросы |
| 7. Сдвиг (pan) | перетаскивание карты не роняет консоль, уходят новые тайловые запросы под новый bbox |
| 8. Клик в области без данных | клик в углу вьюпорта НЕ показывает `.map-popup`, консоль без ошибок |

### B3. Правило в CLAUDE.md

фронтенда не считается завершённой без зелёного прогона

## Блок C. Метатайлы и 891 мс

### Важная оговорка перед цифрами

Исходные «891 мс ожидания ответа сервера», упомянутые в сообщении
пользователя (преамбула ТЗ), были замерены **против сломанного слоя**
(блок A ещё не был починен на момент того замера в браузере) — то есть
это время получения `HTTP 400`/страницы ошибки GWC, а не время
рендера реального тайла. Напрямую «объяснить именно эти 891 мс»
поэтому нельзя — можно только установить фактом состав времени
запроса РАБОТАЮЩЕГО тайла в сопоставимых условиях (холодное соединение
снаружи, промах кэша) и показать, что величина того же порядка
получается из вполне реальных, объясняемых факторов, а не только из
факта поломки.

### C1. Из чего складывается время тайла (машина: VPS, изнутри — `curl`
на `localhost:8090`, без Caddy/TLS/внешней сети — та же точка, что
round32 A.2)

Прямое сравнение `MISS`/`HIT` для ОДНОГО и того же свежего тайла:

```
первый запрос (MISS, метатайл 4×4 рендерит блок 4×4 = 16 тайлов): total=0.661s
повторный запрос того же тайла (HIT):                              total=0.006s
```

Серия из 16 смежных, заведомо НЕ запрошенных ранее тайлов (один
метатайл 4×4 целиком, z=16):

| тайл в блоке | geowebcache-cache-result | время |
|---|---|---|
| 1 (первый) | **MISS** | **371 мс** |
| 2–16 | HIT | 3–6 мс каждый |

**Гипотеза ТЗ подтверждена фактом**: первый запрос в новой области
платит за рендер всего метатайла (16 тайлов) на сервере — ~370-660мс
на VPS; все соседние тайлы того же метатайла после этого отдаются из
кэша почти мгновенно (~5мс).

Внешне (снаружи, через домен, `curl`, холодное TCP+TLS-соединение,
тот же приём, что round32 A.4) для свежего (`MISS`) тайла:

```
connect=0.0001s tls=0.335s total=0.683s   (geowebcache-cache-result: MISS)
```

Т.е. **TLS-хендшейк (~335мс) + рендер метатайла на сервере (~350-370мс
из точки выше) в сумме дают ~680-700мс** — того же порядка, что и
исходные 891мс, хотя это два независимых источника задержки, оба
реальны и складываются именно в момент первого визита пользователя на
новую область при холодном соединении (частый случай — первая
загрузка страницы).

экономии (соседние тайлы становятся `HIT`) работает — просто цена
рендера большего метатайла на **первом** тайле нового экрана
перевешивает экономию на соседних. При 1×1 каждый из 12 тайлов —
собственный `MISS` (~11мс на тайл), но суммарно это дешевле одного
дорогого рендера 4×4-блока (~170-325мс) плюс более быстрых соседей.

**Это измерение — только для ХОЛОДНОГО (первый визит в область)
случая**, что и просит ТЗ. Оно не отражает вторичный эффект
метатайлинга — экономию для ДРУГИХ пользователей/сессий, которые
впоследствии откроют ЧАСТИЧНО пересекающийся, но не идентичный участок
(типичный сценарий публичной витрины: разные посетители смотрят на
похожие, но не идентичные bbox) — при более крупном метатайле у них
выше шанс попасть в уже прогретую область. Существующие измерения это
не покрывают (нужен трейс реальных запросов за длительный период, не
собран в этом раунде).

### C3. Рекомендация

**Не менять** `metaWidthHeight` на VPS по результату этого раунда.
Причины:
1. Выигрыш по суммарному времени экрана при уменьшении метатайла
   реален для ПЕРВОГО холодного визита в область (C2), но данных
   недостаточно (3 повтора, один необъяснённый выброс) для уверенного
   решения по боевой системе — правило ТЗ «внедрять по результату, не
   наугад» пока не выполнено в сторону обратного изменения тоже.
2. Эксперимент не учитывает эффект метатайлинга на ПОВТОРНЫЕ визиты
   разных пользователей в похожие (не идентичные) области — именно
   ради этого эффекта метатайлинг был включён в раунде 32; отключать
   его без данных о реальном профиле повторных заходов — риск
   разменять один непроверенный выигрыш на другой непроверенный
   проигрыш.
3. Симптом, из-за которого начался раунд (891мс на сломанном слое),
   объясняется фактом поломки (блок A: 400 без рендера вообще) в
   гораздо большей степени, чем размером метатайла — после фикса
   реальный «холодный» тайл занимает те же ~680-700мс (C1), что
   субъективно не отличается от жалобы пользователя, а не хуже неё.

Эмулятор возвращён в исходное состояние (`metaWidthHeight=4×4`,
как было) — команда проверки:
```
ssh 192.168.251.190 'source ~/repikurr/.env && curl -s -u admin:$GEOSERVER_ADMIN_PASSWORD \
  http://localhost:8090/geoserver/gwc/rest/layers/pikurr:image_assessment.xml | grep -A2 metaWidthHeight'
```

### C4. Доля сетевой задержки до пользователя

Из C1: на **холодном** соединении снаружи TLS-хендшейк (координатор →
VPS) — **~335мс** сам по себе, это **~49%** от полных ~683мс на
свежий (MISS) тайл. На **тёплом** (переиспользованном) соединении —
round32, блок A.4 уже установил для того же маршрута (координатор↔VPS,
другой, векторный слой, но тот же сетевой путь): внешний RTT даёт
**~130-230мс** (~55-70% от типичного тёплого ответа ~230-320мс),
TLS на холодном — ещё **+400-800мс** сверху. Сегодняшнее измерение
(335мс TLS на холодном соединении) — того же порядка, что и round32
A.4 (371-501мс `time_appconnect`), совпадение ожидаемо (тот же
сетевой путь, тот же тип ВМ), не подгонялось.

**Вывод**: доля сетевой задержки до пользователя (RTT + TLS) в общем
времени ответа — доминирующая на холодном соединении (около половины
и больше), сопоставимая по порядку величины с ценой рендера метатайла
при `MISS` на самой VPS. Оба фактора реальны и складываются в худшем
случае (первый визит на новую область, новое TLS-соединение) — именно
эта комбинация правдоподобно стоит за подобными пользовательскими
жалобами на «около секунды» задержки, а не какой-то один из факторов
в отдельности.
