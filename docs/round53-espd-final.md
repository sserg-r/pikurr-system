## 1. Блок A

### A1. `assessment.id` при инициализации с нуля — сделано

**Происхождение расхождения.** Первоначально (коммит `610e235`) таблица создавалась с `id SERIAL PRIMARY KEY`; в раунде 28, блок E (коммит `e66e313`, «первая доставка на пустую БД без ручных вмешательств») определение было приведено к тому, что реально создаёт `ogr2ogr` при импорте пакета на витрине: `fid SERIAL PRIMARY KEY` плюс `id INTEGER NOT NULL` (значение приходит из пакета), а без `DEFAULT` — потому что для витрины `id` всегда задан явно. Про сценарий записи из ETL (`save_db.py` `id` не задаёт) тогда не думали: живая ETL-база создана раньше и имеет `id serial`.

**Как файл используется на сервере публикации** (по `REPIKURR/deliver.py`, `deploy.sh`, `docs/deploy-repikurr-vps.md`):
- `_package_schema_version()` читает из него только маркер `-- SCHEMA_VERSION = N` (регулярное выражение);
- целиком его выполняет `psql -f` (`recreate_views`, `deliver.py:863-895`) **только** через `ensure_assessment_schema()` — если материализованные представления отсутствуют, не материализованы или версия на объектах не равна `SCHEMA_VERSION` (первое развёртывание либо миграция); при совпадении версии шаг пропускается (`deliver.py:830-835`);
- `bootstrap_empty_schema.sql` выполняется вручную один раз на чистой базе до первого запуска GeoServer и содержит своё определение `assessment` (в нём была та же строка `id INTEGER NOT NULL`);
- частичного выполнения нет;
- перенос данных при каждой доставке (`_swap_staged_tables`, `deliver.py:478-590`) идёт в уже существующие боевые таблицы явным списком столбцов (`INSERT INTO … (cols) SELECT cols FROM …_stage`), а на пустой базе боевая таблица создаётся как `CREATE TABLE … (LIKE …_stage INCLUDING ALL)` из временной таблицы, созданной `ogr2ogr`, — не из этого DDL; поэтому правка DDL путь доставки не затрагивает.

**Исправление.** В обоих файлах (`create_assessment_schema.sql`, `bootstrap_empty_schema.sql`): `id INTEGER NOT NULL GENERATED BY DEFAULT AS IDENTITY` (последовательность создаётся вместе с таблицей и принадлежит ей; явное значение `id` по-прежнему допускается — путь импорта пакета не меняется). Выбран столбец-идентификатор, а не `CREATE SEQUENCE IF NOT EXISTS … DEFAULT nextval(…)` из примера в ТЗ: последний создавал бы «осиротевшую» последовательность на серверах, где таблица уже существует и `CREATE TABLE IF NOT EXISTS` пропускается; идентификатор появляется только вместе с новой таблицей. Существующие таблицы на VPS и стенде не изменяются (`ALTER` нет).

**`SCHEMA_VERSION` не повышался** (остаётся 3). Обоснование: структура материализованных представлений и путь импорта не меняются; версия сравнивается с маркером на **представлениях** — повышение вызвало бы `DROP`/пересоздание трёх материализованных представлений на боевом сервере при следующей доставке без необходимости. Существующие серверы новый вид `assessment.id` не получат (и не нуждаются в нём); он действует только для баз, создаваемых с нуля.

## 5а. Находки при эксплуатации ETL на стенде (после сдачи раунда)

1. **Потеря GPU контейнером `etl`.** Запуск шага 3 (сегментация) с панели завершился `RuntimeError: … CUDAExecutionProvider не активен` (ONNX Runtime: `no CUDA-capable device is detected`, откат на CPU). Диагностика (только чтение): на хосте `nvidia-smi -L` видит видеокарту и `/dev/nvidia*` на месте; внутри контейнера, запущенного 2026-09-28, `nvidia-smi -L` — `Failed to initialize NVML: Unknown Error`; драйвер cgroup Docker — `systemd`. Типичная причина — потеря доступа к устройствам у давно работающего контейнера после перезагрузки systemd/cgroup на хосте (что именно её вызвало — не выяснялось). Лечение — пересоздание контейнера (`docker compose -f docker-compose.yml up -d --force-recreate etl`); выполнено пользователем, сегментация прошла. Постоянное решение (`native.cgroupdriver=cgroupfs` в `daemon.json`) не применялось — изменение конфигурации стенда, решение за пользователем. Строка про симптом добавлена в руководство оператора (табл. 3, п. 4.1). Защитное поведение кода (явный отказ вместо тихого перехода на CPU, `PIKURR/src/services/inference.py:25-33`) сработало как задумано.
2. **Нет индикации прогресса на шаге 6 «Статистика БД» (и на шаге 7 «Публикация данных»).** `PIKURR/src/tasks/save_db.py:103` и `PIKURR/src/tasks/export.py:189` показывают ход через `tqdm`, который пишет в поток ошибок; панель управления перехватывает только `logging` и `print` (`PIKURR/dashboard.py:100-133`), поэтому в «Системном журнале» видна лишь строка `Processing N fields for year Y`. Остальные шаги (`download`, `segmentate`, `usability`, `classify`) используют `ProgressReporter` (строка прогресса каждые 30 с). Пользователь наблюдал шаг 6 более часа без сообщений и принял его за зависший.
   - Факты наблюдения (стенд, чтение, 2026-09-30): контейнер `etl` — ≈ 99,6 % одного ядра, БД — 0,2 % CPU; `max(updated_at)` в `assessment` каждую минуту двигался вперёд, число строк оставалось 55 784 (запись идёт поверх существующих строк — `UPSERT`); перезаписано 21 759 строк за ≈ 70 минут (с 11:34:36), в среднем ≈ 310 строк/мин (последняя минута — 424); оценка остатка — 80–110 минут (по числу перезаписываемых строк; итог может быть меньше, если поля без растров пропускаются). Способ наблюдения без доступа к журналу: `SELECT count(*) FROM assessment WHERE updated_at > '<время начала шага>'`.
   - **Не исправлено** (по решению пользователя: «пока не надо»). Предложение: подключить `ProgressReporter` в `save_db.py` и `export.py` так же, как в других задачах (изменение вывода, не расчёта).
