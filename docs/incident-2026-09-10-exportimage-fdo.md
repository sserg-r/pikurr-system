# Инцидент: geodzz.by exportImage возвращает FDO error -1 (2026-09-10)

## Кратко

С 12:59 UTC 10.09.2026 все запросы `exportImage` к сервису
`georesursDDZ/Belarus_Web_Mercator_new` на geodzz.by перестали отдавать
снимки — независимо от координат bbox. Старый тайловый эндпоинт того же
сервиса (`/tile/{level}/{row}/{col}`) при этом продолжает работать штатно.
Это не бан по IP и не полный отказ сервиса, а поломка конкретно динамической
сборки снимка (mosaic dataset query).

## Затронутый компонент

- Сервер: `georesursDDZ/Belarus_Web_Mercator_new` (ArcGIS ImageServer 10.22),
  `https://www.geodzz.by/arcgis/rest/services/georesursDDZ/Belarus_Web_Mercator_new/ImageServer`
- Внутренний потребитель: `src/services/dzz_export.py` (`fetch_block`,
  `fetch_tile_via_export`), метод фазы A блочной выкачки (`DZZ__USE_EXPORT=true`)
  в `src/tasks/download.py`
- Затронутый узел: `AMD_Belarus_WGS84_Web_Mercator_CAT` (mosaic dataset
  catalog, упоминается в тексте ошибки)

## Диагностика

Три контрольных запроса с сервера 192.168.251.190 (тот же IP и Referer, что
использует пайплайн):

1. **`exportImage`, точка в районе Минска** (bbox из области, где точно есть
   агрополя/снимки):
   ```
   GET .../exportImage?bbox=3050000,7150000,3060000,7160000&bboxSR=3857&imageSR=3857&size=256,256&format=jpg&f=image
   → HTTP 200, тело: {"error":{"code":400,"message":"Unable to complete operation.",
     "details":["FDO error: -1 [AMD_Belarus_WGS84_Web_Mercator_CAT]"]}}
   ```

2. **`exportImage`, точка в районе Бреста** (другой конец страны, для
   исключения локальной дыры в покрытии):
   ```
   GET .../exportImage?bbox=2650000,6980000,2660000,6990000&...
   → тот же результат: FDO error -1
   ```

3. **Старый тайловый эндпоинт `/tile/{level}/{row}/{col}`** для той же
   географической области:
   ```
   GET .../tile/11/40800/75920
   → HTTP 200, image/jpeg, 8325 байт — валидный снимок
   ```

4. **Метаданные сервиса** (`?f=json`) — не показательны сами по себе:
   отдаются из конфигурации сервиса и остаются живыми даже при полностью
   недоступном mosaic dataset, каталог этим тестом не проверяется.
   ```
   → HTTP 200, extent покрывает всю территорию Беларуси
   ```

5. **Различающий тест — прямой запрос к каталогу без рендеринга**:
   ```
   GET .../ImageServer/query?where=1%3D1&returnCountOnly=true&f=json
   → HTTP 200, тело: {"error":{"code":400,"message":"Failed to execute query.","details":[]}}
   ```
   `query` обращается к тому же каталогу `AMD_Belarus_WGS84_Web_Mercator_CAT`,
   что и `exportImage`, но не рендерит изображение — только читает записи.
   Ошибка здесь означает, что **не читается сам каталог**, а не только
   не работает сборка снимка.

**Вывод:** сервис и IP не заблокированы (иначе `/tile` тоже отвечал бы
ошибкой/403). Но ломается не только рендеринг — **недоступен сам каталог
`AMD_Belarus_WGS84_Web_Mercator_CAT`** (тест №5), причём для *любых*
координат в тесте №1–2, а не только для граничных/бездырых участков — это
отличает текущую ситуацию от единичных точечных FDO-ошибок, которые
наблюдались раньше на стыках зон покрытия и обрабатывались штатным
водопадом источников. Тайловый кэш (`/tile`) не читает каталог напрямую —
раздаёт статически подготовленные тайлы, поэтому и продолжает отвечать.

## Рабочая гипотеза

Раз недоступен сам каталог (не только рендер-путь), это больше похоже на
отказ инфраструктуры каталога на стороне geodzz.by (упавший/перегруженный
источник данных за mosaic dataset — БД или файловый провайдер), чем на
точечную деградацию одной лишь операции сборки снимка. Часовой прогон
блочной выкачки (11:44–12:38, `DZZ__BLOCK_WORKERS=2`, непрерывные
`exportImage`-запросы) мог быть триггером, если использовал тот же ресурс,
что и `query` (например, пул соединений FDO-провайдера) — но прямого
подтверждения со стороны geodzz.by нет, это гипотеза по совпадению времени
и характеру отказа.

Альтернативная гипотеза: плановое обслуживание/сбой каталога на стороне
geodzz.by, совпавший по времени с нашим прогоном (внешняя причина, от нас
не зависящая).

## Данные не потеряны

Резюмируемость (уже скачанные тайлы + общий пул `outputs/tiles/_pool/`) не
затронута — ничего не перезаписывается и не удаляется. При возобновлении
пайплайн продолжит с того места, где остановился.

## Рекомендации

1. Не продолжать нагружать `exportImage` тестовыми запросами — дать
   ресурсу на стороне geodzz.by время на восстановление.
2. Через несколько часов повторить тест №5 (`query returnCountOnly`) —
   он дешевле и точнее показывает восстановление каталога, чем повтор
   `exportImage`; если вернёт число вместо ошибки — можно возобновлять
   блочную выкачку.
3. Краткосрочный обходной путь (по решению пользователя, не применён): временно
   выставить `DZZ__USE_EXPORT=false`, чтобы пайплайн продолжил работу через
   потайловый водопад (`dzz-tile-cache → esri → google`), который сейчас
   подтверждённо исправен, ценой более медленной скачки.
4. Backlog: авто-детект систематического отказа `exportImage` (N ошибок FDO
   подряд на разных координатах) с автоматическим временным переключением
   на потайловый путь, вместо ручного вмешательства.
5. Backlog (см. также отдельно зафиксировано ранее): `-nlt PROMOTE_TO_MULTI`
   для `ogr2ogr` в `initialize.py` — сделано в этом же цикле, коммит `b65a906`.
