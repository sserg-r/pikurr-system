**Важная поправка методики (зафиксировано честно, т.к. привела к
неверному промежуточному выводу)**: первая попытка сравнить
`FRONTEND_DB_PASSWORD` с реальным паролем роли Postgres дала ложное
несовпадение (`879e798b` vs `777a7913`) из-за несогласованной обработки
завершающего `\n` при хешировании — часть значений извлекалась через
`git show ... | cut ... | $(...)` (перевод строки обрезается командной
подстановкой), часть — через прямой `grep | cut | sha256sum` по живому
файлу (перевод строки остаётся и меняет хеш). Проверено прямо:
```
$ printf 'pikurr\n' | sha256sum | cut -c1-8
879e798b
$ printf 'pikurr' | sha256sum | cut -c1-8
777a7913
```
Оба хеша — от одного и того же значения. После исправления методики
(везде `tr -d '\n'` перед `sha256sum`) выяснилось: **`FRONTEND_DB_PASSWORD`
в `deliver.env` стенда РЕАЛЬНО совпадал с паролем роли Postgres, и оба
совпадали с утёкшим значением** — таблица выше уже отражает
исправленный результат (строка 1: «совпадал с утечкой» — уже
прошедшее время, потому что пароль был сменён ниже, в A3).

**`pg_hba.conf` внутри `pikurr_srv_postgis`** — проверен для полноты,
но **не объясняет отсутствие риска**, как предполагалось до исправления
методики:
```
$ docker exec pikurr_srv_postgis cat /var/lib/postgresql/data/pg_hba.conf | grep -v '^#\|^$'
local   all   all                     trust
host    all   all   127.0.0.1/32      trust
host    all   all   ::1/128           trust
...
host all all all scram-sha-256
```
Правило `trust` относится только к соединениям, которые postgres внутри
контейнера видит как пришедшие с его собственного `127.0.0.1`/unix-socket
— то есть к диагностике через `docker exec ... psql`. `deliver.py`
работает не в контейнере, а прямо на хосте (запускается
`watchdog.py` через systemd, `ExecStart=/usr/bin/python3
.../watchdog.py`), и подключается через **опубликованный TCP-порт**
(`FRONTEND_DB_HOST=localhost`, `FRONTEND_DB_PORT=5435` — это порт
хоста, проброшенный docker'ом, не unix-socket контейнера). Проверено
фактом — такое подключение попадает под `host all all all
scram-sha-256`, то есть **пароль реально требуется**:
```
$ ssh 192.168.251.190 "PGPASSWORD='<новый>' psql -h 127.0.0.1 -p 5435 -U pikurr -d pikurr -tAc 'SELECT 1;'"
1
$ ssh 192.168.251.190 "PGPASSWORD='<утёкший>' psql -h 127.0.0.1 -p 5435 -U pikurr -d pikurr -tAc 'SELECT 1;'"
psql: error: ... FATAL:  password authentication failed for user "pikurr"
```
Итог: `FRONTEND_DB_PASSWORD` **был** настоящим рабочим паролем роли
`pikurr` в PostgreSQL на стенде, совпадающим с утёкшим значением — не
«мёртвой записью», как показалось на первой (ошибочной) итерации. Это
меняет вывод A2 ниже: экспозиция была реальной, а не теоретической.

По `GEOSERVER_PASSWORD` — иначе: `GEOSERVER_ADMIN_PASSWORD` в переменных
окружения контейнера `pikurr_srv_geoserver` применяется GeoServer'ом
**только при первом старте на пустом security-каталоге** — дальше
пароль живёт в персистентном `users.xml` (том с данными) и не зависит
от переменной окружения при последующих перезапусках. Значение в
`deliver.env` (`882400b6`, = «geoserver») подтверждено рабочим фактом
(этим же паролем в этой же сессии несколько раз успешно выполнялась
REST-аутентификация к GeoServer стенда — round24, задача 6, и разведка
только что) — то есть это и есть реальный текущий пароль администратора
GeoServer на стенде, совпадающий с утекшим в апреле значением.

```
22:      POSTGRES_PASSWORD: pikurr
34:      - GEOSERVER_ADMIN_PASSWORD=geoserver

```

```
38:      - GEOSERVER_ADMIN_PASSWORD=${GEOSERVER_ADMIN_PASSWORD:?Задайте GEOSERVER_ADMIN_PASSWORD в .env (см. .env.example)}
```

`GEOSERVER_ADMIN_PASSWORD` из переменной окружения контейнера **при
каждом пересоздании контейнера** (не только на первом старте на пустом

что при любом пересоздании контейнер откатывался обратно на утёкший
пароль. Это отдельный, ранее неизвестный дефект — «файл в git и файл
на диске разошлись», в этот раз не в watchdog-юните (round24), а в
самом compose-файле, несущем секрет.

```bash
git filter-repo --invert-paths --paths-from-file /tmp/paths-to-strip.txt

# 4. Принудительный пуш переписанной истории (ПОСЛЕ решения
#    пользователя — не выполнено в этом раунде).
```

**Что произойдёт с существующими клонами**: у всех, кто уже клонировал
репозиторий (в том числе оба клона этого проекта — на
`192.168.251.190` и локально), история разойдётся с origin
безвозвратно (другие SHA у всех коммитов после точки вычистки — сам
факт удаления объекта меняет хеш коммита и всех потомков). Обычный
`git pull` после такого force-push **не работает и даёт конфликты**;
единственный чистый путь для существующих клонов — удалить их и
клонировать заново с нуля. Любые локальные ветки/незакоммиченные
изменения в старых клонах (в этом репозитории их сейчас много — round23/24
правки, см. блок C1) нужно переносить вручную (cherry-pick / патчи) ДО
удаления старого клона.

**Принудительная перезапись публичного репозитория НЕ удаляет старые
объекты с GitHub автоматически.** GitHub хранит объекты коммитов до
сборки мусора (garbage collection), которая на бесплатных репозиториях
запускается по своему расписанию, не по команде пользователя. Коммит
`21f53d7` (и любой другой, ранее видимый в истории) **останется
доступен по прямому SHA** — как через `git cat-file`/`git show <SHA>`
у любого, кто уже знает или сохранил этот хеш (в том числе через кэш
поисковых систем, форки, Wayback Machine, или локальные клоны других
людей, если репозиторий кто-то уже клонировал до вычистки) — так и
потенциально через GitHub API/UI, пока GC не пройдёт.

**Что нужно, чтобы гарантированно убрать данные с GitHub**:
- запрос в поддержку GitHub (support.github.com) на принудительную
  сборку мусора и удаление конкретных объектов/коммитов — официальный
  задокументированный путь для случаев утечки секретов;
- альтернатива проще, но радикальнее: **удалить репозиторий полностью
  и создать заново без истории** (терять всю историю коммитов, issues,
  PR, звёзды, форки других пользователей — тоже придётся пересоздавать
  вручную или заново). Решение зависит от того, насколько ценна
  сохранённая история проекта для пользователя.
- ни `filter-repo`, ни force-push сами по себе **не решают** проблему
  форков — если кто-то уже сделал fork репозитория на GitHub до
  вычистки, у форка сохранится независимая копия истории со старыми
  коммитами, которую автор `pikurr-system` не контролирует.

**Вывод**: ротация секретов (A3) обязательна в любом случае — она
единственная реально закрывает риск использования утёкших значений
СЕЙЧАС. Вычистка истории — дополнение (снижает шанс, что кто-то
случайно наткнётся на секрет через обычный `git log`/`git blame`), а
не замена ротации: даже после идеальной вычистки истории и force-push
уже утёкшие в прошлом значения остаются потенциально скомпрометированы
навсегда (кто угодно мог их сохранить в любой момент с апреля по
сегодня) — именно поэтому ТЗ этого раунда правильно ставит ротацию
(A3) раньше вычистки истории (A4) и не делает вычистку условием
ротации.

**Решение о переписывании истории принимает пользователь** — в этом
раунде не выполнялось.

### B2. Убрать `DROP ... CASCADE` из пути доставки

**Реализовано** в `REPIKURR/deliver.py`:

1. `import_vectors()` — `ogr2ogr -overwrite` теперь пишет в
   `<layer>_stage` (`agrifields_stage`, `razgrafka_stage`,
   `assessment_stage`), не в боевые имена. `-overwrite` по-прежнему
   делает `DROP TABLE ... CASCADE`, но роняет **только staging-таблицы**
   — у них по определению нет зависимых объектов (каждая доставка
   создаёт их заново с нуля), каскадить нечему.
2. `_swap_staged_tables()` — перенос одной транзакцией:
   `BEGIN; TRUNCATE agrifields, razgrafka, assessment; INSERT INTO
   <table> SELECT * FROM <table>_stage; DROP TABLE ..._stage; COMMIT;`.
   `TRUNCATE` (в отличие от `DROP`) не меняет OID таблицы и не требует
   пересоздания зависимых объектов — `assessment_ready` переживает эту
   операцию, продолжая отдавать **старые, ещё валидные** данные вплоть
   до последующего `REFRESH`.
3. `recreate_views()` — теперь путь **только миграции**. Новая функция
   `assessment_ready_is_materialized()` проверяет `relkind` объекта
   перед вызовом; если это уже `'m'` (материализованное представление),
   `recreate_views()` полностью пропускается, доставка сразу переходит
   к `REFRESH MATERIALIZED VIEW`.

**Побочная находка при внедрении** (важно честно зафиксировать —
не имеет отношения к самой атомарности, но всплыла из-за более раннего
шага этого же раунда): после ротации пароля роли `pikurr` в PostgreSQL
(A3) первая же тестовая доставка на стенде вскрыла, что **у GeoServer
есть СВОЙ, отдельно хранимый пароль** для подключения к тому же PostGIS
(`connectionParameters` датастора `postgis_pikurr`, зашифрован в
`geoserver.jceks` тем самым мастер-паролем, который в этом же раунде не
удалось сменить, см. A3) — он не подхватывает смену пароля роли
автоматически и продолжает пытаться подключаться со старым значением,
из-за чего WFS/WMS первое время после ротации отдавали
`ServiceExceptionReport` (`password authentication failed`) — **не
из-за дефекта атомарности**, а из-за того, что пароль был сменён не во
всех местах, где он хранится. Обновлено через REST
(`PUT /rest/workspaces/pikurr/datastores/postgis_pikurr.json`, с полным
набором `connectionParameters`, не только `passwd` — первая попытка
передать только `passwd` **стёрла остальные параметры** датастора
целиком, урок зафиксирован для раздела «Предлагаемые исправления»).
Это означает, что пароль роли `pikurr` в PostgreSQL сейчас хранится (и
должен обновляться синхронно) минимум в **четырёх** местах:
`deliver.env`, реальная роль в PostgreSQL, `docker-compose.server.yml`
(через `.env`), и датастор GeoServer — раньше это не было
задокументировано ни в одном отчёте.

**Проверено фактом** (подробности — B3 ниже): `assessment_ready_is_materialized()`
корректно определяет уже-материализованный объект и пропускает
`recreate_views()`; `_swap_staged_tables()` отрабатывает за ~1с на
стенде; OID `assessment_ready` не меняется между доставками подряд.

### B4. Статус-файл при аварийном завершении

**Реализовано** в `deliver.py`:
- `_StepTracker` теперь пишет **промежуточный** статус
  (`step_in_progress`, `ok: null`) при **каждой** смене шага — не
  только в `finally` в конце;
- обработчики `signal.signal(SIGTERM/SIGINT, _handle_signal)` — при
  получении сигнала записывают в общую переменную `error_msg` текст
  `"Прервано сигналом {SIGTERM|SIGINT}"` и передают управление
  единственному месту, которое реально пишет финальный статус-файл
  (`finally` в `main()`), с `step_failed=<текущий шаг>`.

**Найденный и исправленный при тестировании баг** (честно, не
скрываю): первая версия обработчика сигнала писала статус
**самостоятельно**, а затем управление всё равно попадало в `finally`,
который писал **второй раз** — с `error=None`, затирая только что
записанную причину. Обнаружено на первом же живом тесте `kill -TERM`
(смотри протокол ниже — первая доставка на стенде правильно показывала
`step_failed`, но `error: null`), исправлено переносом записи ошибки в
разделяемую переменную, читаемую `finally`.

**Проверка фактом — `kill -TERM` на трёх разных шагах** (тестовый
стенд, прямой вызов `deliver.py`):

| Шаг | Статус-файл после `kill -TERM` |
|---|---|
| `copy_rasters` | `{"ok": false, "step_failed": "copy_rasters", "error": "Прервано сигналом SIGTERM"}` |
| `import_vectors` | `{"ok": false, "step_failed": "import_vectors", "error": "Прервано сигналом SIGTERM"}` |
| `refresh_materialized_view` | `{"ok": false, "step_failed": "refresh_materialized_view", "error": "Прервано сигналом SIGTERM"}` |

**Подтверждено**: во всех трёх случаях статус-файл есть, шаг указан
верно, причина — понятный текст, а не пустое значение.

**`kill -9` — уточнение относительно буквальной формулировки ТЗ**
(«статуса нет»): на практике **не совсем «статуса нет вообще»** —
промежуточная запись (`step_in_progress`, `ok: null`), сделанная ДО
убийства процесса при последней смене шага, физически остаётся на
диске (SIGKILL убивает процесс мгновенно, не даёт ничего досделать, но
и не откатывает уже записанный ранее файл). В реальном тесте (см. B3,
«kill -9 во время import_vectors») статус-файл после убийства содержал
`{"step_in_progress": "import_vectors", "ok": null}` — **это не
финальный, «правильный» статус с `step_failed`, но и не полное
отсутствие диагностики**: видно, на каком шаге доставка была в момент
гибели процесса, чего не было вообще ни при каком раунде до этого
(round24 задача 5: было буквально пусто). `PushTask`, опрашивающий
статус, при `ok: null` не получит ни успеха, ни явного провала —
затянувшееся ожидание `ok != null` в итоге упрётся в таймаут, но с
частичной подсказкой (`step_in_progress`) в самом файле, если кто-то
откроет его руками. Задокументировано честно как факт, не
подгонялось под формулировку ТЗ задним числом.

### C3. Заглушка `bootstrap_empty_schema.sql`

**Сначала — факт по`docs/deploy-repikurr-vps.md`, раздел 3**: слои в
GeoServer на чистом инстансе появляются **не REST-вызовами с нуля**, а
из **версионированного `geoserver_data/`**, который целиком
монтируется как том при `docker compose -f docker-compose.vps.yml up
-d` (шаг 4 раздела 3) — сама процедура не содержит ни одного REST-вызова
создания workspace/datastore/featuretype. Раздел 3 предполагает, что
`geoserver_data/` уже содержит нужную конфигурацию слоёв (перенесённую
с уже работавшего инстанса, как и произошло на самом
`geobotany.of.by` — round22, round24 задача 6 это подтвердили
фактом).

**Следствие**: дефект №6 из round24 (`nativeBoundingBox`/`srs` остаются
от момента создания слоя над пустой заглушкой, `EPSG:404000`) — это
**свойство конкретного тестового метода round24** (создание featuretype
REST-вызовом с нуля поверх пустой БД), а не свойство документированной
процедуры развёртывания, которая слои с нуля через REST никогда не
создаёт. Вызов пересчёта bbox в `deliver.py:reload_geoserver()`
остаётся уместным как страховка на случай, если однажды `geoserver_data/`
для нового окружения действительно соберут с нуля (а не перенесут с
уже рабочего), но не как исправление уже наблюдавшегося на практике
сценария — такого сценария на практике не было.

**Правка типов колонок** — `stats` (`jsonb` → `character varying`,
как в реальной таблице `assessment`), `geom` (`geometry` без типа/SRID
→ `geometry(MultiPolygon,4326)`, чтобы GeoServer не подставлял
`EPSG:404000` уже на этапе заглушки, если featuretype всё же создаётся
не из перенесённого `geoserver_data/`, а REST-вызовом), `district`
(`varchar` → `varchar(4)`, как в боевом представлении). `area_ha` и
`valuation` уже присутствовали в заглушке корректно (round24 неверно
указал их как отсутствующие — на самом деле оба были, ошибка того
отчёта исправлена здесь, задним числом, не путём переписывания
round24-документа, а фиксацией факта здесь).

**Проверено фактом** — применение исправленного скрипта к чистой БД:
```
$ CREATE EXTENSION postgis; \i bootstrap_empty_schema.sql
$ \d assessment_ready
   geom      | geometry(MultiPolygon,4326)
   stats      | character varying
   district   | character varying(4)
```
Применяется без ошибок, миграционный путь (реальный
`create_assessment_schema.sql` поверх этой заглушки) не проверялся
повторно в этом раунде — механизм `DROP VIEW ... CASCADE` →
`CREATE MATERIALIZED VIEW` не зависит от точных типов колонок
заглушки (весь объект целиком заменяется), это уже было проверено
фактом в round23/round24.

Реальный `create_assessment_schema.sql` и боевое представление — не
тронуты (правка только в `bootstrap_empty_schema.sql`).

### C7. Стор `image_assessment_2024` — факт, без удаления

**Не удалялось** (явный запрет ТЗ). Зафиксирован факт:
```
$ curl -u admin:*** http://localhost:8090/geoserver/rest/workspaces/pikurr/coveragestores/image_assessment_2024.json
{"coverageStore":{"name":"image_assessment_2024", ...,
 "url":"file:///mnt/data/geodata/2024/", ...}}

$ ls ~/repikurr/data/geodata/2024
ls: cannot access '.../geodata/2024': No such file or directory
```
Каталог, на который указывает стор, не существует на диске VPS. Стор
загружается при `/rest/reload` без ошибок в лог (`CONFIG [org.geoserver]
- Loaded coverage store 'image_assessment_2024', enabled` — не warning,
не error), но **прямой запрос к слою `pikurr:image_assessment_2024`
возвращает `ServiceExceptionReport`**:
```
java.io.IOException: Failed to create reader from file:///mnt/data/geodata/2024/ ...
```

**Чем это грозит при `reload`**: пока к этому слою никто не
обращается напрямую (текущий `year_district.json` содержит только
2025 — фронтенд не строит на него ссылку), стор просто «висит»
безвредно и переживает каждый `/rest/reload` без ошибок. Риск —
если когда-нибудь в БД снова появятся строки с `year=2024` (например,
переливка старых данных) без восстановления соответствующего каталога
растров — фронтенд предложит пользователю год 2024 в выпадающем
списке, а WMS для него будет стабильно возвращать
`ServiceExceptionReport`. Также, если `_rebuild_mosaic_index()`/
`_reload_one_store()` из `deliver.py` когда-либо вызовутся для года
2024 (доставка мультигодового пакета, включающего 2024), они будут
работать с несуществующим каталогом — не проверялось фактом в этом
раунде (нет такого пакета под рукой, и это разрушительный эксперимент
на бою, вне разрешённого метода этого раунда для VPS).

Решение (восстановить каталог/данные, или явно удалить стор) — за
пользователем, явно связано с вопросом многолетности витрины (round24,
задача 3), не решаемым фактами этого раунда.
