# CLAUDE.md

Инструкции для работы с этим репозиторием (PIKURR/REPIKURR — ETL и
доставка данных геоботанической оценки полей). Один раунд — одна
сессия (`prompts/SESSION_RESTART.md`); всё, что новой сессии нужно
знать, должно быть здесь или в `docs/round*.md`, не только в контексте
прошлой сессии.

## Не делать

- не менять `passes_quality()`, `segmentate.py`, пороги цветовой
  коррекции (`is_green`, `is_soil`, `is_water_blue`), модель,
  нормализацию входа;
- не менять математику `merge_imageset` (формулы сдвигов, паддинг, кроп);
- не менять схему БД ETL-контура;
- не переобучать и не предлагать переобучение;
- не удалять карантин раунда 16 и каталоги `_removed_`;
- не коммитить `.env`, `deliver.env`, пароли, хеши `basic_auth`,
  приватные ключи — проверять `git check-ignore -v` перед добавлением
  любого файла, похожего на конфигурацию с секретами;
- не записывать временные тайлы в `_pool/` или в папки листов;
- не переписывать историю git без явного запроса пользователя —
  решение о переписывании истории (`git filter-repo`/BFG, force-push)
  принимает пользователь, не Claude Code;
- не менять состав годов на витрине без явного решения пользователя
  (round39: 2024 год удалён по явному решению — «данные 2024 года на
  проде не нужны, вычистить полностью»; стор `image_assessment_2024`
  на самом деле никогда не существовал в каталоге GeoServer, round25
  зафиксировал факт по косвенным признакам — см. "Открытые вопросы");
- не подстраивать замеры под цифры прошлых раундов — каждый замер
  самостоятельный, с честным указанием источника при сравнении.

## Ловушки, купленные ошибками

- **`docker compose` только с `-f <нужный файл>`** — без него на обеих
  машинах поднимается ДРУГОЙ дефолтный `docker-compose.yml`
  (например, ETL вместо REPIKURR), создавая паразитный
  неправильно названный контейнер и лишний том (round32). Правильный
  файл для существующего контейнера — `docker inspect
  <контейнер> --format '{{index .Config.Labels
  "com.docker.compose.project.config_files"}}'`.
- **`docker restart`/тег образа не заставляют контейнер подхватить
  новый образ** — контейнер привязан к ID образа на момент создания;
  после `docker tag ... :latest` нужен `docker compose -f <файл> up -d
  --force-recreate <сервис>` (round32).
- **На эмуляторе `nginx.local.conf` резолвит upstream `geoserver`
  СТАТИЧЕСКИ при собственном старте**, не лениво через Docker DNS —
  если `geoserver`-контейнер недоступен по имени в момент старта/рестарта
  nginx, nginx падает целиком (`host not found in upstream`), забирая
  с собой и раздачу React SPA (тот же nginx хендлит `/`). На проде
  Caddy так не делает (резолвит на каждый запрос) — риск специфичен
  для стенда (round33, найдено при инъекции отказа GeoServer, не
  исправлено — не было причиной реальной аварии).
- **REST `PUT` на GWC diskquota меняет только рантайм, никогда не
  пишет файл на диске** — причина найдена фактом в round34 (block D1):
  `PUT /geoserver/gwc/rest/diskquota.xml` сразу виден через `GET` того
  же URL, но `geoserver_data/gwc/geowebcache-diskquota.xml` на диске
  остаётся со старым значением байт-в-байт сразу после успешного PUT,
  ДО какого-либо рестарта — то есть дело не в «REST-настройка не
  переживает рестарт» (это была верная, но неполная формулировка
  round33), а в том, что REST для этого конкретного эндпоинта вообще
  не персистентен, только runtime. При старте GeoServer читает файл на
  диске и переопределяет рантайм-значение обратно к дефолту (20 GiB).
  **Устойчивое решение — писать сам файл напрямую**, не полагаться на
  REST: `REPIKURR/tools/gwc_diskquota_2gib.xml` (инструкция применения
  и отката — в комментарии файла; схема на диске отличается от
  REST-схемы, корневой элемент `<gwcQuotaConfiguration>`, не
  `<org.geowebcache.diskquota.DiskQuotaConfig>`). Проверено фактом
  рестартом на эмуляторе и на VPS (round34) — квота 2 GiB пережила
  `docker compose restart geoserver` на обеих машинах. Регистрация
  тайловых слоёв (grid, `metaWidthHeight`, `expireClients`) — тоже
  файловая и тоже переживает рестарт (не путать с этим пунктом, это
  было верно и раньше).
- **HTTP-проверка не исполняет JavaScript.** `curl`/`healthcheck.py`
  видят код 200 и корректный `index.html`, даже если весь React
  падает с необработанным исключением при рендере (round33: `MapView.jsx`
  использовал `const` до объявления — `ReferenceError` на каждой
  загрузке с момента деплоя round32, никто не заметил, потому что
  верификация была HTTP-level). Выкатка фронтенда не считается
  проверенной, пока не пройден дымовой сценарий в настоящем браузере
  (см. "Инструменты измерения").
- **`docker-compose depends_on` без `condition: service_healthy`
  управляет только порядком СОЗДАНИЯ контейнеров**, не ожиданием
  реальной готовности приложения внутри — GeoServer (JVM) после
  старта контейнера ещё ~15-90с (машинозависимо) не готов принимать
  запросы, а Caddy/nginx уже проксируют на него.
- **Ответ `200` с пустым/синтетическим телом — не успех.** WFS/WMS
  могут отдать `200` с `ServiceExceptionReport` (round24); Caddy
  `handle_response` без `copy_response` подменяет ЛЮБОЙ ответ апстрима
  (включая `404`/`500`) на пустой `200` (round30). Проверять код **и**
  тело, всегда.
- **Нагрузочный тест без проверки содержимого измеряет пустоту, не
  производительность** (round31, блок B): случайные bbox дают до 100%
  пустых тайлов, время рендера пустоты систематически ниже времени
  рендера данных. Использовать `docs/round32_assets/tiles_with_data.json`
  или явно замерять и показывать долю пустых/маленьких ответов.
- **`watchdog.py` (`pikurr-watchdog.service`) работает не только на
  эмуляторе, но и на VPS** — перехватывает пакеты из `~/repikurr/inbox/`
  на ОБЕИХ машинах (найдено фактом round38: прошлые формулировки этого
  раздела и памяти утверждали «только на эмуляторе» — не так; не
  выяснялось, с какого раунда это верно на VPS). Ручной параллельный
  запуск `deliver.py` с ним конкурирует за один и тот же пакет (см.
  `flock` в watchdog, round21 A4, но конкуренция за СМЫСЛ доставки — не
  за файл — всё ещё возможна). round38 также наблюдал дважды подряд
  ложный отказ `unpack` («File is not a zip file») сразу после `cp`
  корректного (сверенного по sha256) файла в inbox — похоже на гонку
  между записью и подхватом вотчдогом, не исследовано глубже; обходной
  путь, который сработал — переносить (`mv`), а не копировать (`cp`),
  уже провалившуюся, но целую по sha256 копию обратно в inbox.
- **Секрет БД в разных местах должен обновляться синхронно**: пароль
  роли `pikurr` и пароль администратора GeoServer живут одновременно в
  `deliver.env`, реальной роли PostgreSQL, `.env` (docker-compose) и
  датасторе `postgis_pikurr` внутри GeoServer (`geoserver.jceks`).
  Смена пароля БД без обновления всех четырёх — `ServiceExceptionReport`
  («password authentication failed») при полностью корректной
  остановке доставки (round25).
- **Не доверять старым записям памяти о правах доступа без
  перепроверки** — `sudo` на эмуляторе был недоступен на 2026-09-14 и
  доступен на 2026-09-23 (round33); что изменилось, не выяснялось.
- **Общий эндпоинт GWC (`/geoserver/gwc/service/wms`) требует имя слоя
  С ПРЕФИКСОМ workspace** (`pikurr:слой`), в отличие от обычного
  `/geoserver/pikurr/wms`, где workspace уже в пути и префикс
  необязателен (round34, блок A) — стоило рабочего растрового слоя на
  проде целый раунд: фронтенд слал `layers=image_assessment` без
  префикса, GWC отвечал `400 Unknown layer` на каждый тайл, а
  `healthcheck.py` этого не видел, т.к. проверял только
  `/geoserver/pikurr/wms` (см. "Критерий приёмки" и блок B round35 —
  проверки должны ходить по тем же URL, что фронтенд).
- **`/geoserver/gwc/service/wms` полностью ИГНОРИРУЕТ `CQL_FILTER` и
  `STYLES`** — отдаёт байт-в-байт тот же закэшированный тайл независимо
  от их значения (round37, блок A1: три запроса с разным `CQL_FILTER`/
  `STYLES`/без них дали идентичный md5 ответа и `geowebcache-cache-result:
  HIT` во всех трёх). Это не баг, а следствие того, как GWC ключует кэш
  (только по слою/стилю-по-умолчанию/bbox/zoom, не по производным WMS-
  параметрам) — но код, который передаёт `CQL_FILTER` в GWC-запрос,
  молча получает нефильтрованный результат вместо ошибки, поэтому баг
  не бросается в глаза. До round37 это уже проявлялось незаметно: попытка
  подсветить выбранную группу через `pikurr:fields_latest` (кэшируемый
  слой) с `CQL_FILTER` в параметрах ничего не фильтровала — отсюда и
  запрос раунда 37 ("все поля выглядят одинаково"). Любой фильтр по
  подмножеству объектов ОБЯЗАН идти через обычный `/geoserver/pikurr/wms`
  (или другой не-GWC путь), никогда через `/geoserver/gwc/service/wms`.
- **WMS-параметр `time` со значением, которое не парсится как дата,
  роняет запрос в `ServiceExceptionReport` с HTTP 200** (round37,
  побочная находка при A1/A2) — фронтенд подставлял в `time` плейсхолдер
  `'loading'` (см. `MapView.jsx`, `cacheBuster`) в узком окне до ответа
  `/static/year_district.json`; GeoServer трактует `time` как WMS-
  размерность TIME и валит запрос с `java.text.ParseException: Invalid
  date: loading`. Классический пример "200 ≠ успех" из раздела
  "Критерий приёмки" — код 200, тело `ServiceExceptionReport`, тайл
  Leaflet считает ошибкой (`tileerror`), при накоплении — баннер
  деградации. Исправлено — `time` не передаётся вовсе, пока версия
  данных ещё не известна, вместо подстановки плейсхолдера.
- **`deliver.py`/`healthcheck.py` на VPS не обновляются автоматически
  вместе с репозиторием** — в отличие от фронтенда (`deploy_frontend_vps.sh`
  явно катит новый образ), для этих двух файлов выделенного скрипта
  синхронизации не было. Найдено фактом (round37, блок C): реальная
  доставка на VPS показала, что статус доставки не содержит ключ
  `seed_gwc_cache` вообще — `md5sum`/`diff` подтвердили, что `deliver.py`
  на VPS был копией ДО round35, без единой строки кода прогрева GWC,
  несмотря на то что CLAUDE.md (и сам `deliver.py` в репозитории)
  описывали фичу как "включена по умолчанию" с round36. Прямое следствие:
  доставка truncate'ила GWC-кэш (эта часть логики в старом файле уже
  была), но досеять было некому — прод какое-то время отдавал холодные
  тайлы после КАЖДОЙ доставки с round35 по round36 включительно,
  никем не замеченное (`healthcheck.py`/`smoke.mjs` проверяют
  успешность ответа и HIT/MISS отдельным вызовом, не сравнивают
  ожидание "прогрето по умолчанию" с фактом). Синхронизировано
  (round37) — `deliver.py`, `healthcheck.py`, плюс на VPS обнаружилось
  плоское развёртывание без `docs/`/`tools/smoke/` из монорепо, из-за
  чего `TILES_WITH_DATA_PATH`/`CAPTURED_GWC_URLS_PATH` не были заданы
  (см. `healthcheck.py` — без них `gwc_layer[...]`/`filtered_layer`
  красные по независящей от кода причине) — заведены в
  `~/repikurr/support_data/` и `deliver.env`. **Урок**: любой файл,
  который правится в репозитории (не только фронтенд), нужно либо
  включать в существующий деплой-скрипт, либо явно фиксировать в этом
  файле СПОСОБ его доставки на прод — иначе рассинхрон копится молча.
  Закрыто (round38, блок D4) — `REPIKURR/deploy_backend_vps.sh`
  (по образцу `deploy_frontend_vps.sh`): `--check` сравнивает
  контрольные суммы `deliver.py`/`healthcheck.py`/`watchdog.py` и
  вспомогательных файлов `healthcheck.py` на VPS против репозитория без
  изменений, `--apply` синхронизирует (с бэкапом старых файлов
  `.bak_pre_deploy_<TS>` на VPS, проверкой `py_compile` после копирования
  и перезапуском `pikurr-watchdog.service`, если менялся `watchdog.py`).
- **Сборка пакета из локальной ETL-базы без проверки её содержимого —
  способ незаметно подменить боевые данные** (round38, полный разбор —
  `docs/round38-data-incident.md`). round37, блок C собрал пакет
  `pikurr_update_2024_2025_2026-09-24_09-41.zip` из контейнера

  (`docker kill <name>`, `docker rm <name>`), никогда через `docker ps
  -q` без фильтра. `docker system prune` — та же категория риска
  (действует на всю машину), тоже не выполнять без явного запроса
  пользователя на конкретную операцию.

## Правила замеров

- Цифры со стенда/эмулятора (`192.168.251.190`), VPS
  (`geobotany.of.by`) не смешивать и не переносить друг на друга;
  каждый замер подписывать машиной. Разница — на порядок и больше
  (round24/25: `REFRESH MATERIALIZED VIEW` — единицы секунд на стенде,
  десятки на VPS; round33: готовность GeoServer после перезагрузки —
  ~15с на эмуляторе, ~51-90с на VPS).
- Минимум 3 повтора, порядок перемешан, состояние кэша (холодный/тёплый)
  указано явно.
- Разброс на VPS до 3× и выше — свойство burstable-машины, не аномалия
  (не пытаться объяснять или устранять сам разброс).
- **Правило непустых тайлов**: доля ответов < 2 КБ указывается в
  КАЖДОМ замере скорости витрины; если она выше 20% — замер не
  считается валидным выводом (round32, после наблюдения 42-100% пустых
  тайлов на случайных bbox в round28-31).
- Не подстраивать новые замеры под цифры прошлых раундов — каждый
  самостоятелен, сравнение — с честным указанием источника.

## Критерий приёмки — по содержимому, не по коду ответа

WFS/WMS GeoServer могут отдавать `HTTP 200` с телом
`ServiceExceptionReport` (round24, задача 2) — протокольная
особенность старых версий WFS/WMS, не баг GeoServer, но означает, что
проверка по HTTP-коду слепа к реальным сбоям. Любая проверка
работоспособности витрины должна разбирать тело ответа
(`REPIKURR/healthcheck.py`, round25, блок B5), а не только код.

Симметричный случай на стороне Caddy (round30, блок C, найдено
проверкой ТЕЛА `/geoserver/nonexistent`, а не только заголовков — до
этого баг жил в проде незамеченным целый раунд): директива
`handle_response` внутри `reverse_proxy` по умолчанию НЕ пробрасывает
исходный ответ апстрима дальше — без явного `copy_response` первой
строкой внутри блока `handle_response` статус и тело подменяются
пустым синтетическим `200 Content-Length: 0`, даже если GeoServer
реально ответил `404`/`500`/`ServiceExceptionReport`. Не доверять
`handle_response` без проверенного факта, что `copy_response`
присутствует.

**Тот же принцип на уровне фронтенда (round33)**: HTTP-код 200 и
корректный `index.html` ничего не говорят об успешности выполнения JS
на клиенте — необработанное исключение при рендере (без React Error
Boundary) размонтирует всё дерево React, оставляя `#root` пустым.
Верификация фронтенда после серьёзных правок обязана включать реальный
браузер (см. "Инструменты измерения"), не только HTTP-уровневые
проверки. `ErrorBoundary` (`REPIKURR/repikurr/src/components/ErrorBoundary.jsx`,
round33) не предотвращает баги, но не даёт будущему необработанному
исключению снова превращаться в тишину.

- **Схема БД**: `SCHEMA_VERSION = 3` (`REPIKURR/deliver.py`). Три
  материализованных представления: `assessment_ready`,
  `assessment_ready_latest`, `levelsagg_ready` (все должны быть

- **Провенанс пакета и предполётные проверки** (round38, блок D,
  разбор подмены боевых данных — `docs/round38-data-incident.md`).
  Манифест пакета (`PIKURR/src/tasks/package.py`, `version: "2.1"`)
  несёт: `source_db` (хост/имя БД, не пароль), `etl_git_commit`,

  статус-файл (ключ `manifest`), доступно сразу при чтении статуса, без
  распаковки ZIP. Перед ЛЮБЫМ изменением боевых данных — две
  последовательные проверки (обе оставляют боевые таблицы нетронутыми
  при отказе): версия схемы (round29, была раньше) и **состав лет**
  (round38, `_check_year_composition` — сверяет `manifest["years"]` с
  набором лет, уже стоящим в боевой `assessment`; несовпадение —
  `YearCompositionGuardError`, обход — `--allow-year-change`). Это
  ДОПОЛНЕНИЕ к проверке усадки (round26, `SwapGuardError`, обход —
  `--allow-shrink`) — усадка ловит уменьшение ОБЪЁМА, состав ловит
  подмену НАБОРА лет независимо от того, вырос объём или нет (round38-
  инцидент: строк стало больше). Сразу после обеих проверок, до первого
  реального изменения БД — `pg_dump` боевых `agrifields`/`razgrafka`/
  `assessment` (`backup_before_swap()`, custom-формат `-Fc`,
  `REPIKURR/backups/`, ротация по числу файлов —
  `BACKUP_RETENTION_COUNT`, по умолчанию 10) — первый штатный путь
  отката ДАННЫХ (раньше — только случайно уцелевшие копии на других
  машинах, см. запись round38 в "Ловушки"). Результат — в статусе,
  ключ `backup`. Восстановление: `pg_restore -d <db> <файл>.dump`.
- **GWC-кэш**: включён (round32) для `pikurr:fields_latest` (векторный)
  и `pikurr:image_assessment` (текущий растр), grid `EPSG:900913`

  `_truncate_gwc_layer_if_cached()` для векторных слоёв сразу после
  `refresh_materialized_view()` и для растровых — внутри
  `_reload_one_store()`.
- **Прогрев кэша (seed) при доставке** (round35, блок C; причина
  "зависания" найдена и устранена round36) — реализован (`deliver.py`,
  `seed_gwc_cache()`/`_seed_gwc_layer()`, шаг после `reload_geoserver`),
  **включён по умолчанию** (`GWC_SEED_ENABLED=true`). round35 приняла
  зависание на ~50% за реальную проблему GWC — round36 (декомпиляция
  GWC 1.24.2 + 13/13 воспроизводимых прогонов на эмуляторе и VPS)
  установила: реального зависания не было, это баг в САМОМ `deliver.py`
  — при `threadCount>1` каждый поток репортит ОДНО И ТО ЖЕ полное
  значение `tilesTotal` (не свою долю), а код суммировал `total` по
  потокам, искусственно удваивая отображаемую цель. Пустой список
  задач GWC — легитимное завершение (`RUNNING→DONE`, задача вычищается
  `drain()`), проверено по содержимому (диск + HIT на контрольных
  тайлах) в 13/13 прогонов. Подробности — `docs/round36-seeding-fix.md`.
  `GWC_SEED_MAX_WAIT_S` поднят `300→420с` — полный диапазон z9-14 на

  объёма и времени (round36). round42 также решил, что z9 структурно
  не досеивается (0 файлов на диске при проверках) и что z10-z12 не
  доходит до 100% — **оба вывода были методологической ошибкой,

  проверял несуществующий путь. При правильной проверке и сверке с

  "файлы перестали расти" — признак затишья, не признак ДОСТИЖЕНИЯ
  цели; добавлена независимая сверка итога с геометрическим расчётом
  (`tile_math.tile_range_for_bbox_3857` по `nativeBoundingBox` слоя из
  REST) — недобор > 10% и > 3 тайлов пишется в статус как
  `shortfall_warning` с обеими цифрами, доставку не останавливает
  (прогрев — оптимизация). Порог подобран так, чтобы не шуметь на
  малых z9/z10 и на легитимном крае bbox. Проверено фактом на VPS:
  нормальный прогон (z9-z12, оба слоя) — точное совпадение факт/расчёт
  (1835/1835, 1992/1992), без предупреждения; на контрольном тесте с
  искусственно удалённой половиной z12 — предупреждение с верными
  числами (847/1835, 53.8%).
- **Эндпоинты**: кэшируемые слои (`fields_latest`, текущий
  `image_assessment`) — через `/geoserver/gwc/service/wms` с
  `tiled=true` (стандартный `/geoserver/pikurr/wms` НЕ включает GWC
  даже с `tiled=true` — проверено фактом, round32). Историчные слои
  (`fields` с `CQL_FILTER=year=...`, `image_assessment_<год>`) — через
  обычный `/geoserver/pikurr/wms` напрямую (GWC для них не
  регистрировался — не входило в объём round32). **Важно** (round34,
  блок A): `/geoserver/gwc/service/wms` не виртуализован по workspace,
  параметр `layers` там ОБЯЗАН быть полным именем (`pikurr:слой`);
  `/geoserver/pikurr/wms` принимает оба варианта, т.к. workspace уже в
  пути — фронтенд (`MapView.jsx`) теперь передаёт полное имя в обоих
  случаях (`rasterFqName`/`vectorLayer`).
- **Фронтенд**: `ErrorBoundary` на верхнем уровне (`main.jsx`), баннеры
  деградации при недоступности `year_district.json` и при массовых
  ошибках тайлов WMS (`MapView.jsx`, `tileerror`), атрибуция карты —
  только сторонние источники (OSM/Esri), без ссылки на саму Leaflet
  (round33). Выкатка на бой обязана пройти
  `REPIKURR/tools/smoke/smoke.mjs` (round34, блок B) — см. "Инструменты
  измерения".
- **Подсветка выбранной группы** (round37, блок A) — при выборе области/
  района/землепользователя поля вне группы приглушаются (константа
  `DIMMED_OPACITY`, `constants.js`), а не скрываются (решение
  пользователя). Устройство — два слоя `pikurr:fields`/`fields_latest`
  одновременно, не один слой с двумя стилями:
  - **нижний (фон)** — тот же слой и тот же путь, что и раньше (GWC,
    когда кэшируем; `CQL_FILTER` только по году, БЕЗ группы), просто с
    `opacity={DIMMED_OPACITY}` при активном выборе. Непрозрачность —
    свойство Leaflet на клиенте (`GridLayer.setOpacity` → CSS
    `style.opacity`), не трогает URL тайла и не портит попадания в GWC
    (проверено фактом, round37 A1).
  - **верхний (подсветка)** — тот же слой, но ВСЕГДА через обычный
    `/geoserver/pikurr/wms` (никогда через GWC — см. "Ловушки": GWC
    игнорирует `CQL_FILTER`), с `CQL_FILTER` = год (если выбран) +
    группа (`nr_user LIKE '<код>%'`, код — область/район/полный код
    землепользователя). Рисуется поверх фона (выше `zIndex`), рендерится
    только когда группа активна.
  - Почему приглушение на клиенте, а не вторым стилем на сервере: второй
    стиль означал бы, что нижний слой рисуется с ИНЫМИ WMS-параметрами
    при активном выборе — GWC счёл бы это другим набором тайлов
    (кэш ключуется в т.ч. по стилю) и прогретый кэш обесценился бы
    (весь смысл раздела "Цена прогрева" ниже). Приглушение на клиенте не
    меняет URL/параметры нижнего слоя вообще — фон продолжает быть
    100% тем же запросом, что и без выбора.
  - Клик/всплывающая карточка — без изменений, фильтруются тем же
    сочетанием год+группа, что и верхний слой.
  - Пустая группа (0 объектов) — не пустая карта: сообщение над картой
    (`App.jsx`, проверка через WFS `resultType=hits`).
- **Caddy**: `lb_try_duration=60s` (round34, блок D2 — 30с оказались
  мало для реального прод-рестарта GeoServer, 3 прогона на VPS дали
  34.9-36.9с окна полной недоступности, все выше 30с).
- **Внешний мониторинг**: systemd timer на эмуляторе, `healthcheck.py`
  каждые 5 минут против прод-домена, лог с ротацией (round33). Способ
  уведомления пользователя (Telegram-бот и другие варианты) —
  спроектирован, не внедрён.
