# CLAUDE.md

Инструкции для работы с этим репозиторием (PIKURR/REPIKURR — ETL и
доставка данных геоботанической оценки полей). Раздел «Не делать» —
постоянная часть, действует во всех раундах, если явно не указано
иное в конкретном ТЗ.

## Не делать

- не менять `passes_quality()`, `segmentate.py`, пороги цветовой
  коррекции (`is_green`, `is_soil`, `is_water_blue`), модель,
  нормализацию входа;
- не менять математику `merge_imageset` (формулы сдвигов, паддинг, кроп);
- не менять схему БД ETL-контура;
- не переобучать и не предлагать переобучение;
- не удалять карантин раунда 16 и каталоги `_removed_`;
- не коммитить `.env`, `deliver.env`, пароли, хеши `basic_auth`,
  приватные ключи — проверять `git check-ignore -v` перед добавлением
  любого файла, похожего на конфигурацию с секретами;
- не записывать временные тайлы в `_pool/` или в папки листов;
- не переписывать историю git без явного запроса пользователя —
  решение о переписывании истории (`git filter-repo`/BFG, force-push)
  принимает пользователь, не Claude Code;
- не удалять стор `image_assessment_2024` в GeoServer и не менять
  состав годов на витрине без явного решения пользователя (round25:
  зафиксирован факт существования стора на несуществующий каталог, не
  устранён — решение связано с вопросом многолетности витрины);
- не подстраивать замеры под цифры прошлых раундов — каждый замер
  самостоятельный, с честным указанием источника при сравнении.

## Правило непустых тайлов

Любой замер скорости витрины делается на тайлах **с реальными
данными** (round32: наблюдение показало, что нагрузочный тест на
случайных bbox давал от 42% до 100% пустых тайлов, round31, блок B —
медианы получались в разы ниже реальных именно потому, что почти
ничего не рендерилось). В каждом отчётном замере указывать долю
ответов < 2 КБ; замер, где эта доля выше 20%, выводом не считается.
Фиксированный проверенный набор — `docs/round32_assets/tiles_with_data.json`
(20 bbox по центроидам полей, каждый подтверждён фактом на непустой
ответ) — использовать его в последующих раундах вместо новых
случайных bbox, если не появится причина расширить набор.

## Нагрузочный тест без проверки содержимого измеряет пустоту, не производительность

Урок round31 (блок B) и его причина: k6-сценарии до этого раунда
проверяли только код ответа (`200`) и не разбирали, есть ли в теле
реальные данные. Раз GeoServer честно отдаёт валидный, но пустой PNG/
FeatureCollection для bbox без полей — такой тест НЕ ошибается по
коду, а измеряет время рендера пустоты, которое системно ниже
времени рендера реальных данных. Любой новый нагрузочный сценарий
обязан либо использовать проверенный набор непустых bbox (см. выше),
либо явно замерять и указывать долю пустых/маленьких ответов в самом
отчёте — тишина по этому пункту недостаточна, число нужно показывать
фактом.

## Правило замеров производительности

**Цифры со стенда `192.168.251.190` и с VPS (`geobotany.of.by`,
`158.160.237.90`) не смешивать и не переносить друг на друга.**
Стенд — 12-16 полных vCPU. VPS — 2 **долевых** (burstable) vCPU с
гарантированной долей ~50% (прерываемая ВМ). Разница в
производительности между ними — на порядок и больше (round24, round25:
одна и та же операция REFRESH MATERIALIZED VIEW — единицы секунд на
стенде, десятки секунд на VPS). Каждый замер времени/производительности
обязательно подписывать машиной, на которой он снят; вывод, сделанный
на одной машине, не может служить оценкой для другой без явной
переоценки.

## Критерий приёмки — по содержимому, не по коду ответа

WFS/WMS GeoServer могут отдавать `HTTP 200` с телом
`ServiceExceptionReport` (round24, задача 2) — это протокольная
особенность старых версий WFS/WMS, не баг GeoServer, но означает, что
проверка по HTTP-коду слепа к реальным сбоям. Любая проверка
работоспособности витрины должна разбирать тело ответа
(`REPIKURR/healthcheck.py`, round25, блок B5), а не только код.

Симметричный случай на стороне Caddy (round30, блок C, найдено
проверкой ТЕЛА `/geoserver/nonexistent`, а не только заголовков —
до этого баг жил в проде незамеченным целый раунд): директива
`handle_response` внутри `reverse_proxy` по умолчанию НЕ пробрасывает
исходный ответ апстрима дальше — без явного `copy_response` первой
строкой внутри блока `handle_response` статус и тело подменяются
пустым синтетическим `200 Content-Length: 0`, даже если GeoServer
реально ответил `404`/`500`/`ServiceExceptionReport`. Проверка одних
только заголовков ответа (без разбора тела) эту подмену не увидит —
`Cache-Control` может быть выставлен корректно на пустом `200`, тело
при этом всё равно потеряно. Правило то же, что и выше: проверять
код **и** тело, и для Caddy-конфигурации в частности — не доверять
`handle_response` без проверенного факта, что `copy_response`
присутствует.

## Секреты

Пароль роли `pikurr` в PostgreSQL и пароль администратора GeoServer
хранятся синхронно в НЕСКОЛЬКИХ местах (round25, блок B2 — найдено при
ротации): `deliver.env`, реальная роль в PostgreSQL, `.env`
(используется `docker-compose.server.yml`/`docker-compose.vps.yml`), и
датастор `postgis_pikurr` внутри самого GeoServer
(`connectionParameters`, зашифрован мастер-паролем в
`geoserver_data/security/geoserver.jceks`). При смене пароля роли
Postgres — обновлять **все четыре** места, иначе WFS/WMS начнут
отдавать `ServiceExceptionReport` («password authentication failed»)
при полностью корректной остановке доставки.

## Обязательная проверка перезагрузкой после изменений инфраструктуры

round33: сценарий «ВМ остановлена и запущена заново» ни разу не
проверялся за всю кампанию — когда это случилось в реальности
(пользователь вручную перезапустил VPS), витрина оказалась сломана.
Причина в тот раз была не в перезагрузке как таковой (белый экран —
`ReferenceError` в `MapView.jsx` из-за обращения к `const` до его
объявления, round32 блок C, `c6af923` — ломало сайт при КАЖДОЙ загрузке
уже с момента деплоя, просто до перезагрузки это не заметили), но сама
процедура впервые вскрыла и её, и отдельные, не связанные с ней риски
(GWC disk quota не переживает рестарт GeoServer, окно ~60-90с между
стартом контейнера GeoServer и его реальной готовностью, за которое
`docker-compose depends_on` без `condition: service_healthy` ничего не
гарантирует). **Правило**: после любого изменения
docker-compose/Caddyfile/nginx.local.conf/systemd-юнитов —
`sudo reboot` соответствующей машины и проверка витрины по содержимому
без единого ручного действия (`docs/deploy-repikurr-vps.md`, раздел 8);
не считать изменение принятым, пока это не пройдено.

## Необработанное исключение при рендере — это не мелочь, а весь сайт

round33: `MapView.jsx` использовал `const vectorIsCached` в `useMemo`
ВЫШЕ строки, где эта константа объявлена (temporal dead zone) —
`ReferenceError` на каждом без исключения рендере. Без React Error
Boundary такое исключение размонтирует ВСЁ дерево React, оставляя
`#root` пустым — белый экран без единого сообщения, неотличимый на
первый взгляд от отказа инфраструктуры. Урок из этого — не про
конкретный порядок объявлений (это должен ловить линтер/ревью), а про
процесс проверки: HTTP-код 200 и корректный `index.html` НИЧЕГО не
говорят об успешности выполнения JS на клиенте (тот же паттерн, что и
«код 200 не значит корректное содержимое» для WMS/WFS/Caddy выше в этом
файле, но уровнем ближе к пользователю) — верификация фронтенда после
серьёзных правок обязана включать проверку в реальном браузере
(консоль, а не только сетевые ответы), не только curl/healthcheck.py.
`ErrorBoundary` (добавлен в round33, блок C.1) не предотвращает баг, но
не даёт будущему аналогичному исключению снова превращаться в тишину.
