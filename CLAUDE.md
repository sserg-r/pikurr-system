# CLAUDE.md

Инструкции для работы с этим репозиторием (PIKURR/REPIKURR — ETL и
доставка данных геоботанической оценки полей). Один раунд — одна
сессия (`prompts/SESSION_RESTART.md`); всё, что новой сессии нужно
знать, должно быть здесь или в `docs/round*.md`, не только в контексте
прошлой сессии.

  коррекции (`is_green`, `is_soil`, `is_water_blue`), модель,
  нормализацию входа;
- не менять математику `merge_imageset` (формулы сдвигов, паддинг, кроп);
- не менять схему БД ETL-контура;
- не переобучать и не предлагать переобучение;
- не удалять карантин раунда 16 и каталоги `_removed_`;
- не коммитить `.env`, `deliver.env`, пароли, хеши `basic_auth`,
  приватные ключи — проверять `git check-ignore -v` перед добавлением
  любого файла, похожего на конфигурацию с секретами;
- не записывать временные тайлы в `_pool/` или в папки листов;

  решение о переписывании истории (`git filter-repo`/BFG, force-push)

## Ловушки, купленные ошибками

- **`docker compose` только с `-f <нужный файл>`** — без него на обеих
  машинах поднимается ДРУГОЙ дефолтный `docker-compose.yml`
  (например, ETL вместо REPIKURR), создавая паразитный
  неправильно названный контейнер и лишний том (round32). Правильный
  файл для существующего контейнера — `docker inspect
  <контейнер> --format '{{index .Config.Labels
  "com.docker.compose.project.config_files"}}'`.
- **`docker restart`/тег образа не заставляют контейнер подхватить
  новый образ** — контейнер привязан к ID образа на момент создания;
  после `docker tag ... :latest` нужен `docker compose -f <файл> up -d
  --force-recreate <сервис>` (round32).
- **На эмуляторе `nginx.local.conf` резолвит upstream `geoserver`
  СТАТИЧЕСКИ при собственном старте**, не лениво через Docker DNS —
  если `geoserver`-контейнер недоступен по имени в момент старта/рестарта
  nginx, nginx падает целиком (`host not found in upstream`), забирая
  с собой и раздачу React SPA (тот же nginx хендлит `/`). На проде
  Caddy так не делает (резолвит на каждый запрос) — риск специфичен
  для стенда (round33, найдено при инъекции отказа GeoServer, не
  исправлено — не было причиной реальной аварии).
- **REST-настройки GeoServer/GWC не все переживают перезапуск**:
  регистрация тайловых слоёв (grid, `metaWidthHeight`, `expireClients`)
  — файловая, переживает; квота диска GWC (`diskquota.xml`) — НЕТ,
  откатывается к дефолтным 20 GiB при каждом перезапуске GeoServer
  (round33). Переприменять из `REPIKURR/tools/gwc_diskquota_2gib.xml`
  после любой перезагрузки/пересоздания контейнера GeoServer.
- **HTTP-проверка не исполняет JavaScript.** `curl`/`healthcheck.py`
  видят код 200 и корректный `index.html`, даже если весь React
  падает с необработанным исключением при рендере (round33: `MapView.jsx`
  использовал `const` до объявления — `ReferenceError` на каждой
  загрузке с момента деплоя round32, никто не заметил, потому что
  верификация была HTTP-level). Выкатка фронтенда не считается
  проверенной, пока не пройден дымовой сценарий в настоящем браузере
  (см. "Инструменты измерения").
- **`docker-compose depends_on` без `condition: service_healthy`
  управляет только порядком СОЗДАНИЯ контейнеров**, не ожиданием
  реальной готовности приложения внутри — GeoServer (JVM) после
  старта контейнера ещё ~15-90с (машинозависимо) не готов принимать
  запросы, а Caddy/nginx уже проксируют на него.
- **Ответ `200` с пустым/синтетическим телом — не успех.** WFS/WMS
  могут отдать `200` с `ServiceExceptionReport` (round24); Caddy
  `handle_response` без `copy_response` подменяет ЛЮБОЙ ответ апстрима
  (включая `404`/`500`) на пустой `200` (round30). Проверять код **и**
  тело, всегда.
- **Нагрузочный тест без проверки содержимого измеряет пустоту, не
  производительность** (round31, блок B): случайные bbox дают до 100%
  пустых тайлов, время рендера пустоты систематически ниже времени
  рендера данных. Использовать `docs/round32_assets/tiles_with_data.json`
  или явно замерять и показывать долю пустых/маленьких ответов.
- **На эмуляторе работает собственный `watchdog.py`**
  (`pikurr-watchdog.service`), перехватывающий пакеты из `~/repikurr/inbox/`
  — ручной параллельный запуск `deliver.py` с ним конкурирует за один
  и тот же пакет (см. `flock` в watchdog, round21 A4, но конкуренция за
  СМЫСЛ доставки — не за файл — всё ещё возможна).
- **Секрет БД в разных местах должен обновляться синхронно**: пароль
  роли `pikurr` и пароль администратора GeoServer живут одновременно в
  `deliver.env`, реальной роли PostgreSQL, `.env` (docker-compose) и
  датасторе `postgis_pikurr` внутри GeoServer (`geoserver.jceks`).
  Смена пароля БД без обновления всех четырёх — `ServiceExceptionReport`
  («password authentication failed») при полностью корректной
  остановке доставки (round25).
- **Не доверять старым записям памяти о правах доступа без
  перепроверки** — `sudo` на эмуляторе был недоступен на 2026-09-14 и
  доступен на 2026-09-23 (round33); что изменилось, не выяснялось.

## Правила замеров

- Цифры со стенда/эмулятора (`192.168.251.190`), VPS
  (`geobotany.of.by`) не смешивать и не переносить друг на друга;
  каждый замер подписывать машиной. Разница — на порядок и больше
  (round24/25: `REFRESH MATERIALIZED VIEW` — единицы секунд на стенде,
  десятки на VPS; round33: готовность GeoServer после перезагрузки —
  ~15с на эмуляторе, ~51-90с на VPS).
- Минимум 3 повтора, порядок перемешан, состояние кэша (холодный/тёплый)
  указано явно.
- Разброс на VPS до 3× и выше — свойство burstable-машины, не аномалия
  (не пытаться объяснять или устранять сам разброс).
- **Правило непустых тайлов**: доля ответов < 2 КБ указывается в
  КАЖДОМ замере скорости витрины; если она выше 20% — замер не
  считается валидным выводом (round32, после наблюдения 42-100% пустых
  тайлов на случайных bbox в round28-31).
- Не подстраивать новые замеры под цифры прошлых раундов — каждый
  самостоятелен, сравнение — с честным указанием источника.

## Критерий приёмки — по содержимому, не по коду ответа

WFS/WMS GeoServer могут отдавать `HTTP 200` с телом
`ServiceExceptionReport` (round24, задача 2) — протокольная
особенность старых версий WFS/WMS, не баг GeoServer, но означает, что
проверка по HTTP-коду слепа к реальным сбоям. Любая проверка
работоспособности витрины должна разбирать тело ответа
(`REPIKURR/healthcheck.py`, round25, блок B5), а не только код.

Симметричный случай на стороне Caddy (round30, блок C, найдено
проверкой ТЕЛА `/geoserver/nonexistent`, а не только заголовков — до
этого баг жил в проде незамеченным целый раунд): директива
`handle_response` внутри `reverse_proxy` по умолчанию НЕ пробрасывает
исходный ответ апстрима дальше — без явного `copy_response` первой
строкой внутри блока `handle_response` статус и тело подменяются
пустым синтетическим `200 Content-Length: 0`, даже если GeoServer
реально ответил `404`/`500`/`ServiceExceptionReport`. Не доверять
`handle_response` без проверенного факта, что `copy_response`
присутствует.

**Тот же принцип на уровне фронтенда (round33)**: HTTP-код 200 и
корректный `index.html` ничего не говорят об успешности выполнения JS
на клиенте — необработанное исключение при рендере (без React Error
Boundary) размонтирует всё дерево React, оставляя `#root` пустым.
Верификация фронтенда после серьёзных правок обязана включать реальный
браузер (см. "Инструменты измерения"), не только HTTP-уровневые
проверки. `ErrorBoundary` (`REPIKURR/repikurr/src/components/ErrorBoundary.jsx`,
round33) не предотвращает баги, но не даёт будущему необработанному
исключению снова превращаться в тишину.

## Текущее состояние системы

- **Схема БД**: `SCHEMA_VERSION = 3` (`REPIKURR/deliver.py`). Три
  материализованных представления: `assessment_ready`,
  `assessment_ready_latest`, `levelsagg_ready` (все должны быть
  `ispopulated = t`).
- **GWC-кэш**: включён (round32) для `pikurr:fields_latest` (векторный)
  и `pikurr:image_assessment` (текущий растр), grid `EPSG:900913`
  (=Web Mercator, соответствует тайлам Leaflet), `metaWidthHeight`
  4×4, `expireCache=0` (не истекает сам, только явный truncate),
  `expireClients=86400` (браузерный `Cache-Control`). Квота диска —
  2 GiB, **не персистентна** через рестарт GeoServer (см. "Ловушки").
  Инвалидация — `deliver.py` вызывает `_truncate_gwc_layer_if_cached()`
  для векторных слоёв сразу после `refresh_materialized_view()` и для
  растровых — внутри `_reload_one_store()`.
- **Эндпоинты**: кэшируемые слои (`fields_latest`, текущий
  `image_assessment`) — через `/geoserver/gwc/service/wms` с
  `tiled=true` (стандартный `/geoserver/pikurr/wms` НЕ включает GWC
  даже с `tiled=true` — проверено фактом, round32). Историчные слои
  (`fields` с `CQL_FILTER=year=...`, `image_assessment_<год>`) — через
  обычный `/geoserver/pikurr/wms` напрямую (GWC для них не
  регистрировался — не входило в объём round32).
- **Фронтенд**: `ErrorBoundary` на верхнем уровне (`main.jsx`), баннеры
  деградации при недоступности `year_district.json` и при массовых
  ошибках тайлов WMS (`MapView.jsx`, `tileerror`), атрибуция карты —
  только сторонние источники (OSM/Esri), без ссылки на саму Leaflet
  (round33).
- **Внешний мониторинг**: systemd timer на эмуляторе, `healthcheck.py`
  каждые 5 минут против прод-домена, лог с ротацией (round33). Способ
  уведомления пользователя (Telegram-бот и другие варианты) —
  спроектирован, не внедрён.

### Открытые вопросы (сознательно не закрыты)

- **Автозапуск ВМ (Cloud Function)** — код и инструкция готовы с
  round23, фактический статус развёртывания не подтверждён: у Claude
  Code нет API-доступа к Yandex Cloud. Проверять по логам функции в
  консоли (см. `docs/round33-reboot-incident.md`, блок B4).
- **`image_assessment_2024` — стор на несуществующий каталог** (round25)
  — не устранено, решение зависит от вопроса многолетности витрины,
  который пользователь ещё не принял.
- **53-76× vs 11-14× расхождение в оценке ускорения** (round31, блок A)
  — объявлено невосстановимым, дальнейшие раунды считают от
  собственных свежих замеров, не пытаются согласовать со старым
  расхождением.
- **k6 VU=3, один прогон из 9 — 30% таймаутов** (round32) — гипотеза
  (control-flow GeoServer при 60 одновременных запросах с одного IP)
  не подтверждена отдельным экспериментом; `controlflow.properties` не
  трогать без явного решения пользователя.
